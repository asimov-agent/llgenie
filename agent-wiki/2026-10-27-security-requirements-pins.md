# 2026-10-27 — the compile inputs state the versions the scan demands

Issue: [#754](https://github.com/asimov-agent/llgenie/issues/754)
OpenSpec change: `security-requirements-pins` (capability `requirements-pins`)

## Why

The daily scan ([run 40537601445](https://github.com/asimov-agent/llgenie/actions/runs/40537601445),
event `schedule`) failing its verdict with eight critical/high findings was not a scanner problem: the
three packages it names — `certifi` (critical, GHSA-6q48-6c7w-9gw2), `filelock` (CVE-2026-112940) and
`urllib3` (CVE-2026-97687/97689) — are transitive pins of the generated `tools/requirements*.txt`, and
the compile inputs stated no version for them or for the direct deps that pull them in (`numpy`,
`huggingface_hub[cli]>=0.30`). The remediation bot only edits a *direct* pin, so it refused all three.
Nothing in the repository could move them, and every scan re-reported the same advisories.

## What changed

- `tools/requirements.in` pins the direct runtime deps exactly (`numpy==2.4.6`, `gguf==0.19.0`,
  `huggingface_hub[cli]==1.30.0`) and states each scanned package's report `fixed` version as an
  annotated `>=` floor.
- `tools/requirements-dev.in` carries the same three floors, because the test image installs the
  runtime and dev pins together.
- Both compiled files were regenerated by `make -C tools generate-requirements` /
  `generate-requirements-dev` (venv fallback — no `nerdctl` on this host). No `.txt` was hand-edited.
- `tests/test_requirements_pins.py` locks the shape: annotated direct pins, annotated floors, and no
  compiled pin below its floor in either file.

## Verified against the spec

- `docker run … llgenie/test:latest python -m pytest tests/test_requirements_pins.py -q` -> **4 passed**.
- `make security-bumps-plan` against the failing run's own reports -> *every floor is already satisfied
  by the compiled pins* (compiled `certifi==2026.10.23`, `filelock==4.2.4`, `urllib3==2.8.0`).
- The verdict subcommand reads the **report artifact**, which is a snapshot of the old image, so
  re-running `make security-verdict` on it can only restate its findings; the next scheduled scan
  re-scans the new pins. That distinction is recorded in the issue's acceptance criteria and in the
  change's `tasks.md`.

## Decision

`tools/security-floors.in` was left alone: it is written only by `make security-bumps` and says so in
its own header. The human-owned compile inputs are the right place for a version the repository
intends, and the bot's floor file remains the mechanism for a future advisory the bot places itself.
