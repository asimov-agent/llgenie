# LLGenie Pipeline Maintainer: add a committed-secret scanner to the security gate

Implements issue #1283 (ready-for-review PR, never merged). A committed **secret** — a `ghp_`/`sk-…`
GitHub or cloud key, a bearer inside a URL — is now a first-class finding in the daily security
pipeline: `make security-scan TOOL=trivy` asks the SAME digest-pinned trivy image for its `secret`
ruleset (`--scanners vuln,secret`), the finding flows through `security-verdict` and
`security-issues` exactly like a CVE, and it reds the daily run (and therefore the all-pipelines
admission-gate sweep) because a committed credential is always actionable — `require_fix` must not
suppress it while `fail_on` still does.

## What changed (measured on this worktree)

- `scripts/security_scan.py` — trivy base is now `--scanners vuln,secret` (was `vuln` only). Added
  `_trivy_secret_findings()` (a `trivy` `Secret`-class result becomes the same fixed finding shape:
  `id` = RuleID, `package` = the file, `current` = redacted match, `fixed` = `""`) and a
  `SECRET_SOURCE = "trivy-secret"` constant. `findings()` reads both the vulnerability array and the
  `Secrets` array from the same `trivy.json`. `blocking()` treats `SECRET_SOURCE` findings as always
  actionable (removal + rotation, never "wait for a patched version") while still honouring
  `fail_on` — a `medium`/`unknown` secret is recorded, never a red.
- `scripts/security_issues.py` — `issue_findings()` no longer lets `require_fix` keep a committed
  secret off the tracker; it becomes a `component:code` issue (not python/container) and is never
  `auto-fixable` (a secret is removed, not version-bumped).
- Tests: `tests/test_security_scan.py` (+5) and `tests/test_security_issues.py` (+1) prove the
  normalisation, the verdict gate, the report-only PR mode and the issue path.

## Verification (measured, not asserted)

- `python3 -m pytest tests/test_security_scan.py tests/test_security_issues.py -q` in the
  `llgenie/test:latest` image: **39 passed**.
- The tree scanned with `--scanners vuln,secret` at this head reports **0 Secrets** (only the pip
  language packages), so enabling the scanner does not red the daily run on a clean tree.
- A planted `aws_access_key_id` fixture in the worktree scan reports `aws-access-key-id` /
  `CRITICAL` through the same `--scanners secret` path (the scanner image 0.70.0 detects it).

This change never weakens the security gate: `make check-security-scan` still forbids a
`push`/`pull_request` trigger, the scan is still its own daily pipeline (issue #738), and a secret
reds exactly the events `enforce_events` already names.
