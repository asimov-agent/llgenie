# 2026-11-02 vllm image-build fix: vendored Rust frontend + rocm/cpu CMake (issue #1365)

vLLM's committed image build breaks on all three arch cells at the pinned `5df63a72`
(measured run `41342311363`). This branch fixes them so the `engine-build` pipeline can
publish every vllm image at its committed post-#1378 tag:

- **rust frontend**: `bash tools/build_rust.sh` before the `-e .` install — vllm `5df63a72`
  vendors a Rust frontend (channel 1.95); without the precompiled artifact the base image has
  no usable cargo toolchain.
- **rocm triton pin**: the vendored `requirements/build/rocm.txt` names the bare
  `triton==3.7.1+git0263a6a6` while its own `torch==2.12.0+rocm7.14.0` requires the
  rocm-suffixed wheel — normalize it before the build-requirements install.
- **rocm HIP/CMake env**: the `-e .` step must point CMake at the base image's `/opt/rocm`
  (`ROCM_HOME`/`ROCM_PATH`/`HIP_PATH` + `CMAKE_MODULE_PATH` → `.../lib/cmake/hip;.../hip-lang`);
  otherwise torch's `LoadHIP.cmake` falls back to the pip `rocm-sdk-core` wheel root and fails
  `No FindHIP.cmake in CMAKE_MODULE_PATH` / `Optional package HIP not found`.
- **cpu libnuma-dev + torchvision/torchaudio ABI**: the cpu cell compiles `csrc/cpu/utils.cpp` which
  needs `numa.h` — add `libnuma-dev` to the cpu container's apt deps. Two cpu failures proved
  independent: the `numa.h` fix let the compile succeed (`vllm==0.32.0+cpu` built), but `vllm --version`
  then died at import with `RuntimeError: operator torchvision::nms does not exist` — cpu.txt installs
  `torch==2.13.0+cpu` from the cpu index but lets bare `torchvision`/`torchaudio` resolve from default
  PyPI, whose `_C` is built against the non-`+cpu` torch ABI, so `torchvision::nms` never registers.
  Fix: preinstall `torchvision torchaudio` from the SAME cpu index as torch (ABI-matched wheels).
- **error surfacing**: `--progress=plain` on buildx + print the captured child stdout/stderr on
  a non-zero rc, so a real docker-layer failure reaches the CI log instead of a silent 14s FAIL.

Each change lives in the engine skill (`skills/engines/vllm/SKILL.md`) and is regenerated into
`containers/engines/params/vllm.json` + `containers/engines/dockerfiles/vllm/Dockerfile.cpu` via
`scripts/engine_skills.py params --only vllm` — the JSON is a generated artifact, never hand-edited.
The vllm tag shifts (rocm/cpu variant params changed) as a designed consequence of the fix.
