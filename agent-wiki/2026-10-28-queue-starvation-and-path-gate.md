# 2026-10-28 — a starved runner queue is not a broken PR, and a PR stops queueing rows it did not need

**Issue:** [#817](https://github.com/asimov-agent/llgenie/issues/817) · **PR:** [#825](https://github.com/asimov-agent/llgenie/pull/825) · **OpenSpec:** `queued-starvation-and-path-gate`

## What was wrong

On 2026-10-28 the repository could not finish a CI run: **18 runs `queued`, 0 `in_progress`**, GitHub
reporting `Actions: operational`. Every open PR's checks sat `pending`, every PR read `BLOCKED`, and
`auto-merge`, `fix-bot` and `rebase-bot` correctly did nothing. Three agents spent about an hour treating
that as a defect in their own workflows, and one recommended merging to drain the queue — which a push to a
`pull_request` cannot do, because `ci.yml` sets `cancel-in-progress` on that event and re-queues the whole
matrix.

Nothing in `docs/BOTS.md` told a reader how to separate "the queue is starved" from "my PR is broken", so
each reader derived it from scratch, and two derived it wrong.

## What changed

`docs/BOTS.md` gains **A queue is not a verdict** (after the generated dispatch table, so
`make check-dispatch-forms` is untouched): the two commands that measure supply
(`gh run list --json status` counts; `gh run view <id> --json jobs` per-job wait), the distinction from
#801's class (one PR's empty rollup with `DIRTY` is a branch needing a rebase), and the "never merge or push
to drain the queue" rule with the measured cost.

## Decisions

- **Prose only, no new target and no new gate.** The measurement already exists — `make queued-alarm`
  (`scripts/queued_run_alarm.py`, `minutes` default 30) — so the doc points at it rather than inventing a
  second test.
- **Two discriminators were proposed and both were wrong; the doc records the correction.** `runner_name` is
  `null` for an `in_progress` job too, and `startedAt` is set at *enqueue*, not at pickup. Verified against
  live runs before writing a line; the wrong version would have been pasted into the doc and trusted.
- **Outside the generated block.** `<!-- dispatch-forms:begin/end -->` is regenerated by
  `make dispatch-forms-report`, so a paragraph inside it would be silently overwritten.

## The second half: a PR queued toolchains it had not touched

Measured from the runs' own job lists: **#786** (a security-script PR, run 40698685046) queued **28
jobs**, four of them `engine-base-cpu/cuda/rocm/vulkan` and one `scanner-images`, for a diff that
touched none of them; **#803** (an engine bump, run 40704612341) queued 26, four of them base rows it
had not changed. The engine matrix already narrowed itself by changed tag (#153); the shared base
toolchains had no gate.

| before | after |
|---|---|
| `engine-base` ran `backend: [cpu, cuda, rocm, vulkan]` unconditionally (4 slots) | matrix from `make list-engine-base-images CHANGED=<ref>`: the changed backends, or ONE `backend: none` row |
| a security-script PR: 28 jobs | 4 base slots collapse to 1 placeholder row that skips every step |

The placeholder row is the idiom `engine-image` already uses (an empty `include` list fails the workflow
before any `if:` is evaluated, run 38105450418), so `tests/test_ci_images.py`'s allowlist gains exactly
one literal — `matrix.backend != 'none'` — and no job-level `if:` or skipped step appears.

**Rows left wide, deliberately:** `ci-images` (one cheap pull-or-build that every job pulls from),
`scanner-images` (one job; removing its slot needs a job-level `if:` or a workflow split that changes the
required-check set — an owner decision), and `pipeline.yml`'s Linux/macOS suites (the actual test gate).
