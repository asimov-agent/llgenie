The `check-pr-sync-line` gate (issue #1724) anchored its profile diff at the literal range start (`git diff --name-only base..head -- agents/`), but the gate's `PR_BASE` is the **live** `origin/main` ref that the workflow step refreshes to the main TIP (scope.yml / ci.yml). `git diff A..B` compares two **trees**, not a commit range — so when main had advanced past a PR's own base, every foreign post-base `agents/` change appeared in the diff as a deletion against head and was misattributed to that PR as an absent `SYNC:`-line demand. Measured instance: #1751's scope red for exactly this reason.

The gate now resolves `git merge-base <base> <head>` first and diffs `merge-base..head` (the #1527 pattern `check_pr_closing` already uses), so only the agents/ edits THIS PR actually introduces demand their live re-sync report. `is_bot_pr` was already safe (`git log {base}..{head}` is a true reachability range, excluding foreign main commits), so only the tree-diff path needed the anchor. Genuine same-PR agents/ changes still require their `SYNC:` line — the gate is not weakened.

Prove-the-guard: two regression tests in `tests/test_pr_hygiene_sync_line.py` build a real repo where main advances with a foreign agents/ change after the PR's base. On the old code both fail (`llgenie-foreign` misattributed); on the fixed code the foreign profile is not named, a genuine same-PR profile edit still reds without its `SYNC:` line, and all 13 sync-line tests pass.
