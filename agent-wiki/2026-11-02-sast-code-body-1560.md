# LLGenie Security Officer: body_for branches remediation for component:code SAST findings

Implements issue #1560 (ready-for-review PR — CI lands it). `scripts/security_issues.py::body_for`
rendered the SAME dependency-flavoured template for every finding, `component:code` included, so a
semgrep finding filed an issue that told the reader to "pin `tools/app.py:5` ... in the compiled
`requirements*.txt`" — a file the path cannot be pinned in. The wrong remediation is how a SAST finding
gets "closed" without the code being fixed.

## What changed (measured on this worktree)

- `scripts/security_issues.py::body_for` now branches on `finding.component == "component:code"` (the
  same classification `component_of` already computes — `source not in ("trivy","grype")`, i.e. a SAST
  or committed-secret finding). A `component:code` finding renders the *edit-the-code* present-tense
  narrative — "Edit the matched region in `tools/app.py:5` ... fix the code, never try to pin a
  dependency" — and never names the generated `requirements*.txt` pin path. Everything else keeps the
  existing *bump-the-pin* template unchanged.
- Idempotency is presentation-invariant: the marker (the idempotency key), advisory id, severity,
  component and run link live in `## Technical` (now the shared `_technical()` helper) and are byte-for-byte
  identical for both body shapes — only the `## How we fix it` / `## Acceptance criteria` /
  `## Not covered` prose differs.
- Tests: `tests/test_security_issues.py` (+2): an SAST body carries the code-remediation wording and
  NOT the `requirements*.txt` wording, and the marker round-trips through `MARKER_RE`; a CVE body still
  carries the pin wording. The CVE-path assertions (sections order, technical last) already existed and
  still pass.

## Verification (measured, not asserted)

- SAST-only reports dir (only `semgrep.json`) through the #1557 reader chain: `security_scan.py
  verdict --event schedule` prints `FAIL ... 1 finding(s)` naming the SAST finding, and
  `security_issues.py plan` lists a `component:code severity:high` issue whose rendered `body_for`
  carries "Edit the matched region in `tools/app.py:5`" and NOT `requirements*.txt`.
- Gates: `make check-security-scan` RC=0 (still refuses `push`/`pull_request` — the scan stays its own
  daily pipeline, #738); `make check-security-issues` RC=0; `make check-security-bumps` RC=0;
  `make check-issue-bodies` RC=0.
- Security pytest suite (`test_security_scan`, `test_security_issues`, `test_security_bot`,
  `test_issue_body`, `test_check_issue_body`): **72 passed**. `make openspec-validate NAME=sast-code-body`
  green.

This change never weakens the security gate: no `push`/`pull_request` trigger is added, no
allowlist/severity set is widened, and the marker/severity mapping itself is untouched.
