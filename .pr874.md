## What this changes

The required review no longer needs an owner action, and no longer depends on a secret that can be missing.

| | before | after |
|---|---|---|
| **review** | `secrets.APPROVER_TOKEN` — empty in the base repo when unset, silently killing the path | **`${{ github.token }}`** — always present |
| **merge** | `secrets.BUMP_TOKEN` | unchanged: a merge made with the job token starts no workflows, and the post-merge run on `main` must happen |

The approval is legal because the approver differs from the **author**: every PR here is opened by `andyholst` (the bots push with the owner PAT), while the workflow's token is `github-actions[bot]` — two accounts.

## The guard had to be made explicit

An installation token **cannot answer `GET /user`** (`403 Resource not accessible by integration`), so the identity is not askable — it is deterministic:

```python
WORKFLOW_BOT = "github-actions[bot]"

def token_login(gh, token=""):
    try:    return _gh(gh, ["api", "user", "--jq", ".login"], token=token).strip()
    except SystemExit:  return ""        # a token that cannot answer is named, not an abort

me = token_login(gh, token=approver_token) or WORKFLOW_BOT
```

So the rule is **"approver != author"**, not "use token X": a PR that `github-actions[bot]` opened is refused by it, and the run falls back to the admin bypass instead of firing a self-approval GitHub would reject with `422`.

## Both constraints are now in the workflow header

- a `pull_request` run **from a fork gets a read-only token** and could neither approve nor merge — the other reason this flow is a `workflow_run` workflow in the base repo;
- `github-actions[bot]` cannot approve its own PR, which is why the guard tests identity rather than trusting a token name.

## Verification

```

                                                       the negative control — a bot-authored PR is not)
check-workflows check-docs check-wiring check-dispatch-forms lint → PASS
```

**Negative controls, three of them:**
1. restoring `secrets.APPROVER_TOKEN` in the workflow → `test_the_merge_uses_the_owner_pat_and_a_make_target` **fails**;
2. removing the 403 tolerance in `token_login()` → the installation-token case aborts instead of approving;
3. a PR authored by `github-actions[bot]` with a bot merge token → **no `pr review` call at all**, admin bypass instead.

One test was strengthened rather than deleted: `test_the_merge_uses_the_owner_pat_and_a_make_target` previously asserted `github.token` appears **nowhere** in the workflow — true when only the merge used a token, wrong now. It asserts the two identities separately: the merge keeps `BUMP_TOKEN`, no step merges with `github.token`, and the review is exactly `${{ github.token }}` with `secrets.APPROVER_TOKEN` gone.
