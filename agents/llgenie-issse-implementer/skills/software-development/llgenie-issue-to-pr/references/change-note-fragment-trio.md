# The change → note → fragment trio (`check-docs` "change->note" red)

## When this gate fires

Any PR whose diff touches a path under `agents/<lane>/skills/**` (a NOTE_SURFACE, matched by
`^agents/[^/]+/skills/` in `scripts/check_docs.py`) owes **three artifacts plus a re-render**:

1. the change itself (the folded/edited file),
2. `agent-wiki/<YYYY-MM-DD>-<stem>.md` — a note that references an issue or PR number,
3. `docs/changes.d/<YYYY-MM-DD>-<stem>.md` — a one-row fragment that indexes that note,
4. `CHANGES.md` regenerated with `make changes-index` (a new fragment means a new row).

The failure text is exactly: `change->note: this branch changes <path> but adds no
agent-wiki/<stem>.md note` (also surfaces as red `scope` and `unit` legs on the PR).

## The gate is NOT limited to `agents/**` — a behavioural `scripts/` change owes the trio too

Do not assume a change under `scripts/` (a gate, a checker, a bot script) is exempt because it
touches no NOTE_SURFACE. A change that alters the BEHAVIOUR of a gate or script reds
`change->note` exactly like a skills edit and owes the same note + fragment + CHANGES row. The
only way to know is to run `make check-docs` at the committed head — a `scripts/` change that
changes what a gate rejects is a behavioural change and is trapped by the same gate. Adding the
trio is cheap; discovering the red after the push is not.

## Pitfall: the dispatch's "index-less, no note" premise can be wrong

A live→tree fold issue often declares itself a pure file swap that needs no note. That premise
is false for any path under `agents/<lane>/skills/`. Do not trust the issue's scope sentence —
run `make check-docs` yourself at the head. If `change->note` fires, the trio is owed and the
issue premise is the defect, not the gate. Carry the trio; the fast gates go green.

## Pitfall: the `changes.d` fragment must be ONE row and NOTHING else

`make changes-index` parses each fragment with a strict row grammar. A prose paragraph, a
heading, or an explanation in the fragment fails the index with `ERROR:
docs/changes.d/<stem>.md: is not a row. This file must contain ONE row and nothing else (no
prose, no heading)` and `CHANGES.md not written` (rc 2). The file is one line:

```
| 2026-01-01 | what changed, in one sentence | [2026-01-01-<stem>.md](agent-wiki/2026-01-01-<stem>.md) | #<n> |
```

The note column must point at `agent-wiki/<same stem>.md` (this fragment's own name) and the
issue column must be a real `#<n>`. Long explanations belong in the `agent-wiki` note, never
in the fragment.

**The commonest way to fail this parser is to drop the LAST column.** A fragment written as
`| date | summary | [note](agent-wiki/<stem>.md) |` (three cells, no `| #<n> |`) looks like a
valid markdown row but is not one to the gate, which reports the same `is not a row … must
contain ONE row` text and never names the missing cell. Diagnose before rewriting the prose:
count the cells against the four-column shape — five `|` characters including both ends, and a
trailing `#<n>` cell. If the count is right, then look for prose/heading contamination.

After fixing, re-run `make changes-index` and `git commit --amend` to fold in
both the corrected fragment and the regenerated `CHANGES.md` — then confirm the commit really
carries everything (`git show --name-only HEAD`), because the trio commit silently lands with
only the note + code files when the index step redded before its `git add`.

## Pitfall: the gate reads COMMITTED diffs, not the working tree

`check_docs.py` builds its changed-path list from `git diff --name-only <base>...HEAD` — i.e.
committed state only. A note+fragment sitting untracked or uncommitted will NOT clear the red,
and re-running `make check-docs` will keep reporting the same "adds no note" even though the
file is on disk. This is the trap that makes a correct fix look broken. Stage and **commit**
the trio, then re-run the gate.

## Verify
- `make check-docs` rc 0 at the committed head (it also runs the architecture census and the
  changes-index consistency check, so one rc 0 covers all three).
- **`make check-docs` alone does NOT prove the `scope` leg green — run `make lint` too.** `scope`
  bundles `check-docs` AND the linefeed/editorconfig lint, and every note/fragment must END WITH A
  NEWLINE. A trio generated by the file-writing tool (not by a heredoc) lands with no trailing `\n`,
  so `check-docs` passes locally, the push goes out, and CI reds `scope` on `make ci-lint` with the
  file simply named as a lint finding. Check every file before pushing:
  `for f in agent-wiki/<stem>.md docs/changes.d/<stem>.md; do [ -n "$(tail -c1 "$f")" ] && echo
  "missing newline: $f"; done` (or `tail -c1 "$f" | od -An -c` must read `\n`), and append `\n`
  where it is missing. Write the trailing newline into the content itself for generated batches.
- `make changes-index` rc 0; commit `CHANGES.md` whenever the fragment row is new.
- Never regenerate `CHANGES.md` on an old base and then rebase: the rebase conflicts on the shared
  append. Rebase FIRST, then re-render the index from the fragments at the new base.
- **A rebase also invalidates every derived artifact that embeds the base sha, not just the index.** The PR body's `AGENTS:` and `BASE:` lines (`make bot-preflight`) both carry the base commit id, so after `git rebase origin/main` they name a stale base and the base-line gate reds even though the lines are present. Sequence: rebase → `make bot-preflight` at the new base to regenerate both lines → `gh pr edit <n> --body-file <file>` with them → re-run `make check-docs`/`make ci-lint` at the rebased head before pushing. Regenerate AFTER the rebase, never before; a body still citing the pre-rebase sha is the same class of staleness as a `CHANGES.md` rendered on the old base.
- If the folded file must stay byte-identical to the live profile, re-hash *after* committing:
  `git rev-parse HEAD:<path>` vs `git hash-object <live-path>` must match.
- Then push and let the PR's `scope`/`unit` legs re-verify — local gate and CI run the same
  script, so a local rc 0 is the honest pre-push proof.

## Related: registry store re-syncs

A PR that re-vendors the upstream registry store (`data/**`, `scripts/sync_registry.py`) ships
committed data that other generators read, so it owes this same trio plus the rendered
`CHANGES.md` row — and every derived artifact must be rendered LAST, after the store is final.
Procedure, merge-key rules and additive-guard residual handling: `registry-store-sync.md`.

## Precedent rule

A later drift fold of a reference that an earlier fold already noted still needs its own
**dated** note + fragment. The index dedupes by note stem, not by the referenced file, so a
second fold cannot reuse the first fold's note.
