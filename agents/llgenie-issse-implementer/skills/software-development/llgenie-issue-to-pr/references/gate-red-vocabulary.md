# Gate-red vocabulary: `mergeable` vs `mergeable_state`, and the two most common PR gate reds

## `mergeable` (file-conflict) vs `mergeable_state` (gate matrix) — never conflate
- `mergeable=true` means *only* "no file conflict". A PR can report `mergeable=true` **and** `mergeable_state=blocked` simultaneously.
- `mergeable_state` is the aggregate gate verdict: `blocked` = at least one required check is not green (a red **or** still in_progress/queued); `clean` = all green and passable; `dirty`/`conflicting` = a real merge conflict.
- So "mergeable=true" is NOT a green PR. The green signal is `mergeable_state=clean` (or all check-runs `completed/success` on the head). Don't answer "is the PR green?" with `mergeable=true`.
- `mergeable`/`mergeStateStatus` can both read **`UNKNOWN`** immediately after a push or right as required checks finish — GitHub is still recounting merge state. That is a transient third state, not `blocked`/`dirty` and not evidence the PR is unmergeable. Re-read once a moment later (`gh pr view <n> --json mergeable,mergeStateStatus`) before reporting; it resolves to `MERGEABLE`/`clean` (and to `MERGED` once the owner merges) on the recount. Never read `UNKNOWN` as a red or reopen work over it.

## #845 stale-base red — `BASE:` body text does NOT move the tree
- The guard compares the head's **true merge-base** against the base, not the `BASE:` string in the body. Writing `BASE: <sha>` in the body never changes the tree.
- **Measure the *actual* ancestry**, never trust the body:
  `git fetch origin main` then `git merge-base origin/main <head>`; a `diverged` compare (ahead N / behind M) means the branch forked earlier than the body claims.
- **`origin/main` is the LOCAL tracking ref — a stale shadow until you fetch.** `git show origin/main:<path>`, `git merge-base origin/main`, `git ls-tree origin/main` and `git log origin/main` all read that local ref, NOT the remote. After a merge lands the local `origin/main` still points at the pre-merge base, so an "is my file on main?" check reads the OLD tree and reports the file missing (cost real time this session: 0/2 files, then 4/4 once fetched). Always `git fetch origin '+refs/heads/main:refs/remotes/origin/main'` immediately before any ancestry/content check, print the sha it moved to (`git rev-parse origin/main`), and verify against that — or use `git ls-remote origin refs/heads/main` for the authoritative tip. Confirm the merge commit is an ancestor: `git merge-base --is-ancestor <squash> origin/main`.
- Fix = rebase onto live `origin/main`: `git rebase origin/main` (after `git fetch origin refs/heads/main:refs/remotes/origin/main --no-tags`), so `merge-base == base`. Check `git merge-tree --write-tree origin/main HEAD` first for a clean non-conflict; after rebase the merge-base must equal the base sha.

## #792 check-pr-agents-line red — never hand-write AGENTS:/BASE:
- The guard validates the **literal `make bot-preflight` output**: `<sha> <bytes>b <lines>l` for `AGENTS:` and `<sha> (== origin/main at open)` for `BASE:`.
- Run `make bot-preflight` on the branch and copy its exact two lines into the PR body. A hand-composed `AGENTS: <sha> <sha> census-ok` (or any non-preflight shape) reds the guard.
- The full sha and the `XXXb`/`YYYl` suffixes are mandatory; the preflight output is the single source of truth for the format.
- **A body edit + re-run creates a NEW guard job id.** After you add the `AGENTS:`/`BASE:` lines and re-run the CI, quote the CURRENT guard job's step verdict — the newer job id, not the original failed attempt. A reviewer/planner who cites the pre-fix job id (e.g. the original 05:59 run) is reading a stale anchor; before acting, re-fetch the live run's job list (`gh api .../actions/runs/<run>/jobs`) and read the latest guard job's `make check-pr-agents-line` step. It is green when the live PR body + re-run landed.

## After the fix: fresh CI is required, and in_progress is not red
- The gate matrix re-evaluates on each push; `mergeable_state=blocked` while required checks are `in_progress`/`queued` is normal, NOT a defect. Wait for all to reach `completed`. Then confirm each conclusion == `success` and `ci-verdict` reads green before calling the PR green.
- Rebase + preflight + amend + push with **plain** `--force-with-lease`; both fork and origin must show the new head (`git ls-remote fork <b>`, `git ls-remote origin <b>`).
- Use the plain `--force-with-lease` form; the explicit `--force-with-lease=<ref>:<expect>` form can reject in this repo even with the correct expected sha — fall back to the plain form rather than debugging the lease.
- Amending an ALREADY-pushed commit (same files, changed tree) can leave `refs/pull/<n>/head` stuck at the previous sha while the fork branch itself advances. Fresh shas reconcile reliably; an amend may not. If the PR head lags after an amend, poll `gh pr view <n> --json headRefOid` a few times, and if it stays stuck add a fresh commit on top instead of re-amending, then re-check. Cross-check the fork with `git ls-remote fork <b>`.

## check-pr-acceptance red on a fix PR — the verdict-gated self-red, NOT your deliverable
- `scripts/check_pr_acceptance.py` (Makefile `check-pr-acceptance`, run inside both `guard` and `scope`) reads the **LIVE issue the PR closes** and reds `claim-unchecked` while that issue's own `## Acceptance criteria` boxes are still `- [ ]`. On a fix PR that closes the issue it fixes, those boxes are unticked by definition until a **reviewer verdict** lands — so this red is BY DESIGN and is not an incomplete implementer step.
- The tick happens ONLY through the verdict-gated write-back seam (the reviewer's COMMENTED verdict writes the boxes back). The implementer must NOT self-tick the issue, must NOT edit the issue body to green it — that is fabrication and defeats the gate. A `## Not covered` deflection is legitimate ONLY in the exact `#1792` shape with a REAL linked tracker and only when the criterion genuinely cannot be produced (see "The legitimate `## Not covered` exemption" below); a bare/paraphrased bullet with no `#<n>` is a fake deflection that changes nothing.
- A PR body that ticks a criterion the issue still leaves unchecked instead trips `claim-exceeds` — worse than the self-red. Keep the PR body's acceptance boxes unticked, mirroring the issue, awaiting the verdict.
- The `scope` failure and the `ci-verdict` / decision-artifact read are DOWNSTREAM of this one step: `scope` never publishes its artifact because `check-pr-acceptance` failed first, so `ci-verdict` reads a missing artifact, and `guard` runs the same `make check-pr-acceptance`. Confirm by reading the `scope` job's step list — its ONLY failed step must be `make check-pr-acceptance`; every implementation step (`ci-lint`, `check-docs`) should show `success`.
- **Count GATES, not red check NAMES.** A single `check-pr-acceptance` failure surfaces as three separately-named red checks — `guard`, `scope` and `ci-verdict` — because `guard` and `scope` each invoke `make check-pr-acceptance` and `ci-verdict` reads the artifact `scope` never published. Before reporting "3 red checks", resolve each name to its failing STEP; if all three bottom out in the same `make check-pr-acceptance` step, report ONE gate with one root cause, never three defects. Two or more *distinct* failing steps is the signal of a real defect.
- **The self-red cannot clear until a witness run exists at the NEW head.** The acceptance boxes are written back only by a reviewer verdict backed by a genuine `COMPLETED-SUCCESS` run of the thing the issue is about. If the fix moved the head, the verification cell pinned at an older sha does not count as the witness — an `engine-build` run must exist at the *current* head. Check for one directly: `gh api "/repos/<o>/<r>/actions/runs?head_sha=<head>" --jq '.workflow_runs[]|"\(.id) \(.status) \(.name)"'`; if no producer run exists at the new head yet, the red is not a defect and not yours to force — the producer is dispatched by its own trigger (whose `paths` filter means a head that touches no engine `params/**` never starts one), so report "blocked on the witness run", never re-dispatch by hand and never self-tick.
- `openspec-image` / `ci-openspec` appearing after the failing step are **skipped (sequenced), not failed** — never report OpenSpec as red when the step was skipped. Verify OpenSpec locally instead: `make ci-openspec` rc=0 (and `openspec-validate` rc=0).
- Verify the finding is the self-red, not an implementation defect: count the reported findings (`gh run view <id> --log-failed | grep -c 'acceptance item'`) and compare to the issue's own unchecked boxes (`gh issue view <n> --json body --jq .body | grep -cE '^- \[ \]'`). Equal counts, each `acceptance item k` quoting a criterion from THAT issue's `## Acceptance criteria` — including criteria owned by peer lanes — proves the red judges the whole issue's definition of done, not your diff. Also confirm the run's ONLY failed step is `make check-pr-acceptance` (`check-git-identity`/`holds` show `success`); any second failed step is a real defect, not the self-red.
- A bot PR that closes a rollout/tracker issue whose criteria are proven by OTHER lanes' merged PRs still reds: the boxes stay `- [ ]` until the reviewer's verdict writes them back (they are ticked once, when the issue's own verdict lands), so the merged peer PRs do not pre-tick them. Do not pre-tick on their behalf.
- Correct handling: prove every implementation gate green locally AND on the wire (lint, check-docs, openspec, body gates, holds), then report the ONE designed self-red honestly and hand the PR to the reviewer lane for the verdict. State task-relative verification (the new tests pass, full `make test-unit` count + `EXIT=0`) so "not done" is refuted by evidence — never claim wire-green and never fabricate a tick.

## The legitimate `## Not covered` exemption — exact shape, and never preempt a live evidence attempt
- When a PR still `closes` an issue whose criterion is unchecked, the gate's ONLY legitimate clearance (short of the reviewer's verdict write-back) is the declared-out-of-scope exemption (#1792). It is read from the **PR body's** `## Not covered` section (NOT the issue's), so a deflection must land in the PR body — an issue-side bullet does not clear the gate while the PR still closes the issue.
- The exact shape `_declared_out_of_scope` requires — get one part wrong and it is a fake deflection that silently does nothing:
  - a line in `## Not covered` matching `(?im)^-.*\s*#\d+\s*$` — it must START with `-` and END with the `#<n>` reference (nothing after the number, trailing whitespace ok); **the bullet must be ONE physical line** — a wrapped/multi-line bullet with an internal newline breaks the `^…$` anchors and matches NOTHING (the exemption silently no-ops);
  - the criterion's first ~3 normalised words (`[a-z0-9 ]` then substring match of the leading words) must appear somewhere in that section — quote the criterion's leading words, not a paraphrase;
  - a bare "out of scope" with no `#<n>`, or one that drops the leading words, is a no-op — the count of `claim-unchecked` findings is unchanged.
- Name a REAL tracker that owns the not-covered work in the linked `#<n>`. An invented issue number is a fabricated deflection and defeats the gate's purpose.
- **Never preempt a live evidence attempt with an out-of-scope declaration.** When the criterion is provable by an in-flight run you dispatched (an engine-build sweep, a witness cell, a pinned-arch run), hold that evidence path and bind the run id when it concludes — fall to `## Not covered` ONLY when the criterion genuinely cannot be produced on the available runners (known upstream/infra blockers). Declaring a criterion out of scope while the exact run that would prove it is still `queued`/`in_progress` abandons the primary proof and can preempt a passing result; report the run id and hold the head until it lands.
- An ownership-correction dispatch that routes the `check-pr-acceptance` red to your lane with "prove it OR declare out of scope" is authorising the exemption — but the choice is a measurement decision, not a way to dodge a live attempt: hold the evidence path first, declare out of scope only on a measured cannot-produce.
- **Verify the exemption's SHAPE locally before spending a CI round-trip.** The gate is a plain function: `from scripts.check_pr_acceptance import acceptance_verdict; acceptance_verdict(<issue-body>, <pr-body>)` returns the finding list (each has `key` + `evidence`, the index parsed from `evidence`). Run `scripts/check_pr_acceptance_probe.py <issue-body-file> <pr-body-file>` inside `llgenie/test:latest` (repo root on `sys.path`) — it prints the exact `violating_items` set. Correct shape = the exempted criterion's item index is ABSENT from that set (e.g. reds become `[1,3]` after exempting item 2); a fake/paraphrased deflection leaves it in. This proves the bullet without waiting for `guard`+`scope` to publish an artifact.
- **A `## Not covered` edit is PR-BODY state, so it SURVIVES a rebase/force-push** (unlike a commit). Re-verifying the exemption at a NEW head after a peer rebase is a body read (`gh pr view <n> --json body`, grep the `## Not covered` bullet + the `#<n>`) plus one FRESH run at that head — never a re-edit. Confirm the exempted item still drops out on the new head's `guard`/`scope` jobs (`check-pr-acceptance` violating set unchanged, exempted index still absent).

## `gh api` body writes — PATCH/POST need the JSON on stdin, not `--input -` with nothing piped
- A `gh api repos/<o>/<r>/<path> --method PATCH` (or POST) that takes a body needs the JSON object piped on **stdin**: `subprocess.run([... "--method","PATCH"], input=json.dumps(payload), text=True)`. Omitting the `input=` (or running the command with no stdin) answers HTTP 400 `Body should be a JSON object` — that is a malformed request, not a rejected change.
- The repo lives in the URL for `gh api` (`repos/<o>/<r>/…`), so a helper must not also pass a `--repo` flag with a URL-style path — that misorders the args. Put owner/repo in the path only.
- `gh` is on PATH in the terminal tool but NOT in the execute_code kernel — run body-edit scripts as `python3 /tmp/x.py` from the terminal, or the gh call dies with a not-found.

## check-proc-gate red — `# proc-allow:` must share the PHYSICAL line with the call
- `scripts/check_proc_gate.py` (Makefile `check-proc-gate`) flags every `subprocess.run(` in `scripts/` that lacks a `# proc-allow: <reason>` marker **on the same physical line**.
- A call split across lines with the comment on a continuation line is NOT recognised — the gate inspects each physical line containing `subprocess.run(` for the marker. Put the call on one line with the trailing comment: `subprocess.run(cmd, ...)  # proc-allow: <reason>`. Verify locally with `python3 scripts/check_proc_gate.py check` (must exit 0) before pushing, or `linux / unit` reds on the proc gate rather than on pytest.

## Post-merge verification — a merged branch is behind advanced main BY DESIGN
- After a PR merges, `main` advances past the base the branch was cut from. Running `make check-pr-base` on that now-stale branch correctly FAILs ("not cut from `origin/main`", naming the branch's own commits as foreign) — that is the gate working as intended, NOT a defect, and NOT unfinished work. A merged branch is read-only forever; never rebase it or reopen the issue to "fix" that red.
- Verify the merged content instead: fetch live main (explicit refspec), then confirm the files/key lines exist on the fetched `origin/main` (`git ls-tree origin/main -- <paths>`, `git show origin/main:<path> | grep …`). Prove the gate's POSITIVE path with a throwaway local branch off the live tip (`git checkout -b verify-<n> origin/main && make check-pr-base`, expect rc=0), then `git branch -D verify-<n>` — never push that branch.

## A `verdict` red on your merge sha may be judging SOMEONE ELSE's head
- The verdict workflow evaluates the CI **run** it names, not the sha it is triggered on. A
  `verdict` job that failed in the post-merge run at your commit can be reporting on
  `run <other-id>` at a different head — another lane's PR. Read the job log for the two ids
  (`evaluated run`, `head`) before attributing the red to your merge, and name both in the report.
- The failing job's log endpoint often returns empty for guard/verdict jobs while the run is still
  `in_progress`. That is "error line not yet retrievable", never a cause: wait for completion, then
  re-fetch. Do not publish a cause inferred from the step name.
- Your merged commit is green only when its OWN post-merge `push` run (the run whose `head_sha` ==
  your merge sha) is `completed/success` with `linux / unit` success; a verdict run firing before
  that run finishes reads a null/in-flight attempt and is not evidence either way.

## CLI vs REST field names — `mergeStateStatus` ≠ `mergeableState`
- The REST field is `mergeable_state` (via `gh api repos/<o>/<r>/pulls/<n> --jq .mergeable_state`).
- `gh pr view --json` does NOT expose `mergeableState` — it reds `Unknown JSON field: "mergeableState"`. The CLI's camelCase name is **`mergeStateStatus`**; the boolean is **`mergeable`**. Measure with `gh pr view <n> --json mergeable,mergeStateStatus,state,headRefOid`.
a `gh api … --jq '{…}'` that returns every field `null` (e.g. `headRefOid`, `baseRefName` all null while `state` is populated) is a transient partial read, not an empty PR — re-run the call once before concluding anything; `gh pr view --json` is the fallback that answers in one shot.

## Verifying a CI-only change (engine-build Docker cells) — dispatch `push=false`, read the actual cell log, hold the head

Some changes are only provable by a real CI run — an engine-build Docker cell (`vllm`/`cuda`/`rocm`), a cold HIP/CUDA compile, a timeout budget. You cannot reproduce those locally; the proof is the cell's own log, not a `conclusion`.
- Dispatch the workflow directly in the SAFE no-publish shape: `gh workflow run engine-build.yml -f engine=vllm -f arch=rocm -f push=false`. `push=false` is build-and-verify — it builds and runs the install step but publishes NO artifact and merges nothing, so an implementer lane may dispatch it. A `push=true` run publishes; that is the release path.
- Read the failing/passing step's OWN log, filtered to the cell: `gh run view <id> --log | grep '<job-name>'`. A cell's log is empty until the compile flushes output; mid-build that is "not yet retrievable", NOT a cause — wait for output, never infer a cause from the step name.
- Do NOT push a further commit that MOVES the PR head while a verification run at that head is `in_progress`: the run proves the sha it started on, and moving the head makes its eventual verdict describe a tree the branch no longer is. Wrap remaining local work (a fold, a body edit) but hold the PUSH until the run concludes, then report its run id + the exact head sha it measured. Verify locally first, monitor the cell log, and never move the head out from under a live verification run.
- **A queued `0`-job engine-build run that gets CANCELLED the same second a newer push lands is the concurrency-supersede guard working, NOT runner starvation / dispatch gating / a trigger bug.** `engine-build-pr-trigger` cancels stale queued runs on each push (a per-branch concurrency key), so a run that shows `jobs.total_count=0` then `conclusion=cancelled` at the exact timestamp of the subsequent push is the guard superseding the stale head, not a stuck runner. Diagnose by correlating the run's `updated_at` with `gh pr view --json headRefOid` push times — same second = supersede. Never `re-dispatch by hand` over it and never report it as runner starvation to the pipeline lane; the fix is a run at a head that stops moving (a pushed/merged head), not a queue fix.
- **A `pull_request`-event run that the concurrency guard would cancel can never prove `push=true` (the release/merge path) anyway.** Witness criteria that need the actual push-time behavior must be captured at a stable/merged head where the concurrency key has no later push to supersede; a run cancelled mid-flight binds nothing.

## AC1/AC2 "provable in live flight" → make it PRE-MERGE provable with a static workflow test (remedy b)
- An acceptance criterion stated as "observed on the next real pin-bump rebase" is a witness-red: it can only clear at a LIVE rebase, whose run may wait on a frozen/stalled runner for an unbounded time. The reviewer's remedy (b) unblocks it without a live flight: a unit test that reads the LIVE workflow YAML and anchors the concurrency/trigger contract as static text.
- Pattern (tests/test_engine_build_pr_trigger.py, #1831/#1833): `yaml.safe_load(repo/.github/workflows/<wf>.yml)`; assert `concurrency.group` interpolates BOTH `${{ github.event.pull_request.number }}` AND `${{ github.event.pull_request.head.sha }}`; `cancel-in-progress` is `false`; the trigger's `pull_request.types` include `synchronize` (a rebase) and `opened`/`reopened`; add a group-distinctness assert (same PR number + two head shas → two different groups) so the "new head must not queue behind the old head" property is provable, not just parsed.
- The `on:` key needs the YAML-1.1 loader-tolerant read (`wf.get("on") or wf.get(True)`) since the bare key parses as boolean True under some loaders (same convention as tests/test_bot_pipeline_isolation.py).
- **Prove the anchoring test anchors — run it against the PRE-FIX artifact too, and require it to FAIL.** A test that only passes at the fixed head may be asserting nothing. Reconstruct the old workflow (`git show <pre-fix>:.github/workflows/<wf>.yml` into a throwaway temp tree with the test copied beside it) and run it in the container; expect a NONZERO rc with the specific assertions that guard the change red (e.g. the number-only group reds the head-sha assertion). Pass-at-fixed + fail-at-old is the pair that proves the test binds the defect; pass-at-fixed alone does not.
- Share the evidence with the REVIEWER lane (they re-write-back the boxes, #1644), not just the planner: the test makes the criterion pre-merge provable as a property of the file, opening the re-write-back without waiting on a rebase witness.

## A test-only PR must NOT `closes` an issue whose ACs demand a LIVE run (the #1834 scope trap)
- An issue whose acceptance criteria are phrased as "completes SUCCESS in a real workflow run" / "a CI embryo proves a cell reaches post-build" / "evidence posted on #NNN" can only be closed by EVIDENCE OF A REAL RUN — never by a test-only regression PR, however good the tests. A reviewer will honestly refuse, the PR stalls, and the unresolved close becomes a #745-class red.
- When an implementer's PR for such an issue turns out test-only/hardening (plus openspec/wiki/docs, zero product/params/workflow), DO NOT let the body keep `closes #<n>`. Reconcile: remove the standalone `closes #<n>` line from the PR body (leave AGENTS:/BASE: untouched — they are base-derived), and ADD a `## Not covered` bullet on the ISSUE stating the ACs are proven by the already-authorized verify run (ref + run id + the planner-authorization comment id + the AC it tracks to), per the ADD-only #1792 rule. Routes: this is a decisions-the-planner-owns choice (path (A) vs (B) re-scope through analyst/PM); a dispatch message from the planner naming both paths and saying "your call" authorizes choosing (A) when it matches the measured file set.
- Read the WIRE before agreeing to a head in a reconcile: the planner may quote an earlier commit while the live PR head advanced — both may carry the same commit message yet neither is the other's ancestor. Use `gh api pulls/<n>` `.head.sha` and `pulls/<n>/files` next to every body sign-off; never act on a sha quoted in a chat message.
- **Bookend on BOTH artifacts, not just the PR.** A scope reconcile touches two things: the PR body (loses its `closes` line) and the ISSUE body (gains the evidence-path bullet). Both need a finish comment: the PR comment records what changed on the PR, and the ISSUE must get its own comment recording why its closes-claim was withdrawn and where its AC evidence now lives. A reconcile bookended only on the PR leaves the issue's next reader (a reviewer, the owner) believing the issue is still closed by that PR — the exact ambiguity the reconcile exists to remove.
- **Verification on a scope-reconcile dispatch is API-body reads, not a tree mutation — a write-only guard will still fire.** The reconcile's deliverable is live PR/issue body state (`pulls/<n>` `.body`, `issues/<n>` `.body` + box count); there is no code change to make. Pair every such dispatch with the one real mutation it does own (the body PATCH and/or the bookend comment) and read it straight back in the same script, so a mutation-required progress check sees a concrete verified change rather than a comment/read-only turn.
