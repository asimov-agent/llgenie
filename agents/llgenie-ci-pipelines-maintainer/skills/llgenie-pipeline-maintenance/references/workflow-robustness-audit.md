# Workflow-robustness audit (the five classes, measured 2026-11-02 at a5aff03b)

When the planner assigns a workflow-robustness sweep, measure these five classes and file ONE refined six-section issue per real gap (they route through the normal queue; I never implement a finding myself — #1088).

1. **cancel-in-progress coverage** — which workflow can race (cron + manual* + a second run) without `concurrency`? CAVEAT: a `workflow_call` reusable (`pipeline.yml`) has NO independent run — it inherits the caller's concurrency, so its lack is NOT a gap; only standalone-triggered workflows need it (30/31 here had it; the 1 exception was the reusable).
2. **stale-head races** — which reactor reads the triggering run's head but acts on a DIFFERENT (moved) ref? Verified guards to pattern-match as clean: `auto_merge.py` refuses `headRefOid != run sha` (the newer run decides); `ci-verdict.yml` posts a `neutral` check on a superseded head; `fix-bot` guards the same. A guard is clean only when the moved-head case exits non-breaking (0 / neutral), never a red over a head that already moved.
3. **silently-never-fires / every-red-routed** — run `check_workflow_run_coverage()` (scripts/check_workflows.py). 0 violations = clean. Non-rostered workflows must each carry a dated, reasoned entry in `tests/fixtures/workflow-run-exemptions.json` (security-scan, run-failure-reactor, ci-hf-live, all-pipelines did). Derive the roster from the workflow files, never a hand-kept list; GitHub matches `workflow_run.workflows` verbatim, no wildcard.
4. **green-when-doing-nothing / empty-denominator** — find a script that can exit 0 while it did nothing or failed to SEE its input. Recurring trap: `_paged_json`-style helpers that collapse a `gh rc!=0`/empty body into `[]`, and a caller that discards the rc (`stale_branch_cleanup.py:41-45,120` — filed #1514). The repo's own bar is `rebase_bot_sweep.py`: "an unreadable answer must never be read as 'nothing in flight, nothing red'" (#453). Also check debounce skips: a debounce is SAFE only if an API failure forces `skip=false` (runs), never hides behind a skip.
   - **Truncation-blind pagination.** A list call that reads `per_page=N` with NO `total_count` check and NO pagination sees only the newest page. Signal: **asymmetry inside one module** — when a sibling helper explicitly refuses a truncated listing (`jobs_of()` guards `total_count`), a bare `per_page=50` in another helper (a branch listing, a superseding-run lookup) is the same defect left unguarded. On a hot branch (main >2000 runs) the item beyond the newest page is missed, so a superseded head posts a false-red verdict instead of the neutral it owes. Grep every `per_page=` in the audited file for this pairing.

5. **swallowed failures — `continue-on-error: true` with no consumer** — a step whose failure is swallowed is a control that does not exist unless a LATER step reads its state. For every `continue-on-error: true`, grep the same workflow for `steps.<id>.outcome` / `steps.<id>.outputs`; if nothing reads it, the step is only acceptable if it is intentional-degrade AND the next step independently re-derives the decision, so a swallowed failure degrades to a correct skip, never a false green. Three clean shapes seen here: the step self-records (`set +e` + `::warning::` + deliberate continue), a later step consumes the outcome (a comment/red carrying `OUTCOME: ${{ steps.<id>.outcome }}`), or a downstream `scripts/*.py` re-queries the API instead of trusting the local checkout (so a failed `gh pr checkout` still lands on a correct `action=skip`). A `continue-on-error` step that writes `$GITHUB_OUTPUT` nobody reads, with NO independent re-derivation downstream, is a swallowed red — file it. Trace the consumer through the whole file, not just the next step: the reader may be the final outcome-commenting step, or absent entirely.

6. **load-time rejections — the run has 0 jobs, the run's NAME is the workflow file path, and every rollup reads clean.** A workflow GitHub refuses to *parse* produces no job rows at all, so `gh pr checks` has no red row and an aggregate says `fail=0`. Two causes measured here, both worth a class of their own:
   - **A reusable-workflow secret may not be named `GITHUB_TOKEN`.** GitHub rejects at load with `Invalid workflow file: .github/workflows/<f>.yml#L<n> error parsing called workflow ... : secret name GITHUB_TOKEN within workflow_call can not be used since it would collide with system reserved name`. The token is legal; only a `workflow_call` **declaration** by that name is not. Fix that compiles: the caller passes it under a plain alias (`RUN_TOKEN: ${{ secrets.GITHUB_TOKEN }}`), the callee declares `RUN_TOKEN` under `on.workflow_call.secrets`, and each job needing it re-exports it in JOB-level `env: GITHUB_TOKEN: ${{ secrets.RUN_TOKEN }}` so any `docker run -e GITHUB_TOKEN` / Makefile forwarding chain is untouched. Verify by **subset, not text grep**: caller's mapping ⊆ callee's declared keys, and `GITHUB_TOKEN` absent from the callee declaration. The literal rejection text lives only in the rendered run page's annotation — the check-runs API returns 0 check-runs on a load failure — so capture the `Invalid workflow file:` line before guessing at the cause.
   - **A merge can land a head whose CI never compiled.** `merged: true` plus a merge-commit sha is not evidence the merged tree loads: an auto-merge can land a red or 0-jobs head when the gate does not read that signal, and then `main` reals the same path-named 0-job failure on every push while the PR reads MERGED. So after any merge that lands a workflow/gate change: `git fetch <canonical> main`, then read the merged head's own runs (`gh api 'repos/O/R/actions/runs?branch=main&per_page=10'`) — a `completed/failure` whose run name is the workflow path with 0 jobs means main is broken and owes a hotfix PR from this lane, not a report.

6b. **The timeout-bounds net names only the build/run workflows — extend it to the scheduled maintenance spiders.** `tests/test_engine_build_timeouts.py` pins only `engine-build.yml`+`engine-build-pr-trigger.yml` (#1865), `tests/test_pipeline_timeouts.py` only `ci.yml`+`pipeline.yml` (#846); the step jobs of `engine-bump.yml` (`plan`/`bump`), `engine-bump-rebase.yml` (`rebase`) and `registry-sync.yml` (`sync`) carry (`timeout-minutes` today but) nothing pins them, so a dropped or an added-unbounded job lands with every gate green and silently inherits GitHub's 360-min default — the #1696/#1250 hang one workflow family out. grep each workflow's step jobs for `timeout-minutes` (skip `uses:` jobs — they cannot carry a ceiling) and fold the maintenance set into one general every-step-job-bound rule; never narrow the #1865 list.

7. **timeout wall vs cell cost — a flat `timeout-minutes` on a matrix job that one variant now trips.** A single `timeout-minutes: N` on a shared matrix build job is a dimension bug the moment one variant's legitimate cost crosses N: the job is `cancelled` at the wall (UNTESTED, never green), so any proof cell that depends on it can never produce a COMPLETED-SUCCESS. Measure per-cell job durations (`gh run view <run> --json jobs` → started/completed per `engine-build-<engine>-<variant>`): a `cancelled` job whose duration ≈ N is a kill, and the `success` band (min/p50/max) in that SAME cell sizes the fix. The fix is **matrix-aware** (a `matrix.timeout_minutes` column — heavy GPU/rocm cells ~2× p95, cheap cells unchanged at their tight cap), NOT a flat global bump. **A timeout raise is only justified by a named COMPLETED-SUCCESS at the new cap, never by a longer cancellation** — land it only after one genuine build finishes on its own under the new wall; if it still does not finish, the defect is a build hang (schedule/steps), and a 600-minute cap just burns a runner. File the issue with the cancelled-at-wall job ids + the success band + that guard-able acceptance; do not implement in the same pass.

Issue shape (match #1508/#1514): `# Problem / # Proposal / # Acceptance criteria / # Ownership / # Related`, label `agent:implement`, anchor the body to the measured sha, cite file:line and the exact command output. Acceptance includes the prove-it-catches-a-bug step (plant the fault, expect red, restore). Clean sweep = record `re-audited at <sha>, no findings`.
