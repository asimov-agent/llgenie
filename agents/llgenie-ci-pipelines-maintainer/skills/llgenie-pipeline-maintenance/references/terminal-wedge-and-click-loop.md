# Terminal wedge and long-poll guardrails

## A read that returns EMPTY/not-found for a path you just created means the WRITE did not land — write-and-read-back in ONE call, never retry the identical read

When a tool sequence goes `write → read_file → EMPTY`, do NOT issue the same read again: an empty or `File not found` answer for a path you believe you just wrote is evidence the write landed in a DIFFERENT context (a degraded shell, a scratch dir deleted mid-call, a tool whose cwd differs per call) — retrying the read reproduces the same empty answer and burns dozens of calls (a session here looped ~50 times across `read_file`/`terminal` on files that were simply never written). Replace the split `write` then `read` with **one self-contained call that both produces and proves the artifact**, and make it report a byte count so an empty result is visible in the same breath:

```bash
gh api repos/<o>/<r>/commits/<sha>/check-runs --jq '.check_runs[]|[.name,.status,(.conclusion//"")]|@tsv' \
  > /tmp/ck.tsv 2>/tmp/ck.err; echo "bytes=$(wc -c </tmp/ck.tsv)"; cat /tmp/ck.tsv
```

then `read_file /tmp/ck.tsv` only if the echoed `cat` was itself truncated. Print `bytes=` (`wc -c`) after any write — a `0` there is the fact you need, and it is a real diagnostic, not a failure to retry. Same shape for a poll: one call prints `state=<..> bytes=<n>`; a second call re-measures, and stop the moment the answer is a definite conclusion rather than re-issuing an identical command.

**Check whether the tool is even pinned for this lane before reaching for it.** This lane's chat session is pinned (see the `host-bot-tools` block in SKILL.md) to `clarify`, `file` (`read_file`/`write_file`/`patch`/`search_files`), `memory`, `session_search`, `skills`, `terminal`, `todo` — a tool outside that set answers `Tool '<name>' does not exist … Available tools: …`, which is a pin, not a transient fault: switch to a pinned tool (use `terminal` for scripting/polling) instead of re-calling the missing one. The failure signature to recognise early is the `[Tool loop warning: same_tool_failure_warning; count=N]` appended to repeated failures — treat that warning as a stop signal to change strategy (different tool, one self-contained call), not as something to push past.

## A long `sleep` poll loop can wedge the terminal for the whole session

Watching a CI run with `for i in ...; do gh run view; sleep 60; done` that gets backgrounded (or whose wait budget expires) can leave a stuck background process holding the session stdout pipe. Thereafter EVERY terminal command — even `date; echo` — returns an empty `tool_result_wait ... backgrounded` placeholder, and read_file follows. The terminal subclass is wedged; the DM path (`message_agent`) still works.

Never run a bounded multi-minute poll loop that the runner may background. Prefer: (1) a single `gh run view --json status,conclusion` call; if still in_progress, (2) end the turn and re-check on the next wake — the delivery notification is the wake. If the terminal wedges, (3) deliver the exact one-liner the recipient can run at their seat (`gh run view <run> --json status,conclusion`) and ask them to confirm; the planner reads at the API and can verify independently. Do not claim a gate green without the concluding run read, and do not keep hammering a wedged tool.

## Deleting a directory that is the shell's cwd wedges EVERY later command — anchor to `workdir=` or a stable `cd`

The terminal tool keeps one persistent shell, so its cwd survives between calls. If you `cd /tmp/wtN && …` to probe/verify a throwaway worktree and then `rm -rf /tmp/wtN` in that same (persistent) shell, the next command runs from a directory that no longer exists: `fatal: Unable to read current working directory`, `pwd: error retrieving current directory: getcwd: cannot access parent directories`, and every following `cd <path>` fails `exit 126: cd: <path>: No such file or directory` even though `<path>` is valid. The `exit 126` looks like a permissions/exec glitch; it is the dead cwd. A probe script written earlier then fires `cd /tmp/wt1720: No such file` because the script itself `cd`s relative to a gone cwd.

Rule: **never leave the persistent shell's cwd inside a directory you intend to delete.** Two habits prevent it: (1) pass an absolute `workdir=` on every terminal call instead of relying on a `cd` from an earlier call — the tool resets per-call cwd from `workdir` and a deleted dir in a prior call cannot wedge it; and (2) when you must `cd` in-command, wrap the whole sequence `( cd /tmp/wtN && … ; cd $HOME/repository/git/ai-repositories/llgenie )` in a subshell (`( … )`) so the parent shell's cwd never moves into the throwaway tree, or end with `cd` back to a stable repo dir before `rm -rf`. If already wedged, one call with a fresh absolute `workdir=` (e.g. `$HOME/repository/git/ai-repositories/llgenie`) restores it — the shell re-resolves a real cwd and subsequent relative commands work again.

## Removing a throwaway worktree: the REGISTRATION drops before the DIRECTORY does, and container residue blocks the delete

Cleaning up a temp verification worktree (`git worktree remove --force /tmp/wtN`) fails with `error: failed to delete '/tmp/wtN': Permission denied` whenever you ran a container in it — the container leaves root-owned `__pycache__/` and `.pytest_cache/` that your user cannot `rm`, and non-interactive `sudo` here cannot read a password (`a terminal is required to read the password`), so the directory cannot be fully removed. **The registration, however, is dropped FIRST, in the same call** — so do NOT loop on the removal or reach for sudo. Verify with `git worktree list --porcelain | grep -c wtN` (expect `0`): once unregistered, the lane board is clean and the lingering `/tmp` dir is harmless residue, not a leak. A follow-up `git worktree remove` then reports `fatal: '/tmp/wtN' is not a working tree` — that is the confirmation, not a failure. Report the residue as such (its own throwaway tree, only `__pycache__`/`pytest_cache` inside, unregistered) and never touch another lane's worktree (owner-only rule).

## A state-changing command is proven by its POST-CONDITION, never by the absence of a printed error

In a wedged shell (dead cwd, above) a `cd <path> && gh run rerun <id>` is a **silent no-op**: `cd` fails, `&&` short-circuits, `gh` never runs — and the tool call still reports `exit_code: 0`, because the tool succeeded at running a shell. Quote that rc anywhere (a comment, a DM to the planner, a PR body) and you have written a fabricated fact onto the record, which survives as a baseline the next lane acts on. Reported once, the correction costs more than the original report.

Rule: **before reporting that a command acted, read back an artifact only its success could have produced** — for `gh run rerun`, a bumped `run_attempt` or the refusal text (`This workflow is already running`); for a push, `git ls-remote <remote> refs/heads/<branch>` equal to local HEAD; for an issue/comment, the direct `.../issues/comments/<id>` read. An empty stdout plus `exit_code: 0` is NOT proof; `echo "bytes=$(wc -c <f)"` returning `0` on the intended output IS the finding. If you already reported a claim you cannot prove, retract it on the same surface and check whether the on-wire artifact even exists — an absent comment is the tell the command never executed, so the honest retraction is "it never landed", not "it landed wrong". Choose state-changing one-liners that fail loudly: prefer `cmd || { echo FAILED; exit 1; }` over a chain whose first element can silently no-op.

## A check-pr-closing range artifact from a stale in-FLIGHT base is cleared by a rebase, not a rerun

2026-11-01 #1412: after my proc-gate fix pushed (7ad820bf), the guard redded on `make check-pr-closing` with violations citing #1414/#1415 — issues that live on MAIN commit d94d3280 (#1415), not in the PR. The runner diffed `--base 391df770` (the branch's base), and the PR merge-ref swept main's newer d94d3280 squash claims into `base..rev`, so the squash check read them as the PR's un-closed claims. Proof it was a range artifact, not a PR-body defect: `check_pr_closing.py check --base d94d3280 --rev HEAD` passed rc 0 with the real body, and `git log 391df770..7ad820bf` = exactly the PR's 2 commits, neither referencing #1414/#1415. Same stale-base class as the linux/unit case in stale-ref-and-transient-red.md. The remedy is a REBASE onto current main (d94d3280), which brings base..rev to the PR's own commits — NOT a rerun of the same head (the runner re-diffs the same stale base). Rebasing is the llgenie-pr-merge-conflict lane's job (#1015: CONFLICTING scope; a test `--onto d94d3280` failing means it is genuinely conflicting now). When handoff is to that lane, report the branch, both heads, the failing command + step + run id, and that the PR's own commits are clean so it is a base/range case, not a defect.
