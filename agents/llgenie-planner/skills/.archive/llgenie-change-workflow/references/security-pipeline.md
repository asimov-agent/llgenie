# The llgenie security pipeline — what owns what

Four moving parts, four owners. Changing one without the others is what reds the repo.

| Owner | Files | Rule |
|---|---|---|
| The scan | `.github/workflows/security-scan.yml`, `scripts/security_scan.py`, `data/security-policy.json` | Its own daily pipeline: only `schedule` + `workflow_dispatch`. NEVER `pull_request:` or `push:` — a pre-existing advisory must not red a PR or `main`. |
| The floor | `scripts/security_bumps.py`, `tools/security-floors.in` | The scan's own findings become the MINIMUM version each package must reach, written as pip-compile constraints and compiled through the one generator. |
| Freshness | `renovate.json`, `.github/workflows/renovate.yml`, `docs/RENOVATE.md` | Bumps pins forward on a daily schedule. Never merges, never touches generated/vendored paths. Runs the CLI ON THE RUNNER (`npx --yes renovate@<exact version>`), not inside the action container, because its `postUpgradeTasks` re-runs the docker-based requirements generator. |
| Tagged issues | `scripts/security_issues.py`, `scripts/security_bot.py` | One issue per (advisory, package), keyed by an HTML marker in the body; the bot edits only a DIRECT pin in `tools/*.in`. |

## The invariants, and the gate that holds each

- **Enforcement is data, never a workflow literal.** `enforce_events` in `data/security-policy.json`
  names the only events that may fail a run; every other event is report-only (prints findings, exits
  0). `security_scan.mode_for(event)` resolves it.
- **`make check-security-scan` refuses the regression.** It fails when `enforce_events` is empty, names
  an unknown event, names `push`/`pull_request`, or when either trigger is re-added to the workflow
  (it parses the workflow's `on:` block). Never relax that check to make a PR green.
- **The floor is the maximum of the minimums.** A package with several advisories needs the highest of
  their lowest fixed versions; a finding with no `fixed`, or a "fix" at or below the installed
  version, is not a floor. `security_bumps.floors()` is the one implementation.
- **A compiled `requirements*.txt` is never hand-edited.** The floor goes into
  `tools/security-floors.in`, which both `.in` files include with `-c security-floors.in`; the pins are
  then REGENERATED by `make -C tools generate-requirements` / `generate-requirements-dev`.
  `make check-security-bumps` fails on a pin below its floor, a floor line with no advisory reason, or
  a missing include.
- **Green or nothing.** A bump PR exists only when the regenerated pins satisfy every floor and the
  fast gates pass; otherwise the floor file is reverted and no PR is opened.
- **CI keeps the single merge authority.** `renovate.json` carries NO automerge key at all — the
  repo's `auto-merge` job is the only thing that merges. Do not add `automerge: true` or
  `platformAutomerge: true` to "make the bot land its own PRs".
- **Generated and vendored paths are off-limits to Renovate:** the generated engine dockerfiles/params
  and their shared base (written by `make generate-engine-params`), `containers/scanners/digests.json`
  (written by `make scanner-digests`), and the vendored registry/quant catalog (written by the syncs).

## Proving a floor/requirements change (do this, do not reason about it)

`pip-compile` accepts `-c security-floors.in` and silently does nothing when the file is empty, so the
include can look wired-up while constraining nothing. Prove both directions with the REAL generator
(`NERDCTL=docker` when `nerdctl` is absent — it runs in a container and needs the index):

```bash
# 1. comment-only floor file: the compiled output must be BYTE-IDENTICAL (the include is inert)
make -C tools generate-requirements NERDCTL=docker && git diff --stat tools/requirements.txt   # expect no change
# 2. write the floors, regenerate, and read the pins back
make -C tools generate-requirements NERDCTL=docker && grep -E '^(certifi|urllib3|filelock)==' tools/requirements.txt
make -C tools generate-requirements-dev NERDCTL=docker && make check-security-bumps
```

A resolved pin usually lands ABOVE the floor (the index's newest compatible), which is correct — the
floor is a minimum, not a pin. Never write a `==` into the floors file to force the scanner's exact
version, and never edit the compiled file to match a floor.

## Affected-image rebuilds need no second list

A base-image bump moves every engine tag because the GENERATED engine Dockerfile embeds
`FROM llgenie/base-<backend>:<hash of the rendered base>` on its `FROM` line, and the engine image tag
hashes that Dockerfile. A Python pin change moves the test image's lockfile hash. So a bump PR starts
the affected `engine-image-*` / `ci-images` jobs by itself — do not add a path filter or an engine list
that duplicates the content-hash scheme.

**But a moved tag means the job must PUBLISH it, and a fork head cannot.** `publish-ci-images` has no
fork skip (the engine images get one, per the fork-publish rule), so a fork PR that changes
`tools/requirements*.txt` or `containers/test/Dockerfile` reds `ci-images` and then
`install-published-*` with `denied: … Write organization package`. Prove the mechanism locally with the
real generator (below), then ship it with an EMPTY floors file / unchanged lockfile and let the daily
run's same-repo branch carry the pin move. `make -s ci-image-refs` is the cheap check: a test-image
hash that differs from `origin/main`'s is the signal.

## Scanners

Each scanner runs from its own immutable GHCR image named by `containers/scanners/digests.json`; the
SBOM tool (syft) rides the grype image via `--entrypoint syft`. Never install a scanner at scan time and
never call one from a floating tag. A version bump is a Dockerfile change plus `make scanner-digests`
plus a PR.

### Retiring a scanner is a whole-tree edit, not a Dockerfile delete

Deleting the image and the dispatch branch is the easy half; the residue is what makes the stack lie.
A doc that says "<scanner> was removed because it needed a paid account" tells a reader the pipeline
STILL runs it and that one scanner still needs a secret. Sweep every surface:

```bash
git grep -in <scanner> <branch>          # run on EACH branch of the stack, not just the tip
gh issue view <n> --json title,body      # the issues the change implements, and their titles
gh pr view <n> --json title,body         # bodies claim the roster; a stale claim is documentation too
```

The places it hides: the scanner's `Dockerfile` and its `digests.json` entry, `docs/SCANNERS.md`,
`docs/SCANS.md`, the `openspec/changes/*/proposal.md` + `tasks.md` bullets, the `agent-wiki` note,
the `security_scan.py` module comment, the workflow's `on:`/inputs, and the Makefile's `##` help text
(the help string is user-facing documentation that `check-docs` reads).

Rewrite each to state the rule that now holds ("every scanner is a pinned apk package, so no scan
reads a credential") rather than narrating the removal; keep zero occurrences in the tree so
`git grep -i <scanner> origin/main` returning nothing is a checkable invariant.

**A negative test must not name the thing you removed.** `scan("<removed-scanner>")` asserting the
unknown-tool error pins the refusal to a real product name — if it ever returns to a roster the test
silently starts passing for the wrong reason. Use an id in no roster (`gitleaks`).

## What is deliberately NOT covered

A base digest with no newer upstream digest, an action SHA with no released tag, a floor the resolver
refuses, and a code finding all need an agent leg — that is a separate issue and workflow, not
something to fold into the deterministic script.
