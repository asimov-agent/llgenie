# Analyzing and filing a rename refactor

When the user says "X is confusing, rename it to Y — do a deep analysis and
create the issue," the deliverable is a grounded issue whose body carries the
measured evidence and a decision table, not a bare request to rename. The
analysis below is the workflow that produced a rename issue the reviewer could
act on without re-deriving anything.

## 1. Disentangle the name's distinct meanings FIRST

A confusing name is almost always one string carrying N different referents.
Build a table before touching anything: each meaning, where it lives, and a
verdict (rename / keep / split). The verdicts are the spine of the whole issue.
In the llgenie case "llama-serve" meant three things:

| meaning | where | verdict |
|---|---|---|
| the tool's own CLI (hardware detect, engine pick, dispatch to per-engine start scripts) | the module file, the installed launcher + symlink | **rename** |
| the upstream binary and the shim that masquerades as it | `~/bin/<upstream>-server` shim, `SERVER_SHIMS`, the upstream params files, its build script | **keep** — upstream's name, and the shim exists so external callers find it |
| the tool's OWN seams wearing the upstream's name | `LLAMA_*` env vars that are the tool's knobs, not upstream flags | **split** — new name preferred, old accepted as deprecated alias |

## 2. Measure scope with grep, excluding noise

- `grep -rc <name> --include="*" . | grep -v ':0$' | grep -v '^\./\.git/'` for
  per-file counts; sum for the total. Exclude `.git` and `__pycache__` — stale
  bytecode (`*.cpython-*.pyc`) inflates the count and is a build artifact, not a
  reference.
- Count the **alias** too — a test-side alias can be worse than the filename
  (measured: `llama_ai` had 291 refs, 242 in one test file named after the
  pre-rename brand, vs 210 for the module name itself). The test file's own name
  is part of the rename.
- Quantify the "the name lies" claim: count the module's functions, the engines
  it dispatches (from the registry), and how many of its functions name the
  upstream — that is the evidence that the file is engine-agnostic while named
  for one engine.

## 3. Find prior art — a prior rename often deliberately stopped at the file

A brand rename that already happened usually has an OpenSpec proposal listing a
capability like "the internal module stays at `<old>.py`" — i.e. the earlier
rename stopped at the file on purpose. Cite that decision verbatim; the new
issue closes the loop it left open. Reuse the prior rename's playbook (git mv,
regenerated install artifacts, image tags untouched) rather than inventing a new
one.

## 4. Identify the pinned artifacts (the real blast radius)

Grep for the things that hardcode the path and are asserted or regenerated:

- Makefile guards: `test -f <old> || { echo "FAIL: repo touched"; exit 1; }`
  (a post-uninstall integrity check that must point at the new name).
- Launcher wrappers that embed the path (often twice) and the symlink that
  points at the module — both regenerated by `make install`, so a reinstall is
  part of the migration, not a manual step.
- Test assertions on the installed artifact (`assert "<old>" in launcher_text`,
  `import scripts.<old>`). These must be updated, not weakened.
- Check whether any CI workflow names the module directly — if they go through
  `make` targets, the blast radius is the Makefile/tests/docs/host install, not
  the pipelines.

## 5. Separate what must NOT be renamed, and why

The upstream binary's name, its build script, its params files, and any shim
that masquerades as the real binary (so other tools that call the upstream name
keep resolving) are all keep. Renaming them breaks external consumers and the
images. State this explicitly in the issue so a reviewer does not over-apply the
rename.

## 6. Split the tool's own seams from the upstream's

Env vars that are the tool's own knobs but wear the upstream's name get new
names with the old accepted as a deprecated alias (no host breaks); the
upstream's own flags keep their names. Name the new convention explicitly (e.g.
`LLGENIE_*`), and note any seam that already follows it as the precedent.

## 7. Propose a one-release compatibility shim

Keep the old path as a one-line re-export (`from <new> import *` plus the names
tools/tests use), marked deprecated, so user scripts, cron entries and
muscle-memory invocations keep working. Remove it in a follow-up once the old
references are gone.

## 8. Verification is behavior-neutral proof

A rename must not change behavior. Acceptance: run the tool's `--dry` plan
before and after for BOTH the "native" engine and a non-native one and show the
output is byte-identical — any diff is a bug in the rename. Plus a grep guard
test (same shape as the wiring guard) that fails if the old name reappears
outside the shim and the historical records.

## 9. Leave history alone

Dated agent-wiki notes and already-merged OpenSpec changes are the record — do
not rewrite them (that falsifies history). The one exception is the prior
rename's decision being superseded, which the new issue states and supersedes.

## Issue body shape

Lead with the summary + the decision table, then: measured scope (occurrences /
files / functions / engines), the must-not-rename list with reasons, the pinned
artifacts, the plan (rename → shim → pinned-artifact updates → seam split →
optional deeper cut), external consumers to check, verification/acceptance, and
related issues. The user asked for "deep analysis" — the numbers and the table
ARE the analysis; the issue must carry them.
