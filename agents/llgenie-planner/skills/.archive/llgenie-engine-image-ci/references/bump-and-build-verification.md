# Verifying a bump actually produced working per-arch images

Use after bump PRs merge (or immediately, to test the pipeline). Order matters: each step below is
cheap-to-expensive, and the cheap ones rule out the failure modes that make the expensive ones lie.

## 1. The generated artifacts match the skills

```bash
make check-engine-params     # -> "[engine-params] 0 file(s) stale"
```

Zero stale means every `containers/engines/params/<id>.json` and every
`containers/engines/dockerfiles/<id>/Dockerfile.<arch>` agrees with the bumped skill pin. Do this
before any build: a stale Dockerfile makes a build failure ambiguous.

## 2. Every arch's build definition resolves

```bash
for f in containers/engines/dockerfiles/*/Dockerfile.*; do
  docker build --check -f "$f" containers/engines >/dev/null 2>&1 || echo "BAD $f"
done
```

**Pitfall — build the four bases first, or ~12 of ~31 files will look broken.** A compiled engine's
Dockerfile starts `FROM llgenie/base-<arch>:<hash>`, a locally-built-and-tagged base. With that tag
absent, `--check` fails with `pull access denied for llgenie/base-cpu:...` and the error names
the `FROM` line, so it reads like a malformed Dockerfile. It is a missing image, not a defect.

```bash
for a in cpu cuda rocm vulkan; do python3 scripts/engine_image.py build-base "$a"; done
```

The subcommand is **`build-base`** (`base` is not a choice). It pulls the published base from GHCR
when one exists, so this is seconds-to-minutes, not a compile. Only then is `--check` conclusive:
expect `OK=<n> BAD=0` for every engine x arch pair.

## 3. Is each arch's install image published?

```bash
for a in cpu cuda rocm vulkan; do make ci-wait-engine-images ARCH=$a; done
# -> "[install] every image install pulls is published"
```

This resolves exactly the tags `install_engine_launchers.install_plan` would pull and polls the
registry manifest — no multi-GB download, and it names a tag that never appeared. It is the cheapest
way to answer "does `make install` work on a rocm/vulkan host".

## 4. A REAL compile, then the two post-build tests

**Pitfall — `make build-engine` may not build anything.** When the tag already exists locally or on
GHCR it prints `available -> no rebuild` and exits 0. That pull is worth knowing (it proves
merge -> CI -> GHCR -> pull carried the pin), but it proves *publication*, not *buildability*. Force a
compile when the question is "does this arch build":

```bash
make build-engine ENGINE=llama.cpp ARCH=cpu  FORCE=1
make build-engine ENGINE=llama.cpp ARCH=cuda FORCE=1   # -> "[engine-image] built <tag>-cuda"
```

Then exercise the artifact, both ways:

```bash
make test-engine-image ENGINE=<id> ARCH=<arch>   # binary prints its version / documented flags
make test-engine       ENGINE=<id> ARCH=<arch>   # container serves the tiny model, OpenAI call answers
```

`test-engine` covers the flag families per engine (a manifest that documents only `--help` still
passes). It downloads the smoke model on first use into `~/models/smoke/`.

## 5. GPU path: say what actually ran

A GPU image of an engine with a CPU fallback serves **without** devices, so a green `test-engine` on
a cuda image proves the binary and the runner, not the GPU. The real device path needs the CDI device
`nvidia.com/gpu=all`, generated by
`sudo nvidia-ctk cdi generate --output=/etc/cdi/nvidia.yaml`. When that file is absent, the host
cannot run the GPU path at all — report the CPU-fallback result and name the missing prerequisite
instead of implying the GPU was exercised. CI's `test-published-*` matrix is where the device path is
covered.

## 6. Driving the bump workflow itself

```bash
gh workflow run engine-bump.yml -f engine=''      # empty = every engine
gh run view <id> --json status,conclusion,jobs --jq '{s:.status,c:.conclusion,jobs:[.jobs[]|{n:.name,c:.conclusion}]}'
```

Jobs are `guard`, `plan`, then one `bump-<engine-id>` per engine, in parallel. Success is not "the
run is green" — confirm the artifacts: `gh pr list --search 'chore/engine-bump' --state all`, then
read one PR's diff (`params/<id>.json` ref + `pinned`, both Dockerfile labels, the clone tag lines)
and its body's `**Dependencies:**` line (`python_added=… apt_added=… python_removed=… apt_removed=…`).

A useful trick while the pipeline is new: run the bump locally in a `--detach` worktree off
`origin/main` first (`git worktree add --detach ../llgenie-wt/bump-verify origin/main`, then
`make engine-bump ENGINE=<id>`), inspect `git diff --stat`, then delete the worktree. That proves the
local generator without touching `main` or racing CI. Clean it with
`git worktree remove --force` (it is detached and dirty by design).

## 7. Bot steps that report instead of applying must exit 0

**Pitfall — a legitimate no-op that exits non-zero is silently thrown away.** A review/analysis step
wrapped in `continue-on-error` + `|| echo "::warning::…"` stays green, but `make: *** Error 1` lands
in the log and any artifact only written on the success path never appears — so the model call is
paid for and the finding is deleted. When a step's honest outcome is "nothing to apply", it must exit
0 and still write its report file.

## 8. Timing

`make test-unit` runs 15-18 minutes. Every long gate in this repo (`test-unit`, engine compiles,
`build-base` of a fat toolchain) goes to a background command with `notify=true` and a log file to
poll; foreground calls hit the tool timeout and lose the result.
