# Generator-owned committed artifacts (README, store, snapshots)

In a repo whose README and data store are GENERATED (trending-local-llms is the reference
case), three files/dirs are owned by a single generator and must never be hand-edited or
bulk-deleted:

- `README.md` — regenerated by `scripts/update_trending.py` from a prose template
  EMBEDDED IN THAT SCRIPT. Hand-editing `README.md` fails the repo's deterministic
  regenerate gate (`check_readme_generated` / `validate` prints `README.md is NOT
  regenerated`). Put the prose in the generator's template, then run the generator, then
  keep ONLY the intended lines in the diff.
- `data/models.json` — also rewritten by the same generator (it re-ingests raw snapshots
  into the store), so regenerating the README churns the whole store. A bot/CI PR that
  only adds a workflow must NOT carry that data churn.
- `data/snapshots/` — COMMITTED, generator-owned history.

## The regenerate-then-revert pattern

To land a prose change (e.g. a new bot bullet) without polluting a feature PR:

1. Edit the prose template inside `scripts/update_trending.py` (line-based insert anchored
   on a unique bullet, not `patch` fuzzy — the template has anchor-escaped sequences).
2. Run the generator: `python3 scripts/update_trending.py`.
3. Revert the data side so the PR is only the template + README:
   `git checkout -- data/models.json` and delete the freshly written snapshot
   (`rm data/snapshots/trending-<ts>.json`, the file the run just added).
4. Re-run the gate to confirm `README.md` now matches the generator output.

## The durable fix: a render-only path, so a docs change never churns the store

The regenerate-then-revert pattern is a WORKAROUND for a design gap: the generator's only
entry point also ingests raws, bumps the store's `generated_utc` and writes a NEW snapshot
containing no new data — store churn a docs-only PR should not carry, and a snapshot
indistinguishable from a real ingest. When a docs/template change needs a regenerate, give
the generator a `--render-only` path instead of reverting the data side by hand:

- Render from the store **as of the store's own `generated_utc`** — the same as-of the
  deterministic regenerate gate re-renders with — and return BEFORE the ingest, the
  timestamp bump, the store write and the snapshot. A store with no usable stamp is a
  loud error (`run make merge`), never a silent empty render.
- **Preserve the `> Last generated:` line already on disk** (the generator stamps the wall
  clock there), so a re-run is a NO-OP and a docs change never moves a timestamp. The
  regenerate gate strips that line before comparing, so correctness is unaffected.
- Expose it as its own `make render-readme` (docker wrapper over the host recipe), the
  repo's standard pairing, and document it in ARCHITECTURE.md (rule 6h).
- Point the regenerate gate's repair message at the right target: `make render-readme` for
  a docs change, `make merge` for new data.
- Prove it with a test that drives the REAL script through its data-dir/README seams
  against a copy of the real store: store byte-identical, no snapshot written, re-run is a
  no-op, a hand-edited README is repaired, the stamp survives, and the Makefile/ARCH
  wiring exists. Verify RED on the pre-change script (the flag did not exist) then GREEN.

This is the same class as the OpenSpec index: a generated artifact that every change
edits needs a path that does not force unrelated churn, and the gate must name the right
repair for each kind of change.

## A change to a DERIVED field needs `merge`, not `render-readme`

`render-only` re-renders the README from the store AS OF its stamp and writes neither the
store nor a snapshot. That is right for template/prose work and wrong the moment the
change alters a DERIVED value (a score, a bonus, a rank, a tier membership): the README
moves, `data/models.json` keeps the old numbers, and the ranking/consistency gate — which
compares the two — goes red for a reason that looks unrelated.

Re-score through the merge path while ingesting NOTHING new: `SINCE` is a lower bound, so
a stamp above every raw snapshot skips them all and still re-sorts, recomputes and writes
store + README + one snapshot together:

```bash
make _merge SINCE=2999-01-01T00:00:00Z
```

Keep that snapshot: it is the record of the new derived state, not churn. Rule of thumb —
prose/template change → `render-readme`; derived-field change → `merge` (with a future
`SINCE` when no new data should enter).

## A new generated SECTION re-points every row lookup in the test suite

Inserting a section ABOVE an existing one silently changes what the existing tests find.
Rows rendered by the new section carry the same `| [**Name**](hf) |` shape and often the
same value cells, so a pattern that used to hit the old table now hits the new one:

- `next(ln for ln in md.splitlines() if ln.startswith("| [**Name**]"))` returns the NEW
  section's row;
- `md.replace("**150** t/s<br>[vLLM]", …)` mutates the NEW table, so a guard test that
  expected a failure goes green with nothing mutated;
- `cells[6]` raises `IndexError` on a four-column row — the suite stops at the first red.

Before adding a section, grep the tests for `splitlines()`, `.replace(` and `startswith("|`
over rendered markdown; every hit is a candidate. Scope each one to its own section and
assert on that slice, never on the whole document:

```python
head, loved = md.split("## ❤️ Most loved", 1)      # or .rsplit / a heading finder
row = next(ln for ln in loved.splitlines() if ln.startswith("| [**Name**]"))
first = next(k for k, ln in enumerate(lines) if ln.startswith("## <heading>"))
i = next(k for k, ln in enumerate(lines) if k > first and ln.startswith("| [**Name**]"))
```

Update those tests in the SAME change (the repo's contract rule) — a section move is a
format change, and the fixture-only assertions are what catch it.

## A gate that admits "unparseable" admits every class word the parser cannot read

A scope gate written as "parse the number; unknown means in scope" — `vram = parse(hw);
return vram is None or vram <= LIMIT` — passes anything its parser cannot recognise. A
hardware string that names a machine CLASS (`datacenter GPUs, 512 concurrent requests`)
has no card name and no size, so it parsed as `None` and a datacenter AGGREGATE earned the
top score and the headline cell, while the gate's own SKU list looked exhaustive.

- **Refuse the class phrase on its own**, not only the SKU families: a word-bounded regex
  for the class (`\bdata[\s-]?cent(er|re)\b`, plus the platform words your data actually
  uses) beside the SKU list, so a new spelling of the class cannot slip through.
- **Keep the unknown-but-plausible case admitted** — an unnamed consumer card is not a
  datacenter part; the rule targets the provable class word, never "we could not parse it".
- **Prove it with the shipped record**, not a fixture alone: assert the real store's worst
  offender is now out of scope AND that the row it dominates still renders in its backend
  table (the figure is not deleted; it stops earning a ranking bonus).

## Where a bad value must be refused: the ingest boundary

An LLM writes structured records into the store, so the store's WRITE PATH is the only
place a guard can hold. Validation on the resulting PR is the wrong gate for a value the
writer manufactured: the PR goes red, a repair bot hand-patches that one row, and the same
source record re-breaks the next run because it is still inside the search window. A
whole day of refreshes was lost this way while each PR looked like an isolated data bug.

- **A prompt that names the bad value BY NAME is not a guard.** An instruction listing the
exact wrong token still produced it — and a second, different invented variant the same
day. State the rule in the prompt AND enforce it mechanically where the record enters
the store; do not spend more prompt budget enumerating bad strings.
- **Refuse on a PROVABLE shape only.** Refuse a field value whose shape cannot be
legitimate in that field — a quantization token (`FP4`, `NVFP4`, `Q8_0`, `AWQ`, `GPTQ`,
`GGUF`, `EXL2`) inside an ENGINE name, a CPU/GPU product token (`Oryon`, `Ryzen`,
`Snapdragon`, `RTX`, `Radeon`, `Strix Halo`, `M4 Max`) inside one. Both are provable: an
engine name never contains them.
- **Constrain the token pattern with a digit or a boundary, or it eats real names.**
  `exl\d*` matched the REAL registered engine `ExLlamaV3`, and an unbounded `strix` would
  match `strixite`. Write `exl\d+`, `q[2-8](?:_[a-z0-9]+)*`, `strix(?![a-z])`, and verify
  against the registry's own names AND against a fixture store whose `engines` map is
  EMPTY — a registry short-circuit hides the false positive in the fixtures that carry the
  full registry and lets it fail in the ones that do not.
- **Do NOT refuse on "the value is a substring of another field".** A real engine name
legitimately appears inside a model name (`WebLLM` inside `Llama-3.1-8B (WebLLM)`, `MLX`
inside `mlx-community/…`), and a substring rule refused a legitimate measurement and broke
an unrelated test module. Heuristics that need a registry to be complete are not guards.
- **Never swallow a plausible-but-unknown value.** A genuinely new engine or format is
UNKNOWN, not invalid: let it through and let the strict gate fail loudly for a human. The
guard's job is the manufactured value, not the unfamiliar one.
- **Refuse loudly, naming the source record** — model, field, value and the post/URL it
came from, one line per row, so the repair lands on the raw snapshot instead of on a PR.
- **Check what the refusal means for the data rules.** Refusing an incoming row is not
"loss": an additive-only rule governs STORED values, and the refused row never became one
(the usual case is a duplicate of a real row under an invented key). But when the refused
row is a new model's only measurement, that model then fails the "at least one
measurement" gate — which is the correct loud outcome, not a silent drop. Normalising an
identifier is a different, riskier move: repair only what is provably a formatting error
(an `_` where the contract allows `-`), never rename an existing stored key, and never let
a normalised id silently split one model into two.
- **Prove it with the real writer.** Drive the actual ingest against a temp raw dir plus a
copy of the real store: the bad row is absent, the good row survives, and the validator
stops failing that record. Then prove RED on the pre-change code by swapping in
`git show origin/master:<script>` and re-running — see `pr-landing-pitfalls.md`.

## Destructive `rm` over a generator-owned directory

A one-line cleanup `rm data/snapshots/trending-*.json` deletes EVERY committed snapshot
in the dir (hundreds of `D` entries in `git status`) as well as the one you meant. Before
any `rm` glob over a generator-owned path, verify the scope (`ls` the match) and, if you
over-delete, restore with `git checkout -- <dir>` — never `git add -A` while those
deletions are staged. Treat every file under a generator-owned dir as non-disposable.

## Test-suite shape (no pytest)

Some CI test repos use a bespoke runner instead of pytest: `tests/test_*.py` each define
`check()`-style cases reporting `_PASS`/`_FAIL` counts and a `main()` that runs them, and
a wiring gate (`test_make_commands` / `architecture-check`) fails if a test file's `main()`
is not reachable from a `make` target. A new bot/pr test must (a) implement that pattern,
(b) be called from `main()`, and (c) have its `main()` invoked by a make target in the
same commit — an orphaned `test_*.py` that is not in any target runs in no gate.
