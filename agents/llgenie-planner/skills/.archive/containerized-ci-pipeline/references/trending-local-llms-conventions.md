# trending-local-llms repo conventions (andyholst/trending-local-llms)

The trend repo is a sibling of llgenie with its own AGENTS.md, OpenSpec and bot fleet. Porting llgenie's `check_secret_output` guard there surfaced these non-obvious rules:

- **Tests run as PLAIN SCRIPTS, not pytest.** The test image's pytest path is dead — `make test`'s `_test` recipe tries `pytest` then falls back to running each `tests/test_*.py` as a script. A new test file MUST be plain-script-runnable: a `check(name, cond, detail)` helper, `main()` that calls every test, `if __name__ == "__main__": raise SystemExit(main())`, and `tempfile.TemporaryDirectory()` instead of pytest `tmp_path`/`capsys` fixtures. It must ALSO be added to the `_test` fallback chain in the Makefile (a test file not in that list runs in no gate).
- **OpenSpec spec.md MUST use delta headers.** The validator rejects a spec whose sections are `## 1.`/`## 2.` — it requires `## ADDED Requirements`, then `### Requirement: <name>` (prose + a `WHEN … / THEN …` block), then `#### Scenario:` with `- **Given**` / `- **When**` / `- **Then**` / `- **Test:** <path>::<test>` lines. A scenario whose `- **Test:**` names a test that does not exist is a defect.
- **The `patch` tool's fuzzy matcher corrupts YAML and markdown indentation** (it re-nests `- name:` list items and shifts bullet indents). For `qa-validate.yml` steps and AGENTS.md rule bullets, do a deterministic line-based splice in Python (locate a unique marker line, replace the slice, write the file) instead of retrying `patch`.
- **The openspec-tasks gate requires EVERY task ticked, including the final verification box.** `make openspec-check` stays red until the last `- [ ]` is `- [x]` — tick the final boxes in the same commit as the fixes that make CI green, or the gate blocks the whole run.
- **The openspec CLI runs with `--user $(id -u):$(id -g)`** in this repo, so `make openspec-new` files are owned by you (unlike llgenie where they are root-owned and need a chown).
- **Auto-merge squashes when `validate` + `live-smoke` are green.** The PR is squash-merged and the branch auto-deleted by qa-validate's `auto-merge` job; the agent never merges. `validate` builds the test image first (image-ensure), so it takes ~9 min; `live-smoke` ~4 min.
- **A PAT without the `workflow` scope CANNOT squash-merge a PR whose diff edits `.github/workflows/*.yml`.** The merge API refuses with `GraphQL: refusing to allow a Personal Access Token to create or update workflow ... without \`workflow\` scope`. An `auto-merge` job that runs `gh pr merge` with an unscoped PAT passes ALL checks yet still fails the merge for a workflow-touching PR, leaving it OPEN and mergeable. This is a credential-scope problem, not a diff problem: the same job merged workflow-file PRs earlier, so the token's scopes drifted (rotated/regenerated without the scope). Fix: give the merge credential the `workflow` scope (or merge manually); confirm the drift by inspecting `gh pr view <n> --json mergedBy,mergeCommit` on the last successful workflow-touching merge.
- **A new guard needs a §8 row AND a rule-3c comment on the issue** (AGENTS.md rule 3c: an issue that changes AGENTS.md behaviour must carry a comment naming the exact sections).
- **The no-secret-VALUE guard (`scripts/check_secret_output.py`) is the llgenie port** — gitleaks (`make secret-scan`) only catches a committed credential VALUE; the output guard catches the run-time leak shapes (printed value, `-e KEY=$KEY`, `${{ secrets.X }}` in a `run:` block, xtrace, env dump, credential-shaped literal). When porting it, include `${{ github.token }}` in the interpolated-`run:` deny set — `github.token` is a real credential even though it is not a `secrets.*` reference, and a naive guard misses it, so a credential VALUE still lands in the step text. It is wired into qa-validate's `validate` job and `make test`.

- **A `workflow_dispatch`-only workflow is NEVER exercised by the PR pipeline.** `qa-validate` runs only on `pull_request`/push, so a change to `publish-agent-image.yml` (or any dispatch-only workflow) ships green and its runtime failure is only found on the first real dispatch. Fix: assert the workflow's runtime SHAPE in a hermetic test (read the YAML, check the step's `env`/order/`if`), because CI cannot run it. Measured: the `publish-agent-image` probe step ran `make agent-image-push-check` with no `env`, so `ensure_image.py push_check()` — which reads `GITHUB_TOKEN`/`GH_TOKEN` from the environment, NOT from `docker login` — failed `no credential in the environment` on every dispatch (#229/#230). `docker login` proves nothing to a script that reads the env.
- **A fix to just-merged work still needs its own issue + OpenSpec change** (the repo's rule 6f/6e: every change is tracked). Create the change with `make openspec-new NAME=...`, tick every task in the same commit you expect CI to make green, and `make openspec-index` LAST (ticking tasks changes the resolved task-progress column, so regenerating the index before the ticks leaves it stale and `make test`'s `test_openspec_index.py` fails).

- **The GHCR push probe must exchange the token for a push-scoped one.** GHCR rejects the raw token used as `Authorization: Bearer` on the registry API (`403 {"code":"DENIED","message":"invalid token"}`); `Basic` on the upload is `401 authentication required`. The working flow is `GET https://ghcr.io/token?scope=repository:<owner>/<repo>:pull,push&service=ghcr.io` with `Authorization: Basic base64(<user>:<token>)` → then `Bearer <scoped>` on `POST /v2/<path>/blobs/uploads/` → **202**. GHCR ignores the Basic username (any non-empty works; empty is 401) — `_docker_user()` reads it from the docker config as the most truthful value. This is what llgenie's `check_push` (`scripts/ci_images.py`) does; the trend repo's `push_check` originally sent the raw token, so it could never pass against the real registry.
- **A fake external CLI that accepts ANY subcommand hides real failures.** The fake `docker` in `tests/test_ensure_image.py` exited 0 on every command, so `docker push <untagged ref>` "succeeded" while real docker prints `tag does not exist` and exits 1 — the publish pipeline's `publish()` pushed `:latest` without ever tagging it and the suite never saw it. Fix: make the stub record the tags `build -t` / `tag` create and REFUSE to push an untagged ref, then falsify (revert the product fix, confirm the test goes red).
- **A `:latest`/extra-ref push needs the ref TAGGED in the same run.** `docker build -t <local> -t <hash>` does not tag the registry `:latest` ref; `docker push ghcr.io/<o>/<r>:latest` then fails `tag does not exist`. Build with every ref you will push (`-t latest_tag()`), or `docker tag` before pushing.
- **A `publish`-style no-op hides an unverified push.** When the hash tag was already published by an earlier run, `make publish-agent-image` returned `already published — nothing to do`, so a green dispatch PROVED nothing about the push. Re-dispatch with `force=true` (`-f force=true`) to exercise the real build+push before claiming the pipeline works.

- **A green PR that EDITS `.github/workflows/*` can fail ONLY at `auto-merge`.** The merge credential is the repo secret `FIXBOT_DISPATCH_TOKEN` (`qa-validate.yml`'s `auto-merge`: `GH_TOKEN: ${{ secrets.FIXBOT_DISPATCH_TOKEN }}`); GitHub refuses `GraphQL: refusing to allow a Personal Access Token to create or update workflow … without \`workflow\` scope (mergePullRequest)`. The PR stays OPEN + MERGEABLE with `validate`/`live-smoke` green, so it reads like anything but a credential problem — those passing does NOT mean the merge will happen. Diagnose from the FAILED job log (`gh run view <id> --log-failed --job <auto-merge-job>`), not the PR state.
  - **Don't assume the scope is permanently missing** — check history: if an EARLIER PR edited the same file and merged through the same job (`Merged PR #n … (validate + live-smoke green)`), the credential had the scope then, so it's a permission change or a transient. Try the cheap `gh run rerun <id> --failed` first, THEN the PAT fix.
  - Fix (admin/secret — the user's action): a CLASSIC PAT needs the `workflow` scope (adding it regenerates the token → `gh secret set FIXBOT_DISPATCH_TOKEN --repo <o>/<r>`); a FINE-GRAINED PAT needs Repository permissions → **Workflows: Read and write** (changeable WITHOUT re-setting the secret, so `gh secret list`'s date looks unchanged).
  - **The local `gh` keyring token often already HAS `workflow` + `write:packages`** (`gh auth status` → `Token scopes: … 'workflow', 'write:packages'`), so it can merge such a PR — but the standing rule is the agent never merges; hand the user the commands.

- **One token rarely does everything: a PAT's `workflow` scope and its `Packages: write` scope are INDEPENDENT.** A fine-grained PAT that can push a branch, dispatch a workflow AND merge a PR editing `.github/workflows/*` (the `workflow` permission) can still be refused on GHCR — `HTTP 403 permission_denied: The token provided does not match expected scopes` — if it lacks **Packages: write**. Measured on the trend repo: switching `publish-agent-image`'s GHCR login from the default `github.token` to the owner PAT (`FIXBOT_DISPATCH_TOKEN`, on the premise it could publish) broke the publish; the push probe caught it in seconds, before the build. Reverted (#249 → #251). Rule: the GHCR push gets the default `github.token` + `packages: write` (from the workflow `permissions:`); the PAT gets only push/dispatch/merge scopes — a `workflow`-capable token is NOT automatically a publishing one.
- **A fail-fast probe is what makes a credential switch safe.** Because `make agent-image-push-check` runs before the build and prints the registry's own words, the bad credential cost seconds, not a ten-minute build. After switching a publish credential, dispatch `-f force=true` — a run whose hash tag is already published is a no-op and proves nothing about the push.

- **A free-text capacity field parsed by "first number" truncates a SPLIT requirement — and the split predicate must exclude negated tokens.** `vram_min` is a free string the crawl writes as the post says, so a MoE offload row can hold `"system RAM holds the expert set (32GB GPU + system RAM)"`; reading it through a `_gb_value()` that returns the FIRST number publishes `32GB` — the GPU half of a requirement whose point is that the experts stream from RAM — which reads to a card owner as "fits a 32 GB card", the opposite of what an offload promises. A split predicate must require a GPU/VRAM word AND RAM, and must NOT match a NEGATED GPU (`"8GB RAM (no GPU)"` is a CPU statement, not a GPU half — the first draft of the fix wrongly split it into `8GB + system RAM`). Add a report-only validator line naming every prose `vram_min` so the truncation is visible, and guard the split, the plain-RAM, and the negated cases.

## Rebasing / fixing an existing conflicting PR

A PR that is `CONFLICTING` with `no checks reported` is simply behind master. Bring it current, verify, and let auto-merge land it, in this order:

- **The remote branch tip is the source of truth, not the local worktree.** A prior/parallel session can leave the worktree with a botched replay (sibling commits folded in, a modified tracked file, an empty `--amend` that appended a chore commit). `gh pr view <n> --json headRefOid` gives the verified head; `git reset --hard origin/<branch>` before rebasing onto `origin/master`.
- **rerere may resolve the file conflict yet still stop the rebase.** Output like `Staged 'Makefile' using previous resolution` means the content was merged but the commit was not made — run `git add -A && GIT_EDITOR=true git rebase --continue`. Verify BOTH sides' additions coexist in the merged file (e.g. two target sets in the Makefile) before continuing.
- **After rebasing an OpenSpec-tracked repo, regenerate the index.** The branch almost always adds a change row, so `openspec-index-check` fails `OPENSPEC.md is stale … rows exist but their data changed`. Run `make openspec-index`, then `make openspec-check` again.
- **Squash the branch to one commit** with `git reset --soft origin/master && git commit`, so the PR stays a tidy single change above master's tip.
- **Force-push `--force-with-lease`** (own PR branch after a rebase). The auto-merge job squashes again when `validate` + `live-smoke` go green, so the PR's commit count is cosmetic — but the re-push MUST make `mergeable` flip to `MERGEABLE` (it reads `UNKNOWN` right after a force-push) and re-trigger CI before it can merge.
