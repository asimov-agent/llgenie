## Pitfalls
- All scripts accept `DATE=${1:-today}` — backfill by looping missing dates.
- **trend-scanner PASS 2 hangs**: the `hermes chat --query-file ... --yolo -m local-llm` child can loop forever on "Compacting context" with no output; wrapper has no timeout. Detect: log mtime frozen >10 min while `hermes chat` child alive. Fix: `kill -9` the chat child → wrapper continues (briefing often already written; validate with `scripts/validate-trend-briefing.py <briefing>` and commit manually as `wip` if valid).
- **Kill-recovery is wrapper-specific — check the wrapper's exit handling before killing a hung child.** `kill -9` the chat child only helps when the wrapper CONTINUES on a non-zero child exit (trend-scanner: it proceeds to validate/commit whatever the child wrote). `focus-recommender` and `knowledge-consolidator` instead do `EXIT1=${PIPESTATUS[0]}; if [ $EXIT1 -ne 0 ]; then echo "Pass 1 failed, aborting"; exit; fi` — killing the child there just aborts the job with nothing written (exit 137). For those, killing is not a recovery; the job must be relaunched and may hang again on the same compaction loop. Distinguish by grepping the wrapper for `PIPESTATUS` + `aborting` before deciding.
- **Deterministic PASS 2 fallback**: `scripts/briefing-from-data.py YYYY-MM-DD` builds a validator-passing briefing straight from `08-Data-Files/trend-data-<date>.json` — no LLM, instant. Use whenever PASS 1 made the data file but the chat pass hung/skipped; always re-validate after.
- Sequential runner v2 (`/tmp/ti-run-all.sh`): wraps every step in `timeout 3600` and auto-runs briefing-from-data.py after a failed scanner step; watchdog must reference the CURRENT chain pid (re-patch after each relaunch).
- Gap audit: compare `01-Daily-Briefings/YYYY-MM-DD.md` vs `08-Data-Files/trend-data-YYYY-MM-DD.json`; a day with data but no briefing needs only PASS 2.
- **Gap-audit surface discipline**: the briefing dir mixes daily briefings with suffix-named sub-reports (`*-Watchlist-Tracker-Report`, `*-STAGING-*`, `*-Consolidation-Report`, `*-Archive-Report`). Those are NOT daily briefings — filter to bare `YYYY-MM-DD.md` when counting daily gaps, else a clean day looks missing.
- **Repo AGENTS.md was realigned 2026-10-09** (correct vault path `ai-repositories/...`, full host-crontab schedule table, PASS 1/2/3 behavior, briefing-from-data.py fallback, catch-up mode, DATE= backfill convention). Still treat this skill + live `crontab -l` as truth if AGENTS.md drifts again. ai-matrix-trends AGENTS.md/daily-scan-prompt.md were fixed same day (4 cron stages, `.py` stage scripts — the '8 stages' line was Stage 4's internal sub-steps).
- Sequential runner pattern: `/tmp/ti-run-all.sh` logs `===== START/END name rc=N =====` to `/tmp/ti-run-all.log`; run via setsid background + watch "ALL SEQUENTIAL SCRIPTS DONE".
- **Progress/monitoring of a running trend-scanner**: script lives at vault ROOT `scripts/trend-scanner.sh` (not under Projects/Trend-Intelligence/scripts/). It logs to `/tmp/trend-scanner-<date>.log`. Catch-up range = 14-day lookback printed at start (`Catch-up range: A → B`); each day prints `── Running day: <date> ──` and, on completion, auto-commits+pushes (`trend scanner: <date> — valid briefing + N notes`). To answer "how much is left": grep the log for `Running day:` markers, note the last one, and count from there to the end of the range — but days that already validate get `(skip)` after the per-day `git pull --rebase`, so they pass in minutes rather than the ~1.8 h a full re-run takes. A live child `hermes chat` process with "Initializing agent..." is normal/working, not hung.
- **Progress caveat vs backfill**: `Catch-up range` is fixed at launch and ignores commits made after start; a backfilled-but-unpushed date inside the range is still re-processed (harmless — it's just regenerated or skipped on pull).

## Confirming a cron run actually executed (audit)

Proof a job ran today = THREE independent signals, check all:
1. the job's `/tmp/<job>-cron.log` mtime is today AND its tail shows a completion banner;
2. a git commit for that day exists with the job's signature (`trend scanner: <date> — …`, `crypto daily briefing: <date>`, `Daily scan: <date>`);
3. the produced file exists and is non-empty (see pitfalls below).

- **Not scheduled ≠ not run.** A job whose cron line is day-scoped (Sun `signal-archiver`, Sat `deep-researcher`, `day-1` `crypto-rebalance`, `*/5` knowledge-consolidator) legitimately has NO log today on a non-matching day — that is healthy, not a miss. Always resolve the cron's day-of-month/DOW against today's date before flagging a missing log; this session's `crypto-rebalance`/`portfolio`/`weekly-deep-scrape`/`backup` absent logs were all correctly scheduled for other days.
- **A failing LLM child still leaves a commit + a covering log line.** `focus-recommender`, `knowledge-consolidator`, `crypto-trend-scanner` each emit "Pass N exit: 1" deep in the log even though some later stage commits a briefing. Grep the LOG for `exit: 1` / `FAILED`, not just for the presence of a commit — a committed output file can coexist with a failed upstream pass (e.g. crypto daily scanner wrote `STATUS-<date>.json = FAILED` while a later manual step committed the briefing).
  - Detect real data loss when the scanner's own `STATUS-<date>.json` says `"data_file":false` / `"briefing":false` — that means the daily JSON or briefing was never produced, so regenerate from the briefing fallback rather than trusting the later commit.

## Missing-file recovery
- **A briefing file of ~421 bytes that "validates" is an EMPTY SKELETON, not a real briefing.** The validator `validate-trend-briefing.py` checks only that the 10 mandatory section headers exist — an LLM pass that failed to produce prose yet wrote the headers passes green. After any backfill/regeneration, verify the file is substantive (a real briefing is ~40 KB; the failing one was ~421 B), or the day's `llm-wiki` and downstream passes silently read an empty doc.
- Deleted briefings are recoverable from git history, not lost: `git log --oneline -- <briefing>` shows the delete commit (often a later-day's scanner run that re-processed the range and failed validation), then `git restore --source=<sha>^ <briefing>` or regenerate deterministically from the surviving `08-Data-Files/trend-data-<date>.json` via `scripts/briefing-from-data.py <date>`. Prefer regeneration when the old file was an early/partial format.
- **`day_done()` contract (the skip-gate) — check it BEFORE blaming a range re-run.** A day counts as DONE only if its briefing file exists AND passes the validator. A `VALIDATION_FAILED` / `FAILED` STATUS marker does NOT count as done — that day must be retried, or a transient failure poisons it forever. If `day_done()` is missing (log fills with `bash: day_done: command not found`) every day looks like a gap and the catch-up loop re-runs the full 14-day range every morning, deleting previously-valid briefings when a regen then fails validation. That is the signature of a broken skip-gate; check whether a maintenance edit removed the helper.
- **`day_done()` must gate on ALL artifacts that job owns, not just the first one written.** `crypto-trend-scanner` keys on the briefing file, but the briefing is written by a SEPARATE `crypto-daily-briefing` step while the SCANNER owns `crypto-trend-data-<date>.json` (consumed by daily-briefing + macro). Keying only on the briefing means a day whose data JSON failed gets skipped as "done" and the missing file is stranded forever. Gate on briefing AND data JSON. Each wrapper's `day_done()` should require every file the later stages read.
- **Fix = back up before regen, never blind `rm -f`.** The scanner used to `rm -f "$BRIEFING"` before PASS 2, so a failed regeneration destroyed the previous valid briefing. Correct pattern: `cp` the existing briefing to a `.bak` before removing it, and on a FAILED/INVALID pass restore the newest backup (guard with a trap so it runs on every return path).
- **The validator's content guard is the fix for the empty-skeleton bug.** `validate-trend-briefing.py` originally passed on section headers alone, so a 421-byte header-only skeleton validated green. It now rejects a body < 1500 chars (after frontmatter) and flags near-empty sections. When auditing a briefing, do not trust "VALID" on a tiny file — a real briefing is tens of KB, an empty skeleton is a few hundred bytes.
- **Re-running a cron LLM job from the agent: launch with `background=true`, NOT foreground.** A foreground terminal call with a tool timeout (420 s max) kills the `hermes chat` child mid-run — often at "Compacting context", leaving the job's files stale (e.g. focus lists still dated 10-05). Relaunch via `terminal(command=..., background=true, notify=[completion patterns])` and poll the log; the tool-timeout kill never fires on the script's own `>` redirect to the log.
- **Clean up stale markers + regen backups in the same recovery commit.** After regenerating a deleted/empty briefing from `briefing-from-data.py`, delete the day's `STATUS-<date>.json` VALIDATION_FAILED marker and any `*.regen-*.bak` leftovers, or the next audit sees the day as still-failed / the tree as dirty.
- **Run audits/restores in the ONE clone, and leave the working tree clean.** An unstaged edit (`_index.md`, a leftover briefing) makes a subsequent cron `git pull --rebase` fail with `cannot pull with rebase: You have unstaged changes` — the job then grinds through its range while never syncing, committing deletions from a stale tree. After a recovery commit, `git status` must be clean before the next scheduled run.
- **llm-wiki backfill: a run that underproduces still touches `.llm-wiki-done-<date>`, so a re-run skips every day as "already done".** The `llm-wiki-update.sh` LLM sub-step is unreliable — it can finish a day having written NO query notes (only `_index.md` or nothing at all) yet still `touch .llm-wiki-done-<date>` at the end. The next backfill then prints `already done for <date>, cleaning up stale pending` and does nothing. Before re-running a backfill, delete the stale `.llm-wiki-done-<date>` markers for the target days (and re-create `.llm-wiki-pending-<date>` if the previous run cleaned them) — otherwise the re-run is a no-op. Verify by counting `queries/<date>-*.md` after, not by trusting the "completed" log line.
- **`pkill -f '<script>.sh'` can match and SIGKILL the invoking shell itself.** When killing a hung background job, a `pkill -f 'focus-recommender.sh'` pattern also matches the very command line running the pkill (it contains the same string), so the cleanup command dies with SIGKILL before reporting. Kill by explicit PID (`pgrep -af` first, then `kill -9 <pid>`) or use a pattern that cannot match the current shell, and re-verify with a fresh `pgrep` in a separate call.
