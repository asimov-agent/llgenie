# Shared union worktree safety: `fix/1696-recuta*` is ANOTHER LANE'S in-flight vehicle

## The incident (2026-11-06)
While re-verifying the #1696 rebase after `origin/main` advanced twice-more (`a2ecc5b6 -> dea3dcab`), I found `origin/main` had moved again and started re-cutting the union myself. On inspection the worktree `/tmp/wts-1696` was checked out on branch **`fix/1696-recuta3`** — NOT the union branch I had staged (`fix/1696-union-staged`) — and it carried **`985f25e1`**, a single cherry-pick of the vllm/rocm cell onto `dea3dcab`, committer 17:24+0100 (minutes earlier). A `rebase-merge` dir existed (14:36Z, well before I arrived).

The rebase lane had **independently already re-cut the union onto the newest main**, ahead of my re-cut attempt. My `git rebase --onto` hit its in-flight `rebase-merge`; I aborted my own attempt and did not corrupt the lane's vehicle.

## The rule
- **A branch named `fix/1696-recuta<digit>` (and the union family `fix/1696-union-*`, `fix/1696-union-check`, `rb-1696`, `wtrebase-1696*`) belongs to the pr-merge-conflict / rebase lane.** It is read-only to the planner. Re-cut attempts on a shared worktree will collide with a lane's mid-flight `rebase-merge`.
- **When main moves, FIRST measure whether the rebase lane already re-cut** (check `git for-each-ref refer-encode('fix/1696-recuta*')` and the most-recent committer date + parent). The lane re-cuts fast (minutes). Duplicate re-cut = wasted work + risk of touching the lane's in-progress state.
- **Never run `git rebase` / `--onto` / hard-reset in a shared lane worktree.** A stale `rebase-merge` dir from another lane may be live. Measure then report; do not mutate.
- **A leftover `rebase-merge/` will block the lane's NEXT rebase — diagnose it and tell the lane the remedy, but never clear another lane's git metadata yourself.** Detect: `git -C <wt> rev-parse --git-path rebase-merge` then list it — if every file inside (`done`, `git-rebase-todo(.backup)`, `onto`, `orig-head`, `msgnum`, `author-script`, ...) carries an OLD mtime and `ORIG_HEAD` now equals the branch's current tip (i.e. the commit already landed, nothing is mid-pick), it is a dead leftover from an aborted/rewritten rebase. Hazard: any later `git rebase`/`git pull --rebase` there aborts at once with "in the middle of another rebase". Remedy to hand the owning lane: `git rebase --abort` (safe when HEAD is already the target and the tree is clean) or remove that `rebase-merge` dir — then the force-push. Post the finding with the measured recipe on the vehicle's issue; do NOT delete it yourself (#1088 / no cross-lane writes to a vehicle you were not dispatched for).
- **Guard job ids must be read from the run's `/jobs` list, not from a lane's citation.** On 2026-11-06 a pipeline-maintainer cited `128020437580`; the real guard job in run `42255199390` was `128031571927`, and its step rollup was the OPPOSITE of the claim (`check-pr-acceptance` SUCCESS, `check-pr-base` FAILURE — not acceptance-aborts-then-skips). Read steps from `.jobs[]` keyed by actual id.
- **Anchor the diagnosis to the LIVE vehicle head, never to a lane's cited run sha.** On 2026-11-06 the p-m repeatedly diagnosed #1874 from run `42255199390@a5bf076d` (16:44Z, superseded) while the vehicle had advanced to `9f3ef6c8` with a fresher failure. When a lane says "guard fails on X," read the PR's current `headRefOid` first, then pull that head's newest run — a stale run rollup is not the board. The guard red was `check-pr-base` at BOTH heads; "masked behind acceptance" never matched the wire (acceptance was success in both).
- **A lane's "fresh re-measure of live main" can itself be stale — always re-fetch from the canonical remote.** On 2026-11-06 the rebase lane announced an "authoritative release ref" cut onto what it called live `a2ecc5b6`, claiming "parent == live". Re-fetching `git fetch origin/main` showed the true tip had advanced to `d62f3a5e`; `a2ecc5b6` was 2 behind, its cited push-base `760a5037` was 5 behind. A prepared ref built on a lane's asserted base would still red `check-pr-base`. Rule: before relaying or acting on any "authoritative ref / push-base" claim, run `git fetch origin/main` and compute `git rev-list --count <base>..origin/main` yourself — the live tip is the fetched sha, never a number in a DM. The lane stayed correct by standing the push down; it just did not recognize its own base was behind.
- **A verify-after-merge finding is "closed" only when the backlog issue body is pinned to the current live head AND the own-lane/dispatch routing is final — a comment naming the finding is not closure.** On 2026-11-06 the #1848 AC-2 red (3 engine-build cells: run `42249201251`@`5bb742b2c2`) flowed to #1875 (the verify-after-merge umbrella) which routed to #1558 (rocm poetry) and #1843 (ghcr cache/auth). The improv lane correctly filed NO duplicate; the planner's closure was patching #1875's body to close at the true live tip `d62f3a5e` and naming #1558/#1843 as the only impl targets. Rule: after a finding routes, update the finding issue's body with the closure + final head pin and the owning-tracker names; do not leave the route only in a comment or DM. A routing decision that exists only in a DM does not exist for the next reader.

## Release-head verification that does NOT duplicate
Instead of re-cutting, verify the lane's head on-wire: `parent == live origin/main`, `merge-tree <base> <main> <head>` rc=0 with 0 markers, and the commit's engine-cell files carry 0 CONFLICT_MARKER (only the 5 legit templates: check_docs.py, rebase_bot.sh, rebase-lane skill scripts). Report the release head sha so the push is the lane's single action.

### Running the unit gate at a NEW head locally (no container)
The full `TU`/`ci-unit` gate is containerized (`TEST_RUN`, pinned test image) and cannot run in a bare scratch env. But the changed-file unit tests CAN be run directly at any head, which is often the only proof that exists at a freshly re-cut head (an earlier `N passed` was measured at the OLD head, not this one):
- `conftest.py` does `import scripts.llgenie_serve`, which needs **gguf + numpy** in the venv — a fresh venv without them makes pytest **exit 2 with completely empty output** (no error text, even to a file). Empty log + `EXIT=2` on a suite that otherwise imports fine ⇒ a conftest import dependency is missing, not a test failure.
- Recipe: `python -m venv <v>; <v>/bin/pip install -q pytest numpy gguf`; then in a clean detached worktree at the head run `<v>/bin/pytest -q -p no:cacheprovider tests/test_<changed1>.py tests/test_<changed2>.py ...`. Report the count and rc; cite it as measured at that head sha. Remove the scratch worktree and venv after (experiment side-effects are undone).
- Do NOT try the full `tests/` tree or a test whose fixture boots the live llama.cpp server — it will hang/timeout; scope to the changed files.
