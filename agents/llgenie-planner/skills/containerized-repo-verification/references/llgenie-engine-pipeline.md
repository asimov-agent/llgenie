# llgenie: how a registry engine becomes a built, published image

The ordered chain, and which component owns each step. Use it to answer "what does what, in what order"
without re-deriving it from the call graph.

| # | step | owner | gate that covers it |
|---|---|---|---|
| 1 | engine appears upstream -> `data/models.json`, `data/engine-skill-gap.json`, trend-list matrix regenerated | `.github/workflows/registry-sync.yml` (`make sync-registry`, `sync-quant-catalog`, `render-trend-list-matrix`, `render-engine-skill-gap`) | `make check-registry`, `check-quant-catalog`, `check-trend-list-matrix` |
| 2 | one tracking issue per new engine, labelled `agent:implement` and read back | `make spawn-engine-skill-issues` (`scripts/engine_skill_gap.py`) | `make check-engine-skill-gap` (ci-unit) — an engine with no skill and no dated decision in `data/unsupported-engines.json` reds it |
| 3 | the skill file is scaffolded before the agent starts | `issue-bot.yml` -> `make issue-bot-dispatch` -> `scripts/issue_implementer.engine_scaffold_line` -> `make engine-skill-scaffold ENGINE=<registry name>` | scaffold leaves every unprovable key EMPTY on purpose |
| 4 | the agent fills `pin`/`install`/`launch` and commits | the implement leg | `make skills-validate` (ci-unit) |
| 5 | params + binaries manifest + one Dockerfile per arch | `make generate-engine-params` (`scripts/engine_skills.py params`) | `make check-engine-params` — committed files must equal generated bytes |
| 6 | the params are cells the matrix will actually BUILD | `scripts/engine_coverage.py` | `make check-engine-coverage` (ci-unit, after `check-engine-params`) — a cell in `engine_image.DISABLED`, a variant outside `CI_VARIANTS`, or no `linux` in `os` is red unless recorded |
| 7 | build -> probe -> publish | `ci.yml` `engine-image-*` (`make list-engine-images CI=1`, `build-engine`, `test-engine-stage`, `push-engine`) | post-build test before publish |
| 8 | pull back from the registry, digest + version + real "hi", then install | `engine-published-test` / `install-published` (`make test-published-engine`, `engine-launchers`, `test-built-engine`) | the published-image job |

## Facts that cost time to rediscover

- `engine-bump` does NOT create skills. It only re-pins engines that already have `SKILL.md`
  (`engine-bump-plan` -> `engine-bump` -> `generate-engine-params`). The new-engine path is
  registry-sync + issue-bot, steps 1-4 above.
- `ENGINE_IMAGE.DISABLED` drops a cell from the CI matrix silently; `CI_VARIANTS` is `cpu, cuda, rocm,
  vulkan`, so a `metal`-only or `darwin`-only engine has no image by design.
- `servable: via` (rides another engine's server) and `servable: false` (a drafter, a browser runtime) are
  deliberately not images — a coverage gate must give them a `not-an-image` state, not an exception.
- The scaffold writes `os: [linux]` unconditionally, so a macOS/Metal-only engine starts life with a
  false Linux claim; decide the `os:` from the registry `backends` before trusting the generated gates.
- `make engine-skill-gap` prints `shipped N (M with no image)` — that count is the quickest census of
  engines the pipeline does not build.
