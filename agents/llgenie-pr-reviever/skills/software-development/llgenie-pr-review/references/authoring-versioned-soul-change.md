# Implementing a behaviour-gap issue against your own SOUL/skill

A continuous-improvement issue that says "your SOUL/skill has no encoding of <duty>" is this lane's own domain: implement it and open the versioned PR yourself (#791/#1062). Do NOT wait to be handed a PR — the issue is the dispatch.

## Before editing

- **Grep BOTH the live skill and the tree SOUL.** The *procedure* for the duty often already lives in the skill (e.g. the empty-queue audit steps); the real gap is that the always-on SOUL lacks the *duty* itself. When that is the case the fix is **SOUL-only**: encode the standing duty in `agents/<profile>/SOUL.md`, point at the skill for the procedure, and do not duplicate the procedure into SOUL or edit the skill.
- **Record the gap as a command before you edit.** Run `grep -icE '<duty terms>' agents/<profile>/SOUL.md` at the fresh-main sha and quote the count (e.g. `→ 0`) as the acceptance baseline; re-run it after. A duty you cannot show was absent is not one you can show you closed.

## Opening the PR

- Branch from freshly fetched live main (`git fetch origin refs/heads/main:refs/remotes/live/main`, verify against the commits API), never a stale ref.
- The change carries the same #1123 note pair (`docs/changes.d` fragment + `agent-wiki` note) and `make changes-index` re-render and AGENTS:/BASE: body-gate lines as any other change, **even though it touches no code** — `make check-docs` enforces the note pair, so a doc/SOUL-only PR is never gate-free.
- Measure the AGENTS: byte/line counts from `AGENTS.md` at the main sha (`git show <main>:AGENTS.md | wc -c` / `wc -l`), not the PR head.
- Commit with the allowlisted author pair already in the worktree's git config; open **ready-for-review**, never draft; report the PR number + sha back to the planner.

## Lane vehicle PRs (a pointer/procedure rollout dispatched to every lane)

A dispatch that says "land this procedure pointer in your own lane" produces a **lane vehicle**: a small
PR touching only `agents/<profile>/` plus the repo's change-note machinery. The shape below is what makes
one green on the first run instead of re-redding gate by gate.

- **Scope stays inside your lane.** `agents/<profile>/` files, the change-note pair, and (only when the
  gate demands it, below) one `openspec/changes/<slug>/` dir. Touching another lane's `agents/` tree is
  the #791 violation the whole exercise exists to prevent.
- **An `agents/`-touching diff is NOT docs-only, so `check-pr-openspec-change` reds without an openspec
  change dir.** The gate's `_is_docs_only` exempts `CHANGES.md`, `README.md`, `docs/`, `agent-wiki/` —
  never `agents/`. A skill+note-only vehicle therefore reds exactly like a code change would. Add
  `openspec/changes/<slug>/` (model the dir on an existing *behaviour*-shaped change; a data-reference
  change carrying only `.openspec.yaml` is not that shape) and confirm rc=0 before opening.
- **The change-note fragment is exactly ONE line.** `docs/changes.d/<slug>.md` holds the single
  `CHANGES.md` row, with the literal placeholder `[note]` as the link text; a multi-line fragment renders
a broken row. `CHANGES.md` is **generated by `make changes-index` — never hand-edit it**; write the
  fragment, run the renderer, then confirm your row appears.
- **The `SYNC:` line is mandatory** for every touched `agents/<profile>/` path (see
  `body-gate-agents-base.md`); add it in the same pass as `AGENTS:`/`BASE:` so the body does not re-red.
- **The AGENTS gate validates sha ancestry and BASE equality only** — `check_pr_hygiene` does not check
  the byte/line counts. Compute them from `AGENTS.md` at the main sha anyway (`make bot-preflight`
  prints the line): a green `check-pr-agents-line` step is no evidence the counts are honest.
- **Run the whole local set with explicit rc echoes before opening** — `git-identity`, `check-pr-agents-line`,
  `check-pr-sync-line`, `check-pr-openspec-change`, `check-docs`, `lint`, `check-agent-skills`. A piped
  command reports the last leg's status; echo each rc instead of trusting a chained run.
- **Bookend the tracking issue.** On opening, comment the head sha **and** the run ids the head produced;
  a vehicle comment without a sha is a claim about time. And the acceptance tick on your own vehicle is
  a **different lane's** review (#1644) — never tick it yourself, never approve it, never merge it.

## Editing the skill file itself (patch-tool mechanics)

- **Never copy `read_file`'s `NNN|` line-number prefix into a `patch` `new_string`/`old_string`.** `read_file` renders each line as `948|content`; the `N` is a display annotation, not file content. The `patch` tool's fuzzy matcher can accept a string that still carries `948|` and then writes the literal `948|` into the file — corrupting the line with a duplicated prefix (`948|948|- **…`). When basing an edit on a paginated read, strip the leading `\d+\|` from every line you quote. After any patch, verify: `grep -cE '^[0-9]+\|' <file>` must return `0`; if it is nonzero, strip with `perl -pi -e 's/^\d+\|- /- /' <file>` and re-read to confirm clean bullets.
- **`SKILL.md` is at/near the 100,000-char ceiling** — a substantial new section is rejected outright. Add always-on one-line rules sparingly and route depth to `references/`; before a large edit, prefer the topical reference over the main file.

## Keep SKILL.md small

This skill's `SKILL.md` sits at the 100,000-char ceiling — a substantial new section is rejected outright. Put workflow depth in `references/<topic>.md` and add only a one-line pointer to `SKILL.md`; flag bloat for consolidation rather than forcing an oversized edit.
