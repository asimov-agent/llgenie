## When to Use
Use when a pull request in `asimov-agent/llgenie` shows `mergeable: CONFLICTING` / `mergeStateStatus: DIRTY` or `BEHIND`, and it must be brought onto the current `main` tip while staying a single reviewable commit.

Use when a pull request in `asimov-agent/llgenie` shows `mergeable: CONFLICTING` / `mergeStateStatus: DIRTY` — a genuine merge conflict — and it must be brought onto the current `main` tip while staying a single reviewable commit. **Rebase ONLY on a genuine conflict.** The owner's ruling: do not sweep-rebase every open PR when main moves; a PR that reads `MERGEABLE` or `BEHIND` (behind main but not conflicting) is not a rebase target — leave it until main's advance actually re-dirties it. A surgical pass that touches only the truly-conflicting subset is correct; a broad pass that re-bases the non-conflicting board is the failure shape.

Repo: `asimov-agent/llgenie`. Two checkouts matter: the owner's clone (never edit it, never `git switch` it) and your own worktree root beside it (`../llgenie-wt/<n>`).

- **The PR-rebase lane (`llgenie-pr-merge-conflict`) must always communicate with the other llgenie bots before rebasing an ongoing PR.** Concretely, BEFORE touching a branch with a live claim, an open PR, or a `bot-claim:` comment: message the owning lane with the id, the head sha you measured, and what you are about to do; then post the conclusion on the PR, because a decision that exists only in a DM does not exist for the next reader. A rebase another lane has to resolve by hand is the failure. *cite #994*
- **All lanes must keep their ongoing PR rebased onto the latest fetched `asimov-agent/llgenie` `main`.** Fetch fresh (`git fetch upstream main`; `asimov-agent/llgenie` is the canonical remote, a fork named `origin` is not upstream) and rebase at the sha fetched in that same moment — never a sha quoted in a message, which is stale by the time you read it. Do not rebase through a live run at the head (cancel-in-progress makes an authorised rebase destructive). *cite #994*

- **Rule 3 (owner 2026-10-29): before starting ANY new issue/PR work, every lane must fetch and rebase its worktree onto the latest fetched `asimov-agent/llgenie` `main`, then report to the planner ("llgenie inbox triage" — me), so the planner can relay the assignment across the fleet (and no two bots pick one issue).** *cite #994*
- **Rebase only when the PR is actually `CONFLICTING` (owner rule #1015, supersedes #994's rebase-every-move clause).** Do NOT rebase a PR on every `main` move — main advancing under a `MERGEABLE`/`BLOCKED` PR is fine until a merge actually needs a rebase. The sweep is the **genuinely-`CONFLICTING` set only**, measured fresh (`mergeable=="CONFLICTING"`, never `mergeStateStatus` alone). Leave `MERGEABLE`/`BLOCKED` PRs alone — that includes a dirty-watch narrowing to conflicts, not enumerating all open PRs. Fetch is still mandatory before any work (explicit refspec `+refs/heads/main:refs/remotes/origin/main`, because a local `refs/heads/origin/main` shadows the remote ref) but fetch ⇒ pull-to-friendly; a `git pull`'s own rebase only fires on a real conflict. A PR whose base merges and then conflicts is rebased then, not preemptively. If a PR is another lane's vehicle (`bot-claim:`, test-led body), never force-push it — report it to that lane, do not rewrite it. *cite #1015*

## 1. Survey

**Arm auto-merge when the work is done — "done" triggers the arm, not "approved".** After the last push of a rebase or conflict resolution, run `gh pr merge <n> --auto --squash` (or the repo's configured strategy) and report the **arm time** in the same comment as the base/head pair. A rebased PR left unarmed is a rebase nobody merges. The only exception is a PR the owner explicitly forbade — write `auto=none (owner instruction)` and say where that instruction lives. If the repo has auto-merge disabled or the branch protection rejects it, say so plainly instead of claiming an arm that did not happen.

**An armed PR is not a protected one — a sibling merge re-dirties it and the arm fires nothing while it stays dirty.** A PR you finished and armed can read `CONFLICTING` minutes later simply because another PR merged and added an index row; re-rebase it through the same gate→lease-push path and then re-read `autoMergeRequest`, because the arm you set is still attached but inert until the branch is mergeable again. Verify the arm actually took (`gh pr view <n> --json autoMergeRequest` → non-null) rather than trusting `gh pr merge --auto`'s exit code.

**Start from a fresh upstream main, and bookend the work with two comments.** Before you create a worktree, branch or first edit: `git fetch` the canonical remote (`asimov-agent/llgenie`, whose remote is named `origin` in the canonical clone — a fork remote is not upstream) and branch from `origin/main` **at the sha you fetched in that moment**. Never from a branch you already had, and never from a sha quoted in a chat message: it is stale by the time you read it. Write that sha into your first comment. Then **bookend**: one comment when you start (issue/PR id, branch, the main sha, what "done" means) and one when you finish (head sha per PR, what changed, the run id or command that proves it, anything left open). **Report the same two lines to the planner.** A start comment with no finish comment is an abandoned claim; a finish comment with no start comment has no baseline.

**Publish the sweep before you touch anything.** A sweep rewrites branches other lanes are actively pushing, so it is legitimate only if the list goes out first: **one comment per sweep on #864** naming `base sha · PR# · branch · head before → after`, posted before the first push. If a lane answers "I am mid-push on that branch", skip it and say so in the same thread rather than winning the race. A rebase that is not announced is indistinguishable from a lane losing its work — and a `--force-with-lease` rejection is that lane answering you, so re-fetch, re-read the thread, and stop. That board thread is an **issue**, not a PR: use `gh issue comment 864 --body-file …` — `gh pr comment` answers `Could not resolve to a PullRequest` and posts nothing.
```bash
gh pr list --repo asimov-agent/llgenie --state open --limit 100 \
  --json number,title,headRefName,baseRefName,isDraft,mergeable,mergeStateStatus
```
`mergeable: CONFLICTING` / `mergeStateStatus: DIRTY` are the ones to rebase. `MERGEABLE` + `BLOCKED` means waiting on checks/approval — do not rebase those.

**Count conflicts with the subcommand's own text: `git merge-tree --write-tree --messages` emits `CONFLICT (content):` / `CONFLICT (add/add):` — never `CONFLICT (merge):`.** Measured: `grep -cE 'CONFLICT \(merge\):'` returned 0 for twelve PRs, two of them genuinely conflicting, which nearly produced a false "0 conflicts on the board" report. Count `grep -cE '^CONFLICT'` AND confirm with the exit code (`git merge-tree --write-tree <base> <head> >/dev/null 2>&1 && echo CLEAN || echo CONFLICT`): a grep that matches nothing is indistinguishable from a clean merge, the exit code is not.

**Never grep the merge-tree MESSAGE stream for a path — it prints AUTO-MERGE notices as well as `CONFLICT` lines, so a filename grep manufactures conflicts that do not exist.** Measured: `git merge-tree --write-tree --messages <main> <head> | grep ARCHITECTURE.md` reported a census conflict on a PR whose only mention was the line `Auto-merging docs/ARCHITECTURE.md` — a clean merge; the PR had zero conflicts. This is the lane's worst false positive because a dispatch often predicts "the conflict will be in docs/ARCHITECTURE.md's census block", so a path grep appears to confirm the prediction. Use `grep -cE '^CONFLICT'` or the exit code only.

**A coordinator's rebase dispatch can be HOURS stale — a PR it calls `DIRTY` may have merged and shipped.** Measured: a dispatch ordered "#919 is DIRTY, rebase onto main `cdb211ba`" and warned the armed PR would "merge on green, so a wrong census resolution lands on main"; `gh api pulls/919 --jq .state,.merged,.merged_at` showed **closed / merged `20:51:19Z` as `d3d9dd28`**, current main was `d5fb875c`, and the cited base `cdb211ba` was 3 h old. Answer with the measured PR state + current main sha + the board's real conflict set — but do NOT stop at "stale": check the SUBSTANCE the dispatch was protecting (here, whether any open PR conflicts on that census doc), because stale wording does not make the concern wrong.

**Measure `isDraft` and report every draft instead of rebasing it silently.** A draft is invisible to auto-merge, to the merge queue and to a reviewer scanning for work, so a rebase performed on one produces a clean branch nobody will ever land. Report it and let its owner flip it with `gh pr ready`; never mark another lane's PR ready yourself. Never open a draft PR of your own either — open ready-for-review and flip it before reporting if it somehow opened as draft.

A conflicting PR reports **no checks at all** ("no checks reported on the … branch") because GitHub builds no merge ref. That is the symptom, not a broken workflow.

If this procedure is scheduled, gate it on a deterministic detector whose whole output is the conflicting subset: an unchanged hour then produces no agent run and no delivery, and "alert only on a transition" is enforced by construction rather than by prompt discipline. Two properties are not optional — the detector must report a hard error (never "nothing conflicting") when the GitHub read itself fails, or the watch has a silent blind spot; and a direct/forced run bypasses the gate, so only a scheduled tick proves suppression.

For how to describe a PR board so every sentence is true at the moment it is printed — the four check conclusions, bot-green vs owner-ready vs stuck-cancelled, and what a watch's silence means — see `references/pr-fleet-monitoring.md`.

## 2. Worktree (never the owner checkout)
```bash
cd <owner-clone>  # the checkout you were told never to edit
git fetch origin main
git fetch origin '<head-branch>:refs/remotes/origin/<head-branch>'
git worktree add -b pr<N>-rebase ../llgenie-wt/pr<N> origin/<head-branch>
```
Branches of agent PRs live in **either** the base repo or the `andyholst` fork, and which one is per-PR: `gh pr view <n> --json isCrossRepository` decides. Fetch that head from **its own** remote and push it back to the **same** remote; the base is always `origin/main` (the upstream sha) whatever the head's remote is. Never push a fork head to `origin`, never an upstream head to the fork — and never assume the two `main` refs agree, because the fork's `main` is a different commit that moves on its own schedule. Confirm the clone before fetching (`git remote -v`, `git ls-remote <remote> refs/heads/main`); there can be more than one checkout of this repo on a host, each naming the upstream differently (`origin` in one, `upstream` in another).

**Give `git worktree add` an ABSOLUTE path, or the worktree lands wherever the shell's cwd is — possibly INSIDE the clone, not beside it.** A relative target like `llgenie-wt/rb841-sweep` from a `cd` into the wrong parent resolves against that cwd and produces `…/llgenie/llgenie-wt/…` (a nested tree the owner's clone-prune and every path-relative command then miss). Always `git worktree add -B <branch> /home/asimov/repository/git/llgenie-wt/rb<N> <sha>` (absolute), and after adding, verify with `git rev-parse --show-toplevel` inside it that the toplevel is the intended sibling — a worktree whose toplevel is the clone itself is the misplacement, and a second `cd` at the wrong level is how a `git -C …` command then reports `fatal: not a git repository`.

## 3. Rebase
```bash
cd ../llgenie-wt/pr<N> && git rebase origin/main
```
Read `AGENTS.md` at the target main sha before the first edit.

### Check the PR's BASE before you pick the target
`origin/main` is the right target only when the PR's base **is** `main`. Read it per PR (`gh pr view <n> --json baseRefName`); a stack of PRs based on another feature branch reads `CONFLICTING` against `main` forever while nothing is wrong with it, and rebasing it onto `main` rewrites somebody's dependent chain. Recurring shape in this repo: a dozen PRs whose `base` is one long-lived agent-profile branch. For those the base is **that branch's current tip**, and the frozen base sha moves under them — a `/tmp` note or the PR body quoting the old base is stale.

**`git rebase --onto <new-base-tip> <old-base>` re-applies the base's own commits and conflicts every time**, because a stacked branch *contains* its base's history: the updatable range includes commits the new base already has. Replay only the branch's own work instead:
```bash
git fetch origin '<base>:refs/remotes/origin/<base>' '<head>:refs/remotes/origin/<head>'
cd ../llgenie-wt/pr<N> && git checkout -B pr<N>-rebase origin/<head>
git cherry -v origin/<base> HEAD      # '+' rows are this PR's own; '-' rows are already in the base
# then: git checkout -B pr<N>-rebase origin/<base>  and cherry-pick the '+' shas in order
git checkout origin/main -- CHANGES.md && make changes-index && git add -A
git commit -C <replay tip>            # keeps author and message
git diff --stat origin/<base>..HEAD   # must be ONLY this PR's files
```
`git cherry` is the instrument because it compares patch-ids: a rebase of the stack would replay the base's commits, and a `--onto` whose upstream is anything but the branch's own merge-base replays them too. Measured on a stack whose branch held 2 unique commits among 30: the replay is two cherry-picks, and the other 28 are the base's.

**A `--onto` re-seat that lands at `head == base` (0 commits ahead) is NOT proof the branch is a duplicate — only a `git cherry` against the RIGHT base proves it.** A stacked child's upstream is the OLD parent head it was stacked on, not a fixed base: when the parent PR is itself rebased (its head moves `X → Y`), re-seat the child with `git rebase --onto Y X`, where `X` is the parent head the child was built on — using a wrong/older upstream, or plain `git rebase Y`, replays the parent's own history as "already applied" and can silently empty a branch that still has real unique commits. Measured: a child showed `git cherry <new-base> <branch-tip> | grep -c '^+'` = 5 unique commits, yet a blind `--onto <newbase> <wrong-old>` resolved it EMPTY (`ahead=0`) — the unique work dropped as if already present. Before declaring any empty re-seat a duplicate vehicle, run `git cherry <target-base> <branch-tip>` and require `0` `+` rows; if there are `+` rows the upstream was wrong — redo using the branch's true merge-base (`git merge-base <target-base> <branch-tip>`) as the `--onto` upstream.

## 4. Resolve — know the two habitual conflicts
- **`CHANGES.md`** is an index table, newest first. Two branches almost always add a new top row at the same position. Resolution is **keep both rows** — main's existing row stays where main has it, the branch's new row goes directly under it. Never drop either row: `make check-docs` fails on a note with no row *and* a row with no note. Same-date rows may sit in either order.
- **Newer trees generate that table** (`docs/changes.d/` + `make changes-index`, issue #934). There, the correct resolution is different and simpler: take `origin/main`'s `CHANGES.md` **wholesale** (it is generated), and add the branch's row as `docs/changes.d/<date>-<note>.md` — then `make changes-index` rewrites the table. Re-inserting a row by hand into a generated file fails `check-docs` with `[changes-index] ERROR: … is not indexed — add docs/changes.d/…`. Check which mechanism the tree uses before resolving: `ls docs/changes.d | head -1` decides it.
- **A stacked PR is replayed, never rebased** — `git cherry origin/<base> origin/<pr> | grep '^+'` then cherry-pick only those shas onto the current base tip. Three failure modes, all seen: an **empty cherry-pick** ("nothing to commit") means that commit is already patch-equivalent — `--skip` it, and never replay the index-rebuild commit before the real fix or the branch ends up empty; **`CHANGES.md` conflicts on every replay** — `git checkout origin/<base> -- CHANGES.md` then `make changes-index` then amend; **JSON/YAML unions leave conflict markers inside the file** — after any such union run `git grep -lE '^(<<<<<<<|>>>>>>>)' -- .` and it must print nothing, because a tree with markers in a data file can still pass `check-docs`.
- **A stacked PR is replayed, never rebased** — `git cherry origin/<base> origin/<pr> | grep '^+'` then cherry-pick only those shas onto the current base tip. Four failure modes, all seen: an **empty cherry-pick** ("nothing to commit") means that commit is already patch-equivalent — `--skip` it, and never replay the index-rebuild commit before the real fix or the branch ends up empty; **`CHANGES.md` conflicts on every replay** — `git checkout origin/<base> -- CHANGES.md` then `make changes-index` then amend; **Conflict markers can survive a rebase that reports success — grep after EVERY rebase/replay, not only after an explicit union.** A marker inside a generated file (one carrying a `_generated_by:` header) is committed by `--continue` while git prints `Successfully rebased`; `git status` and `check-docs` stay green and the marker surfaces only as a downstream `JSONDecodeError` test red. Run `git grep -lE '^(<<<<<<<|>>>>>>>)' -- .` after every rebase/replay — it must print nothing — and when a failing test names a generated file, look for markers BEFORE blaming the branch. `git checkout --theirs` does NOT reliably clear such a marker (it can re-stage the same marked side): regenerate the file with the command its `_generated_by:` header names, then amend; **a NON-empty cherry-pick can still regress** — a replayed commit that re-derives a file whose canonical newer form is already on the base tip applies cleanly yet silently undoes the newer content (measured: re-applying an old "SOUL carries the canonical fleet block" commit onto a base that already carried the new verbatim block deleted rule 16, reddening the very agent-profile gates the branch is about). Always run the branch-relevant gates after a stacked replay; a red in the territory the branch itself works is the signal to check whether one replayed commit is an older generation that regressed the base — drop it (keep the base's newer file) rather than hand-reconcile it, because its intent is already satisfied by the base.
- **The acceptance pair for a docs-touching branch is measured, not felt**: `git ls-tree -r --name-only HEAD agent-wiki/ | grep -c '\.md$'` must equal the row count in `CHANGES.md`. A branch at 222/222 while `main` is at 223/223 fails the same four index assertions as a dozen other PRs — a shared base, not a dozen mistakes, and `make changes-index` is the remedy, never an edit to the diff. When it conflicts across many PRs in one sweep, do not hand-merge hunks: take `origin/main`'s file wholesale, re-insert the branch's added rows under the header separator, and let `make check-docs` referee (`references/sweep-mechanics.md` §4 has the loop).
- **`rerere` is ON in this repo and its cache is shared across worktrees, so `git rebase` can auto-resolve `CHANGES.md` with ANOTHER lane's row.** The rebase prints `CONFLICT (content): Merge conflict in CHANGES.md` then `Staged 'CHANGES.md' using previous resolution.` and leaves no `UU` entries, so `git status` looks solved — while the staged row is a different branch's change record (columns swapped, prose belonging to a different PR). Always diff the resolved file against `origin/main` (`git diff origin/main -- CHANGES.md`) and against the branch's own commit (`git show <sha> -- CHANGES.md`) before `rebase --continue`; replace the row with the branch's verbatim row rather than accepting git's staged version. `make check-docs` does NOT catch it — the wrong row names a note that does exist, so the index gate stays green.
- Engine/docs registries (`README.md`, `docs/ARCHITECTURE.md`) resolve toward **main's** version; do not invent a third behaviour inside a rebase.
- Engine/docs registries (`README.md`, `docs/ARCHITECTURE.md`) resolve toward **main's** version; do not invent a third behaviour inside a rebase — **EXCEPT when two sibling PRs each made an ADDITIVE change to a counted registry: then the merged truth is NEITHER side's number, and you must take it from the generator, not from either branch's assertion.** Measured: two engine PRs each converted "prebuilt" cells to source builds; after one merged, the other conflicted on 5 files (`README.md`, `docs/ENGINES.md`, `tests/test_engine_skills.py`, `tests/test_engine_source_guard.py`, `CHANGES.md`), and the two branches asserted `23 source / 8 prebuilt` vs `25 / 6`. Both were right for their own base and wrong for the merged tree. The authoritative count comes from the guard's OWN report — `python3 scripts/engine_source_guard.py report` printed `31 cell(s): 26 prebuilt=false, 5 prebuilt=true` — so resolve every assertion and both docs to **26/5** (docstring, `len(source)`/`len(prebuilt)`, the per-cell `FROM` assertions showing BOTH engines now source-build, and the prose "five cells … prebuilt"), never to either branch's figure. Rule: for a count a script can compute, run the script on the merged tree and write its number everywhere; hand-picking one side's number is how a "union" silently drops the sibling's conversion.
- Two conflict shapes are scriptable and should not be hand-merged: `.PHONY` token sets (`scripts/resolve-phony-union.py <Makefile>` — union of both sides' keys, refuses a hunk that is not a continuation) and rulebook bullets in `agents/*/SOUL.md` / skills (`scripts/resolve-rule-union.py <file>` — base's text plus the branch's unseen `- **rule.**` bullets). Both print what they wrote; neither decides whether the branch's edit was legitimate, so re-run the gates afterwards.
- Three more are versioned beside them, because each one exists to stop a specific mistake that cost a push tonight: `scripts/resolve-fleet-triple.py <repo>` — the `standing-rules.md` / `fleet-block-exemptions.json` / `SOUL.md` triple that a stacked branch collides with once a rule lands (canonical file wins, exemptions union by profile, fleet section regenerated); `scripts/splice-fleet-block.py <SOUL.md>` — splices the **canonical fence out of the issue body** instead of retyping it, then asserts `block in soul` (punctuation is load-bearing: rules 13/14/15 have no period inside the bold and rule 16 does, and #972 is a lane failing on that alone); `scripts/stack-replay.sh <n:branch>…` — the stacked-PR replay loop (`git cherry` → cherry-pick the `+` commits, `CHANGES.md` from the base then `changes-index`, marker check, gates, lease) with `scripts/batch-rebase.sh` for the `main`-based equivalent. A hand-run union is how conflict markers end up committed inside a JSON file that a passing `check-docs` never looks at.

If the conflict is a genuine redesign rather than a re-apply, stop and report instead of redesigning.

**Before resolving anything, check whether the change already landed — a conflicting PR is often a duplicate vehicle.** When main already carries the same files and the same openspec change through a *different* PR, the conflict is the duplicate, not a divergence to reconcile. Two reads settle it:

```bash
git ls-tree -r --name-only origin/main | grep -E '<the feature paths>'   # the change IS on main
git merge-base --is-ancestor <branch-tip> origin/main                    # ...but ITS commit never merged
```

Present on main + not an ancestor = superseded. Do not rebase it: post the tree listing and both shas on the PR, say it is a duplicate vehicle, and leave the branch untouched — rebasing the duplicate rebuilds the same conflict against the copy that already shipped, and the eight-file "conflict" is really main winning twice.

**A single squashed commit can be a BUNDLE that re-carries already-merged work under another PR's message — verify content against the merged commit before resolving, and do NOT supersede it.** When the branch's lone commit carries a subject citing a DIFFERENT PR than the branch's own purpose (e.g. a registry-sync PR whose commit message names a merged holds-gate PR), it is often a squash assembled on a stale base: part of its content is already on `main` through that other PR, the rest is the branch's genuine new work. Two reads settle which part is real:
```bash
git diff --stat <branch-tip>^ <branch-tip>          # what the commit ACTUALLY changed vs its own parent
git diff <merged-commit-on-main> <branch-tip> -- <suspect files> | wc -l   # 0 = that content already ships on main
```
When the suspect files (a workflow, its gate script, its tests) differ by zero lines from the merged commit, they are not a divergence to reconcile — the rebase will not duplicate them, and `git checkout --theirs` on a generated data file that IS the branch's deliverable is the right union. Never "fix" the mislabeled subject in the rebase (preserving the original message is a hard rule), and flag the mislabel in the report so the reviewer knows the commit's message understates its diff.

Keep the branch at **one commit**. Author must remain `Asimov Agent <support@docondee.com>` or `Andy Holst` — a rebase preserves the original author; never re-author.

**Verify the WHOLE commit range for the author-identity gate, never just the tip — one mistyped address anywhere in the range reds it.** `check-pr-authors` allowlists *addresses paired with* display names, so a correct display name with a one-character-typo email still fails (`support@doccondee.com`, one extra `n`, was rejected while `Asimov Agent` was otherwise right). After any amend, commit, or rebase:
```bash
git log --format='%ae' <base>..HEAD | sort -u     # must print exactly ONE allowlisted address
python3 scripts/check_pr_authors.py check --base <base> --head HEAD
```
A tip-only check is how a single typo ships: every other commit was correct and the tip looked fine on its own. Two mechanisms are distinct here and are not interchangeable — the commit **author identity** (this rule) versus a `Co-authored-by:` **trailer** in the message body (below). A `grep` for the address proves nothing about either, because commit prose that merely documents the trailer rule contains the address.

**Attributing another lane's author-gate red: name the exact commits and hand back the re-author command, do not rewrite their history.** Measured: a PR's `guard` job red with `[check-pr-authors] 2 violation(s)` on two commits authored `LLGenie Architect <architect@llgenie.local>`. The reply names both shas, quotes the gate's own words (*an alias list names display names, never addresses*), and gives the remedy — `git config user.email <allowlisted> && git rebase --reset-author && git push --force-with-lease` — plus the range-verification line. A re-author rewrites every commit's identity, so it is never done on a PR this lane was not dispatched for; a `mergeable` PR with 0 conflicts is not a sweep target either.

## Salvage audit before an owner prune — `scripts/salvage-audit.sh`

The owner's prune is irreversible for work that exists on no remote, and **uncommitted files are invisible to every ancestry test**, so a clean-looking branch list can still hide the only copy of a lane's run. Run `scripts/salvage-audit.sh [<repo>]` (read-only; deletes nothing) and report its four buckets plus the worktree flags.

Two refinements the script encodes, each of which a hand audit got wrong:

1. **A branch that ADDS a path main lacks is not automatically unique — test its CONTENT against every open PR head.** A rebase lane's own scratch branches (`rb<N>*`, `pr<N>-*`) hold replays whose content already sits in an open PR under a *different branch name*; classifying them UNIQUE inflates the preserve list and buries the real work. Measured: 13 raw UNIQUE collapsed to **5** once the added paths were checked against open PR heads.
2. **Fingerprint the added-file blobs to expose duplicate branches.** Two branches can hold the identical artifact (`agents/security-agent-soul-versioning` and `tmp/asv-trial` both carried blob `e22242fe6932`) — one preserve entry, not two.

Also: a path main *does* carry at a different path or in a different form is **not** byte-superseded (main had a file under `agents/llgenie-security/skills/security-scan-ops/references/`, while the branch held a standalone skill directory under `agents/llgenie-security/skills/`) — say that nuance rather than collapsing it into "already on main".

**Measure against `refs/remotes/origin/main`, never the bare name** — a stray `refs/heads/origin/main` shadows it and corrupts every quoted sha. The script prints whether that shadow exists.

## 5. Gates before push

**Run `post-rebase-verify.sh <full-base-sha>` first — it ships with this lane's skill, NOT in the repo tree (measured: `bash scripts/post-rebase-verify.sh` inside the worktree exits `No such file or directory`; the working invocation is `bash ~/.hermes/profiles/llgenie-pr-merge-conflict/skills/llgenie-pr-rebase/scripts/post-rebase-verify.sh <full-base-sha>` run from the worktree).** Both are invisible to `git rebase`'s "Successfully rebased":

1. **a conflict marker survived `--continue` and was committed** (only a syntax check sees it);
2. **`CHANGES.md` no longer equals a fresh `changes_index.py` render** — and critically, `changes_index.py check` still prints `ok: N fragment(s)` because that line describes the *fragments*, not the rendered file. Verified by negative control: swapping two rows in `CHANGES.md` leaves `check` saying `ok: 276 fragment(s)`, while the script reports `CHANGES.md != render` and exits 1.

The script runs 10 checks (clean worktree · no committed markers · every changed `.py` parses · every changed `.json` loads · `CHANGES.md == ci.render(REPO)` · census · lint_linefeeds · base is an ancestor · `merge-tree` clean by EXIT CODE · local HEAD vs the fetched remote ref) and prints `SAFE TO PUSH` / `DO NOT PUSH`. Both negative controls were exercised: a committed marker and a stale render each produce exit 1 with the failing check named.

```bash
make check-docs
make openspec-validate NAME=<change-name>
docker run --rm -u root -v "$PWD":/repo:rw -v "<owner-clone>":"<owner-clone>":rw -w /repo llgenie/test \
  python -m pytest tests/test_<touched>.py -p no:cacheprovider -q
```
`make test-unit` is the full gate but slow (~10 min); the targeted container run gives the same signal in seconds and does not depend on the host having pytest.

**Mount the owner clone as well as the worktree.** `-v "$PWD":/repo` alone makes git-dependent tests fail with `fatal: not a git repository: <clone>/.git/worktrees/<n>` — the worktree's `.git` file points into the parent repo, which is not mounted. Two tests reddened against a perfectly good tree until the second `-v` was added. The repo's own `TEST_OPTS`/`WORKTREE_MOUNT` does this; a hand-written `docker run` must replicate it.

**Gate the push on the result, not on the run.** A loop that pushes unconditionally lands red branches: write the gate so a failing test SKIPS the push and prints why. Then distinguish the two causes before blaming the branch — a test that also fails on a clean `main` worktree is a pre-existing red (disclose it and the sha), while one that passes on `main` and fails on the branch is the branch's own defect (do not push, report it).

**A targeted test list that expands to nothing runs the WHOLE suite.** `docker … pytest $TESTS` with an empty `$TESTS` silently becomes a full-suite run, and its first failure is then a red you did not ask for and may push straight past. Guard the variable and print what is about to run: when a PR touches no `tests/test_*.py`, `make check-docs` (+ `check-workflows` / `check-agent-profiles` for the files it does touch) IS the gate — say "no test files touched" instead of letting the shell substitute an empty argument.

## 6. Push
```bash
BR=<head-branch>
git push --force-with-lease="refs/heads/$BR:origin/$BR" origin "HEAD:refs/heads/$BR"
```
Lease on the ref you actually fetched, or the push is rejected. Verify: `git rev-parse HEAD` == `git rev-parse origin/$BR`; and for a SINGLE-commit branch parent == `origin/main`, but for a multi-commit pile check the BOTTOM replayed commit's parent (`git log --format=%H <base>..HEAD | tail -1` then its `^`), never `HEAD^` — `HEAD^` is the second-to-last replay, and mis-reading it as the base makes a correct rebase look detached (measured on a 6-commit #885: bottom parent == f244efe8, `HEAD^` was the #1010-block commit).

## 7. Report
Read back, never assume: `gh pr view <N> --json headRefOid,mergeable,mergeStateStatus` and `gh pr checks <N>`. Optionally post the rebase note as a PR comment and re-read it via the API.
**When `gh pr view` disagrees with the branch, `gh api` decides.** After a push in a busy repo `gh pr view --json headRefOid` can still return the *previous* head (and `mergeable: null` while GitHub recomputes); `gh api repos/<owner>/<repo>/pulls/<n> --jq '"\(.head.sha) \(.mergeable) \(.mergeable_state)"'` is the authoritative read. Quote the API's sha next to `git ls-remote <remote> refs/heads/<branch>`, and treat `mergeable: null` as *not computed yet* rather than as a conflict.

**Never report a state from BEFORE your own last action — a coordinator re-measures every row and a superseded row costs them a full cycle.** After a push, a merge, or a completed fix, re-read the refs you are about to describe and say what CHANGED rather than restating the pre-action picture: "<PR> was CONFLICTING at <old-sha>; rebased to <new-sha>, now MERGEABLE" rather than "<PR> is CONFLICTING". The same discipline runs in the other direction — a finding that quotes a sha older than your last push is expired, so re-measure before acting on it and never re-assert a defect you already fixed. When you cannot re-measure a deep queue, say `as of <iso8601>` so the reader knows to verify rather than relay.

**After a squash-merge, `git merge-base --is-ancestor <your-rebased-head> <mergeCommit>` returns NO — that is normal, not evidence your work was dropped.** A squash assembles a fresh commit from the PR's content, so your head is never an ancestor and the trees differ whenever the squash folded in other commits. Prove the merge carries your work by content and by the PR's own fields (`mergedAt`, `mergeCommit`, `state: MERGED`), plus a file-level read (`git show <mergeCommit>:<file-you-resolved>`), never by ancestry. Chasing that failed ancestor check as a defect wastes a cycle — the same trap applies to the squashed content of a stacked child.

**When `gh pr view` disagrees with the branch, `gh api` decides — but `gh api .head.sha` can ITSELF lag the branch ref, so `refs/pull/<n>/head` is the tiebreak.** After a push in a busy repo `gh pr view --json headRefOid` can still return the *previous* head (and `mergeable: null` while GitHub recomputes); `gh api repos/<owner>/<repo>/pulls/<n> --jq '"\(.head.sha) \(.mergeable) \(.mergeable_state)"'` is the normally-authoritative read. But measured this session: after a correct force-push the *branch* ref was `d7e26f40` while BOTH `gh api pulls/<n> .head.sha` AND `git ls-remote refs/pull/<n>/head` still returned the stale pre-push head `e0b277f3` — GitHub's lazy PR-head-ref sync (worsened by transient `Internal Server Error` 5xxs on push) held the old head for minutes, so the PR kept showing a conflict the branch no longer had (`git merge-tree <base> <stale-head>` = conflict, while `<base> <branch-ref>` = 0). Reading `mergeable`/`mergeable_state` alone will NOT reveal this. Reconcile by re-setting the PR's base/head through the API, which forces GitHub to re-read the branch: `gh api -X PATCH repos/<o>/<r>/pulls/<n> -f base='<base-ref>' -f head='<head-ref>'` → it returns the refreshed `.head.sha`; confirm `refs/pull/<n>/head` now equals the branch ref. Quote the branch-ref sha next to `git ls-remote <remote> refs/heads/<branch>`, treat `mergeable: null`/`unknown` as *not computed yet*, and when the PR-head ref disagrees with the branch ref after a push, believe the branch ref and reconcile — never re-rebase to "fix" a conflict that exists only on a stale PR-head ref.

## 8. Sweeping many PRs after a long-parked `main` finally moves
A merge that moves a parked `main` invalidates every open PR at once: `MERGEABLE` becomes `BEHIND`, and some become `DIRTY`. Rules for that sweep:

- Plan from live state each step, not from the list you collected at the start. The PR that caused the move disappears from `gh pr list` as its branch is deleted, so the count you quote before is not the count you report after. Say which PRs vanished instead of implying the plan was exact.
- One PR per pass, in that PR's own worktree (reused if one already exists), one commit, gates, then `--force-with-lease` against the ref you actually fetched.
- Exclude drafts and anything labelled `do-not-merge`: those are a human's hold, and rebasing them pushes a branch under someone else's hand.
- Re-read the head sha before quoting any check verdict for a PR. A PR still being pushed can change head three times while you plan, and a verdict on the old sha describes a commit nobody will merge.
- **A coordinator's whole board TABLE can be an aged snapshot — read `.state` and `.merged_at` per row, not only `.head.sha`.** A handoff listing a dozen PRs as "open … awaiting your retarget" can have most of them already MERGED: re-measure each row with `gh api repos/<o>/<r>/pulls/<n> --jq '"\(.state)|\(.head.sha[0:8])|\(.merged_at // "-")|\(.base.ref)"'` and diff against what you believe. A merged PR's head sha still resolves and its check-runs still return verdicts, so `head.sha` alone cannot tell you the PR left the board — only `state`/`merged_at` can. Stamp the measurement time in your reply (`as of <iso8601>, main <sha>`) so a reader can judge the age rather than re-derive it, and when a row you were told to work has merged, say so with its `mergeCommit` instead of performing the work.
- **A coordinator's defect report can name a stale head — verify the sha it quotes IS the live head before fixing.** A dispatch saying "#PR at <sha>: duplicated census block / not rebased" may be reading the head from BEFORE your push (its query tool caches the pre-push sha while the branch has since moved). First `git ls-remote <remote> refs/heads/<branch>` and `gh api …/pulls/<n> --jq .head.sha`: if the quoted sha ≠ the live head, measure the LIVE head — the "defect" may already be fixed, and applying the prescribed fix would duplicate or churn a correct branch. This recurs: trust the remote ref over any sha quoted in a message or a coordinator's summary. **And when you report the mismatch back, say it as "expired", not "you mis-read": a coordinator's measurement was TRUE at the sha it quotes and simply AGED under your later pushes — accusing the tool of reading the wrong ref is a false diagnosis and it corrodes the working relationship.** State it as "your <old-sha> snapshot predates my push at <new-sha>; at the live head X is already fixed, here are the check-run lines." The reciprocal duty is yours too: treat any finding that quotes a sha older than your last push as expired, re-measure before acting, and never re-assert a defect you have already fixed. **The harder variant: after a `git filter-branch --msg-filter` rewrite the quoted sha is not merely stale, it is ORPHANED — `git merge-base --is-ancestor <quoted> <live-head>` = NO, while `gh api commits/<quoted>/check-runs` still returns the OLD verdicts forever because GitHub keys check-runs by sha.** A coordinator then reports "both reds still present" from a commit no longer in the branch. Answer with three independent live-head reads (`git ls-remote refs/heads/<b>`, `gh pr view --json headRefOid`, `git ls-remote refs/pull/<n>/head`) plus check-runs measured at THAT sha, and never re-apply a fix because an orphaned sha's check-run says red.
- Serial, never parallel: the whole point is to not re-queue N matrices at once, which is what starves the runners in the first place.
- Ready-made loops for the whole sweep — measuring staleness, preparing a batch without resetting, the gate-then-push shape, and the union resolutions for the habitual conflict files — are in `references/sweep-mechanics.md`.
- **A salvage/prune audit of local branches and worktrees** (read-only, never deleting) has its own decision table and a false-positive trap that makes a naive version useless — a three-dot diff is non-empty for squash-merged work too. See `references/salvage-audit.md`.
- **A hold beats a handed order.** A sweep order written by a coordinator can list a `do-not-merge` PR — including as its first, dependency-critical step. Audit the order against the live labels before walking it (`sweep-plan.py --order '#834 #877 #901 …'` prints each held or missing step) and report the contradiction instead of resolving it by guessing; a hold is the owner's explicit stop, so the held PR is skipped and every later step that depended on it is deferred, not dropped.
- **Prepare in batches, push one at a time.** Rebasing a batch of worktrees in one pass is safe and fast; pushing must stay per-PR and gated, because the push is what starts the verdict. Prepare → resolve → gate → push for one PR, then the next.
- **Reuse an existing worktree instead of creating a second one.** If `../llgenie-wt/pr<N>-rebase` already exists, move it to the branch tip with `git merge --ff-only` and rebase there; a second worktree for the same PR splits the evidence and multiplies the count the owner has to review.
- **A worktree that will not fast-forward is a finding, not an obstacle to clear.** Compare `git rev-parse <local>^{tree}` with `git rev-parse <remote-tip>^{tree}`: identical trees mean the local commit is a superseded replay and the branch can be moved to the remote head safely; different trees mean unpushed work, so report it and leave the worktree alone. A long divergence (dozens of unique commits each way) is a stacked branch that has moved on — never force it onto the new base.
- **Before a lease push on a diverged branch, ask what the push would DELETE.** `git cherry HEAD <remote>/<branch>` lists the remote's commits: a `+` row is remote work with no local equivalent, and a lease push that succeeds would erase it. Push only when every row is `-` (already present) or the two trees are identical; otherwise complete the local rebase, park it, and report the `+` shas — the dangerous outcome is not a rejected lease, it is a lease that succeeds on a branch someone else still owns.
- **Exactly one rebaser at a time.** A host sweep is a workaround for a broken in-repo automation, and a workaround that outlives its cause becomes a second writer of the same branch. While the in-repo bot's sweep is red, this lane rebases; once it is green again *after its own fix has merged* — and not merely because one of its runs concluded `success` while a PR stayed conflicted — this lane degrades to reporting transitions and pushes nothing. Say which regime produced any report, so a stale one cannot be read as current.
- **A stacked PR (base ≠ `main`) gets NO `pull_request` CI at all, so `mergeStateStatus: CLEAN` on it is meaningless, not a pass.** Every workflow here gates `pull_request` on `main` (#950), so a PR whose base is a feature branch runs only `holds`/`guard` — no scope/unit matrix — and reads `CLEAN` because no required checks apply on a non-main base. Never report such a PR “green” or “CI pending”: say “stacked on <base>, no PR CI until retarget to main.” Verify with `gh api repos/<o>/<r>/actions/runs?head_sha=<sha>` — only `holds`/`guard` present is the absence of CI, not a green.
- **A coordinator can name the wrong REMOTE and the wrong commit COUNT — measure both per PR before acting.** Two measured misses in one dispatch: “push to the fork” when `gh pr view --json isCrossRepository,headRepositoryOwner` said `cross:false, owner:asimov-agent` (a fork push would create a divergent branch that never moves the PR — push to the owner repo); and “three commits carry the trailer” when exactly one did. Before a history rewrite, read `isCrossRepository`+`headRepositoryOwner` for the push target and `git rev-list <base>..<head>` with a `%B` grep for the count; trust the measurement over the message.
- **The same failing check on many unrelated PRs is one cause, not many.** When a batch reports `linux / unit` (or any single job) newly failing across a dozen branches, prove the shared cause against a pristine worktree of the new `main` before touching any branch: if it fails there too, the branches are innocent and only a main-side fix unblocks them; rebasing them re-queues the same red. Attribute it per PR with the sha it was measured at, so no lane re-derives it.

## Sweeping a whole board that conflicts on ONE index row does not converge in one pass

`CHANGES.md` adds a row at the same table position on every branch, so **each PR that merges re-dirties every
other PR in the sweep** (measured: eight rebases read `MERGEABLE` after pass 1; the moment #826 merged as
`71c84025`, the other eleven read `CONFLICTING` again — one new row is enough). Plan for a second and third pass:

- Push, then `git fetch origin main` again and **re-rebase only the ones the merge re-dirtied**, reusing the same
  worktrees. The branch content is already gated, so a re-pass only re-unions the row: `check-docs` + lease push,
  no test re-run (`git diff origin/main -- <code>` is empty, only `+` rows in `CHANGES.md`).
- Loop the union+continue until no rebase is in progress: a multi-commit branch can conflict on `CHANGES.md` once
  per commit (`git rebase --continue` then stops again), and a branch that **renames** its note file can re-add a
  row naming the old note. `make check-docs` catches exactly that (`links agent-wiki/…, which does not exist`) —
  delete the stale row and `git commit --amend --no-edit` rather than inventing a note.
- The structural cause is a filed issue (`#934`, `#682`): report it instead of re-pushing in a loop forever.

## A skipped cherry-pick turns a rebase into silent DELETIONS of main's work

`git rebase` prints `warning: skipped previously applied commit` when the branch's first commit was squash-merged
as a *different* commit. The remaining commit's patch is then computed against a parent that carried files the
merge base never had, so it **deletes** main's copies (`scripts/pr_heads.py`, `tests/…`, a `.pr874.md`) while the
rebase reports `Successfully rebased`. `merge-tree` had flagged the same pair as conflicting; a clean rebase is not
evidence of a correct one.

Detect: after any rebase, `git diff origin/main --stat` must show **only additions** for a change that only adds
files. On a deletion you did not author, rebuild the branch from the branch's NET diff:

```bash
git checkout -B pr<N>-rebase origin/main
git diff $(git merge-base origin/main <remote>/<branch>) <remote>/<branch> > /tmp/net.diff
git apply --3way /tmp/net.diff      # conflicts are then real unions: .PHONY keys + target blocks, docs sections
git add -A && git commit -C <old-tip>   # keeps the original author+message
```
Lease on the ref you actually fetched, or the push is rejected. Verify: `git rev-parse HEAD` == `git rev-parse origin/$BR`, and parent == `origin/main`.

Resolve `Makefile` hunks as: main's `.PHONY` line with the branch's key inserted (never the branch's whole line —
it drops keys main added, e.g. `ci-slow-rows`), and both target blocks (main's newer block first, the branch's after).

## Two sweep lessons that cost a re-run each

**A branch that has moved `CHANGES.md` to one-row fragments is NOT a row union.** After #934 the index is
`docs/changes.d/<note-stem>.md`, one row per file, rendered into `CHANGES.md` by `scripts/changes_index.py`.
A rebase of such a branch conflicts because main added rows the branch has no fragment for, and inserting a
row into the rendered table fights the generator. Resolve at the FRAGMENT level: for each row in
`git show origin/main:CHANGES.md` whose note stem is missing from `docs/changes.d/`, write
`docs/changes.d/<stem>.md` holding that row verbatim, then let `scripts/changes_index.py check` +
`write` referee. Verify with the row-set diff (`comm -23` over `^| 20` rows must be empty; `comm -13` must
be exactly the branch's own row) — a hand-inserted row renders away on the next `make changes-index`.

**Gate the push on the branch's OWN head, not only on the rebased tree.** Two PRs in one sweep
(#882, #940) had a green rebase and a red PR: their tests/openspec jobs fail at the branch's tip
before the rebase, because the branch's own second commit contradicted its own test (removed
`timeout-minutes` from `uses:` jobs, then demanded it) or left its OpenSpec checklist unticked.
Before pushing, read the run at the PR's CURRENT head (`gh run list --commit <sha>`) and, for any
failing job, reproduce it on the rebased tree — then on a pristine `origin/main` worktree. Fails on
main too → inherited; fails at the branch's own head and on the rebased tree → the branch's, so park
the rebase, comment the measured evidence (job, `path:line`, both counts), and push nothing: a push
only buys a fresh matrix for a verdict already known, and ticking another change's tasks or
re-designing its logic is not this lane's call.

## Fleet orchestration (issue #1010) — this skill's lane side
- **A local branch named `origin/main` shadows the remote-tracking ref and sends every `git rebase origin/main` at the wrong base.** Git's resolution order checks `refs/heads/<name>` (a local branch) BEFORE `refs/remotes/<name>`, so once anything does `git branch origin/main <sha>` the bare name resolves to that local branch while the real remote is `refs/remotes/origin/main` — and `git rev-parse origin/main` printing several distinct shas plus `warning: refname 'origin/main' is ambiguous` is this class of accident. Defend: disambiguate the canonical base unconditionally — rebase with `refs/remotes/origin/main`, and before pushing cross-check the authoritative head directly via `gh api repos/<owner>/<repo>/commits/main --jq .sha`; when the API sha, `refs/remotes/origin/main` and what you rebased onto all agree, the base is real. Never rebase a branch whose base sha you only ever saw as an ambiguous bare ref.
- **Scoped admission gates green do NOT prove the running unit suite green — the full suite catches fleet invariants a branch's own gate run never touches.** A rebase that lands a new workflow or edits the Makefile's `ci-unit` list can pass `check-workflows`/`check-dispatch-forms`/`check-docs`/`check-wiring` AND the touched spec files while `ci-unit` reds on three distinct invariants: a **cron-slot collision** (`test_bot_pipeline_isolation`: a schedule's minute is owned by an every-hour bot or another scheduled bot — free when the branch was cut, reserved on current main); an **unclassified ci-unit gate** (`test_issue_bot_gates::test_the_real_tree_is_wired`: you added `make check-<new>` to `ci-unit` but never filed it in the guard's `FAST_GATES`/`DEFERRED`); and a **header-vs-cron drift** (`check-dispatch-forms` compares the workflow's header claim against the cron — change the minute and forget the header and the gate flips). Before pushing any workflow-touching rebase, run the actual full hermetic gate — the CI's exact invocation, not a scoped subset — and read its summary line. A branch owner's own "admission gates green, verified before push" is a claim about their changed files, not about the fleet invariants their change disturbs.
- **A touched test file that hangs locally is NOT a missing gate — it is reaching for the network seam; run it under CI's own `-m "not network"` selection and it finishes in under a second.** Measured: `tests/test_check_model_links.py` + `tests/test_pick_full_registry.py` blew a 400 s foreground timeout, then the same two files under `-q -m "not network"` returned `5 passed, 11879 deselected in 0.47s`. That selection is *exactly* what the CI unit job uses, so the local result is the CI verdict, quotable as evidence. Two traps: `--timeout=120` is **not available** (the image lacks `pytest-timeout`; pytest exits `error: unrecognized arguments`), and a hanging test tempts you to skip the evidence and push anyway — do neither; re-run with the CI selection and report it.
- **`git worktree add -B <branch>` fails when that branch name is already checked out in another worktree, and an existing `rb<N>` directory is not necessarily this PR's.** `fatal: '<branch>' is already used by worktree at '<path>'` means the name is taken, not that the path is busy — pick a fresh branch name (and verify the existing worktree's `git rev-parse --abbrev-ref HEAD` really is the branch you want before reusing it, since a worktree named for one PR can hold an unrelated branch's replay).
- **`make ci-unit` cannot run inside the container — docker-in-docker.** Its recipe is itself another `docker run`, so inside `llgenie/test` it fails instantly with `Cannot connect to the Docker daemon` (outer make exits 125/2). That is an infra limit, not a branch verdict. Run the same seam directly, what `make test-unit` executes: `docker run --rm -u root -v "$PWD":/repo:rw -v "<owner-clone>":"<owner-clone>":rw -w /repo -e HOME=/root llgenie/test python scripts/unit_tests.py run` — identical discovery/`-m "not network"` selection as the CI job. **Run it proactively while the CI matrix is queued**: it needs ~28 min, gives the verdict the queued job would give, and its summary line (`N passed, M deselected`) is quotable evidence that does not depend on a runner slot — the right answer when a PR has had several defect cycles and you need to know whether the tree is actually green before another push. Start it in the background and keep working; do not poll it.
- **Verify the COMMITTED HEAD after regenerating a generated file, not the clean-looking worktree — an uncommitted `M file` means the push ships the pre-fix tree.** Easy to ship: fix the generator output in the worktree, run gates (green on the dirty tree), commit README/docs, lease-push — the committed head still carries the hand-merged order while the fix sits uncommitted, and the PR reds on the exact gate you cleared. Before pushing a regenerated file, `git status --porcelain` must be empty AND `git show HEAD:<file>` must satisfy the gate (e.g. `check-dispatch-forms` on the committed table, not the staged one); then a small follow-up commit/amend is the legitimate corrective lease push.
- **When the full-suite red names a cron collision or unclassified gate riding a workflow PR, the owning lane's branch is the vehicle — answer on that PR with the measured job + assertion + corrective sha, not only your own bookend.** A "verified before push" claim on their side stays harmless only if the full-gate red is attributed and re-verified on the corrected head.
- **Pick a cron minute against the derived ownership map, not against the board.** All the every-hour bots reserve a minute on all seven weekdays; daily/weekly bots own (minute, weekday) slots from their `range`/step fields. Compute the free set from the actual workflow files (`_reserved_minutes` + the pairwise owners map), choose an odd free minute, and update the header doc claim in the same commit so `check-dispatch-forms` and the isolation tests stay green together.
- **Author-gate red at a PR's merge-ref range during merge churn is a SHARED-BASE red — attribute then re-base, never re-author.** `check-pr-authors` scans the PR's effective range; if main moved since the PR's base was cut, the merge-ref range can include a squash-merge commit authored with a bare name (`Andy <…>` vs the allowlisted `Andy Holst <…>` / `Asimov Agent <…>`), so the gate reds even though every commit the branch itself authored is allowlisted. Ask which commit the gate names and whether it sits on the branch or only on main (`git merge-base --is-ancestor <that-sha> <head-branch>`): if it is main-only, the fix is to re-base the PR onto the newer main — that drops the off-list merge commit from the gate's range — never to re-author the branch's own commits, which would rewrite a lane's history to satisfy a gate the branch never violated.
- **A `Co-authored-by:` trailer outside the allowlist: the COMMIT'S AUTHOR decides whether dropping it is allowed — not the mere presence of a trailer.** `check-pr-authors` treats a co-author trailer as attribution, so `Co-authored-by: <someone>@<non-allowlisted>` reds it. First attribute it: iterate the range (`for c in $(git rev-list <base>..<head>); do git log -1 --format='%h %an <%ae> | %cn <%ce> :: %s' $c; done`) and read each trailer-carrying commit's **author AND committer**. If they are the allowlisted OWNER (`Andy <andy.holst@…>` / `Andy Holst <…>` / `Asimov Agent <…>`), dropping a stray co-author trailer is NOT re-authoring — it removes an attribution the gate itself sanctions (`Drop the trailer or make the co-author one of the two allowlisted addresses`), and you MAY fix it. If the commit belongs to another lane (author is neither allowlisted identity), stop and route it — editing it would rewrite their work. Two ways to know which commits/trailers are real, because a dispatch can overstate the count: grep `%B` for the exact FULL trailer string, never the word in the subject (three commits whose SUBJECTS contained “architect” were reported as carrying it; exactly one did); and remember a prose sentence that merely CONTAINS `Co-authored-by: X <y>` is not a trailer the gate flags — do not “fix” prose.
