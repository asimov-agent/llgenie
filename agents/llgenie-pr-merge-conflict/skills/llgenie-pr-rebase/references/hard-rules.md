# Hard rules — this lane's non-negotiables

Split out of `SKILL.md` when that file crossed skill_manage's ~100,000-character cap and
could no longer accept a patch (by `skill_manage`). The text below is verbatim from the
SKILL.md section it replaced; SKILL.md keeps the heading and a one-line pointer so a reader
still finds the rule where it is used.

## Hard rules
- **A conflict is the reason a PR may be held, never the remedy.** Two cases and they are different: if a rebase resolves it, do the rebase and do not label anything; if the divergence is structural (a duplicate vehicle, a base that will never converge, a file another PR is restructuring), the hold needs the issue that removes the cause — named on the PR with the exact removal condition — not a note saying "conflicts". Never place `do-not-merge` on a bot's PR out of caution: "I am not confident" is a review, not a label, and a hold whose reason expired reads identically to abandonment (`BLOCKED` either way).
- **A conflict block can be a POSITION clash, not a content clash — resolve it as "both, in order".** Both sides inserted a run of functions/tests at the same point (main's `_deferred_engines` rewrite vs 11 new tests; main's `_unquote`/`workflow_run_coverage` vs the branch's `_jobs_block`/`check_uses_job_keys`). The union is the branch's block, then MAIN's newer block, and the shared closing lines (`})` / `return out`) belong to BOTH — duplicate them, or the first function loses its body and only a syntax check catches it.
- **`git checkout --theirs -- <path>` during a rebase takes the branch's WHOLE file and silently deletes whatever main added to it.** Measured on #913: `--theirs` reverted main's #925 (`import base_ref`, the `base: str | None = None` signature). Always re-derive such a file from `origin/main` and re-apply only the branch's own hunk (here: remove the `sys.path.insert` lines, keep `import json`/`import base_ref`), then prove it with `git diff origin/main -- <path> | grep -E '^[+-][^+-]'` showing only the intended lines.
- **During a stacked CHERRY-PICK, `git checkout --ours` is the BASE side — a fallback that "takes a side" for a conflict your resolver could not union silently DROPS the replayed commit's own change.** Measured: on a conflict the replay driver did not union, it ran `git checkout --ours` for the remaining file and carried on; `base.txt` came back as main's `mainline-change`, losing the branch's own `pr-own-work` line, and the cherry-pick still committed — a silent revert, inverted, that reports success. A replay driver must **REFUSE and abort** (naming the file) on anything the resolver left unmerged, never quietly prefer a side: the author reconciles two real intents. The one file it MAY take from the base is the generated `CHANGES.md` table, because `changes_index.py write` re-derives it from the fragments — no content is lost. Before trusting a shipped replay script, grep it for a code-level `git checkout --ours`/`--theirs` and read the conflict branch in full; a comment that merely NAMES the foot-gun does not count (see the next rule).
- **When a test greps a script for a defect PATTERN, strip comments FIRST, then match on the remaining code — a comment that documents the foot-gun is not the foot-gun.** A guard test that filtered raw lines for `git checkout --ours` matched the file's own explanatory note (`# ... git checkout --ours silently DROPS ...`), stripped it to whitespace, and asserted `not ['    ']` — red on a correct tree against nothing. Convert each line with `ln.split('#', 1)[0]` before the `in` test, and keep a negative control that appends a REAL offending call (`git checkout --ours f`) to prove the guard still bites. This is the same "assert behaviour across the real shapes, not text" discipline the detector rules already carry.
- **"The branch's file is a superset of main's, so take it wholesale" is a claim about the base you MEASURED, not about the file — when main moves, the same file can be an OLDER generation and the wholesale take reverts main's fix.** Measured: a branch's test file was a strict superset by def-name count, so it was taken wholesale — correct against the base it was measured on, silently wrong one merge later, because main had meanwhile gained a **newer signature** of a shared helper (`_fits_card(model, gb)` → `_fits_card(model, gb, arch)`) plus a new oracle helper. The wholesale take reverted both and red-ed a test that lives on **main**, which reads exactly like the branch's own defect. Compare **signatures of shared helpers**, not the set of def names: `comm -13 <(git show <main>:<f> | grep -oE '^def [a-z_0-9]+' | sort -u) <(git show <branch>:<f> | grep -oE '^def [a-z_0-9]+' | sort -u)` names what the branch *adds*, and diffing those shared defs' first lines names what main *changed*. The correct union for a superset-shaped test file is **main's file plus only the defs the branch adds**, extracted by name and appended — then re-run the suite, because the appended helpers may call the old signature (a helper calling `_fits_card(model, vram)` after main added `arch` lets an Apple-Silicon row satisfy a CUDA fit and reds an unrelated assertion).
- **`git rebase --continue` hang** — without `GIT_EDITOR` it can open an editor on the commit message and sit forever (measured: a 180 s tool timeout with the rebase still at `msgnum 2/25` and no git process left). Always `GIT_EDITOR=true git -c rerere.enabled=false rebase --continue`; if it already hung, re-run it with the variable — the rebase state is intact.
- **Automate the row insert with a script FILE, not a heredoc** — a `python3 - <<'EOF'` heredoc is refused as a dangerous command in unattended runs. Keep `insert_rows.py` (takes path + a rows file, inserts after the `|---` separator) in the profile scratch dir and call it, plus one `rows_<pr>.txt` holding the branch's verbatim row.
- **`check-architecture-census` has two traps, and its verdict depends on WHERE git runs.** (a) Run inside a docker-mounted linked worktree it reports `tracked=0` and `13 claim(s) stale` on EVERY clean head, because the worktree's `.git` file points to a host-absolute gitdir path the container does not mount (the same class as the git-dependent-test mount failure) — "13 stale" from there is environmental, never a branch verdict. Prove the gate's real conditions on the clone: `git -C <clone> cat-file -e <pointer>^{commit}` for pointer-real AND `git ls-tree -r --name-only <pointer> | wc -l` must equal the same count for HEAD. (b) The census gate now measures the tree at the sha the doc NAMES: the pointer must name a REAL commit that is an **ANCESTOR of HEAD**, and the counts must match `git ls-tree -r --name-only <pointer>`, NOT the count at HEAD. So a file-adding PR passes with the pointer untouched — a rebase onto a main carrying the fix keeps an ancestor pointer valid and the gate prints `[census-gate] OK — measured at <sha> … is an ancestor of HEAD`. **Do not re-derive the census on a rebase**: the pre-fix habit of re-pointing `measured at` at a same-count-as-HEAD sha (once needed because the OLD gate reddened `Re-derive it now` on a count mismatch) now only risks a second contradicting block; that old contract is gone. If a resolution DUPLICATED the block — a botched union leaves several `measured at` lines and the gate reports `no usable referent` — collapse it: `git checkout <main> -- docs/ARCHITECTURE.md`, re-apply only the branch's own rows, and require the gate to print `OK`. Count the block: exactly ONE `(measured at `<sha>`)` line, because a two-hit grep that also matches a prose mention of `measured at` reads a duplicated block as solved. **The duplication is not only the paragraph — a botched union duplicates the Repository-layout TABLE ROWS too.** Measured: one head carried 8 stacked `measured at` lines AND 5 duplicate ``| `agent-wiki/` |`` rows (256/245/244/254/253) AND 2 duplicate ``| `openspec/` |`` rows — collapsing only the paragraph left the table wrong. Count both (each of `grep -c '| `agent-wiki/`'` and `grep -c '| `openspec/`'` must be 1) and set every row's number from the tree at the pointer sha (`check_architecture_census.py report` prints the true counts). Prove it in real git on the clone, never docker-in-worktree (`tracked=0` artifact). When the dispatch says "drop the census hunk", the vehicle is usually a **census-only tip commit**: prove it with `git show --stat <tip>` (docs-only) plus `git log origin/main..<parent> -- docs/ARCHITECTURE.md` printing nothing, then drop the commit so the file is byte-identical to main — never re-derive a third census block inside a rebase, because the census moves to a single vehicle (#1053/#1046) and its red is expected there, not here. Leaving contradicting census blocks is the same red. **A `ci-scope`/`scope` red is often NOT the gate its job name implies — read the failing STEP, and a `check-wiring` step failing on `json.decoder.JSONDecodeError` means a malformed JSON fixture, not a wiring fault.** Two shapes: (a) `[openspec-tasks] FAIL <change>: unchecked task checkbox(es) at lines [...]` — the branch author's unfinished change, pre-existing (below); (b) `make check-wiring` → `json.decoder.JSONDecodeError: Expecting ',' delimiter: line N column 1` → one `tests/fixtures/*.json` is INVALID JSON (a truncated entry: `"issue": 1027,` with no closing `}` leaves one `{` unclosed). Find it by loading every tracked JSON (`git ls-files '*.json'` through `json.load`) and close the entry; attribute first — invalid at the branch head BEFORE your commits = pre-existing, and a valid copy on main confirms it is the branch's own merge artifact, so fixing the JSON is in scope. Also: `lint_linefeeds.py` returns on the FIRST failure class (missing trailing newline) before checking markdown headings, so fixing the newline SURFACES a masked blank-line-before-heading defect in the same job — fix both or the lint job stays red.

**A census PR's `ci-scope` red is often `openspec-tasks`, not the census — read the failing STEP, not the job name.** After the gate fix greens the census, the same `ci-scope` job can still be red on `[openspec-tasks] FAIL <change>: unchecked task checkbox(es) at lines [...]` — the branch author's unfinished change, pre-existing. Ticking another change's checklist or redesigning its logic is not this lane's call; report the change + line numbers and route to the author. Census-green + openspec-red is the honest state of such a PR after a rebase.
- **`check-wiring` has a SECOND shape beyond malformed JSON: a STALE host-only entry must be DELETED once a merge wires its script.** After main or a folded sibling merges a change that makes a previously host-only script reachable from CI, the gate prints `[check-wiring] <path>: '<script>' runs in CI now (<the test that reaches it>) — delete the host-only entry`. The remedy is to remove that key from `tests/fixtures/host-only-wiring.json` (load with `json`, `del d['documents'][<path>]`, dump with the SAME indent, add a trailing newline), then require `[check-wiring] OK … N host-only` with N one lower, and confirm `git diff` shows ONLY the deleted entry (a naive re-dump that reformats the whole file is churn). This is the intended contract: an entry is stale the moment CI reaches it.
- **A LONG branch replaying over a main that regenerated a shared generated file (census/CHANGES) stops on that file at many replay steps — pre-empt with ONE `-X theirs` rebase, then regenerate once at the end, and prove nothing else was silently preferred.** Measured: a 128-commit branch rebased over a main carrying a census refresh + a `CHANGES.md` row conflicted on those generated files repeatedly; resolving per-step is the failure shape. Instead `GIT_EDITOR=true git -c rerere.enabled=false rebase -X theirs <main>` (prefer the branch's content on conflict) runs the whole replay in one pass, then you fix the generated file once for the final tree (regenerate the census from the current tree / `scripts/changes_index.py write` for CHANGES) and commit. `-X theirs` is UNSAFE by default because it silently prefers the branch on ANY conflict, so verify AFTER: `git diff <main> HEAD --name-only` must be exactly the branch's own files plus the regenerated one, and run every gate — if an unexpected file appears, that conflict was a real union you let `theirs` swallow, so redo with a normal rebase. Only use this when the conflicting files are ones you re-derive anyway.
- **Inline backtick-quoted shas in a double-quoted `gh … --body "…"` shell string get command-substituted and vanish or error** — a `gh issue/ pr comment --body "…#919 → `7f3e2e01`…"` makes bash execute the backticks (`7f3e2e01: command not found`), and the posted comment carries no sha. Measured again with a multi-backtick body: `gh pr comment … --body "… `63d8bc97`… `git rebase --abort`…"` exited `accepts at most 1 arg(s), received 6` and **posted nothing at all** — so an announcement you believed you had made never existed, and a claim on a branch silently did not happen. Check the exit code and that a URL came back before assuming the comment landed. Same class as the heredoc-refused rule: put the body in a file (single-quoted heredoc so backticks are literal) and post `--body-file /tmp/note.md`; this also lets you verify the text before it lands.
- **`make check-registry` cannot finish on this host** — its first half, `scripts/sync_registry.py check`, fetches the upstream contract and hangs past 600 s; the guard that actually protects a rebased re-vendor branch is the deterministic half. Run `make check-registry-keys` and report the network half as unable-to-run instead of calling the PR red.
- **A rebase sweep never needs `git reset --hard`, and a worktree is not storage.** Before touching a worktree you did not create this session, run `git status --porcelain` and `git log <remote>/<branch>..HEAD` — anything listed there is somebody's work that exists on no remote. Measured the hard way: a `reset --hard` onto the fork head moved a branch off a local-only commit that had never been pushed, and it survived only because a tag was made seconds later. Reset only a worktree you created and whose commits are already pushed; otherwise report it.
- **Collapsing a duplicated census block on a stack ROOT can re-dirty a stacked CHILD, and the child's own duplicate is the cause — report it, do not "un-fix" the root.** Measured: fixing #919's 8-line duplicated `measured at` block (`089af914`→`de3085c`, gate OK) turned #999 from 0 conflicts to `CONFLICTING/DIRTY` against its new base, because #999's own `docs/ARCHITECTURE.md` carried its own 17-line duplicate — it never collided while the base held the byte-identical block. Before reporting a stacked child clean after a root census fix, re-run `git merge-tree --write-tree <new-root> <child>`; if it now conflicts and the only file is the census doc, the child's duplicate block is the cause. Do NOT revert the root fix (it was correct) and do NOT silently rewrite a read-only child: report the conflict with the child's pointer count and the collapse remedy, and let the owning lane/planner authorise the child fix.
- **A mass `linux/unit` red is attributed ONLY by its `E` assertion lines plus a same-window control run at main — never by the word `urllib` appearing anywhere in the log.** Reading `FAILED tests/…` (test names) or grepping a substring like `urllib.error` matches lines that are NOT the failure text and will mis-classify a real branch defect as a flake. Read the failure body (`grep -A6 'AssertionError\|Error'`, the `E ` lines) to get the actual assertion. Then control it: find main's own unit job at the current main sha (`gh api 'repos/<o>/<r>/actions/runs?event=push' | select head_sha==main`) and compare — same suite, same window, same runner passing on main while the branch reds ⇒ **branch defect**; main reds identically ⇒ shared/inherited. Measured: a `42 failed, 14987 passed` red was declared a network flake from a stray `urllib.error` grep, then the control showed `AssertionError: <repo> has no files on the Hub / assert []` at `tests/test_pick_full_registry.py:255` with main's identical suite `completed/success` — a real defect in the branch's own change. Do not re-run hoping a genuine red clears, and do not report it green. Independently: a `mergeable:true`/`behind` PR is not a rebase target at all (#1015) regardless of its red.
- **A branch cut before main added a NEW fast gate will red on that gate without any conflict — check the gate's age before calling it the branch's defect.** Measured on #919: `linux/unit` failed `make check-import-roots` with `bare: 54 now, 52 recorded / sys-path: 33 now, 32 recorded`, and `scripts/check_import_roots.py` was **absent at the branch's old base `564e9383`, present at current main `36cfa8c1`** — it arrived with an unrelated merged PR. The branch's new test file used the pre-ratchet style (`sys.path.insert(0, str(REPO / "scripts"))` plus bare `import <scripts_module>`), which `tests/conftest.py` already makes unnecessary. Isolate the exact delta by running the gate's OWN function against two worktrees — `importlib` the script, call `findings(Path(root))` in a clean `main` worktree and in a `main`+merge worktree, and set-difference the `where` values; that names the precise file:line instead of guessing (`tests/fixtures/import-roots-baseline.json` only prints totals). The fix is package imports (`import scripts.<mod> as x`) and dropping the redundant insert; prove it with `[import-roots] OK: counts at or below the recorded baseline` **on a main+merge tree**, because the script lives on main and the branch head cannot run it. Same class as the census/newline/JSON defects: a gate newer than the branch is not the branch's mistake, but it is the branch's repair.
- **The same class has a FIXTURE variant: a branch that predates a hermetic snapshot main now ships reds by reaching the network and rate-limiting, and the failure text is a 429, not an assertion.** Measured: `linux/unit` red at a head whose branch was 3 commits behind main; `tests/fixtures/hub-snapshot.json` (232 KB) was **absent on the branch, present on main**, so `trend_list_matrix.py --check` had nothing to replay and hit `huggingface.co/api` → `[hf] rate limited (429) … waiting 291s`. The remedy is a rebase onto main (the fixture and the hermetic script arrive with those commits) — nothing in the branch's own diff needs changing. Distinguish the two sub-cases before acting: **a 429 with a missing fixture is the branch being behind**, while an assertion failure is the branch's code. Guard against a second misread in the same job: `check_import_roots` reporting a slightly higher count than main is **advisory and pre-existing**, never head-of-line — say so rather than blaming it.
- **When the CI logs are unavailable, reproduce the gate locally instead of naming a cause you did not measure.** `gh run view --job <id> --log-failed` can return only post-job cleanup lines (or nothing) even for a real failure, and `--log` can come back empty; that is not evidence the job passed. Check out the failing PR head into a scratch worktree and run the gate itself:
  ```bash
  git worktree add -q /tmp/chk<N> -B chk<N> <head-sha> && cd /tmp/chk<N>
  python3 scripts/<the-gate>.py --check          # the STEP's own command, not the job name
  ```
  Then attribute against a clean `main` worktree as the control. **Never name a cause you could not reproduce** — report "reproduced as X" or "not reproduced; logs empty, needs a fresh run", and keep the two distinct in the reply.
- **`changes_index.py write` must run at the END of a replay, never mid-replay — a mid-replay write passes `check` and still reds `linux/unit`.** Measured: a rebase wrote the index while resolving a `CHANGES.md` conflict at commit 2 of 6; `changes_index.py check` said `ok: 271 fragment(s)` (true of the *fragments*) and every gate I ran was green, but the committed table's ROW ORDER no longer matched a fresh render, so `linux/unit` concluded `failure` with `1 failed, 3288 passed` on `test_the_real_index_renders_the_committed_changes_md — assert committed == rendered`. The fragments were untouched by the later replay steps; only the rendered file's ordering went stale. Fix and verify: `python3 scripts/changes_index.py write`, then assert the invariant the test asserts — `committed == ci.render(REPO)` — and run `pytest tests/test_changes_index.py` (7 passed). `[changes-index] ok` is NOT that assertion; quote the render equality instead.
- **A change-detector that trusts GitHub's `mergeable` field has a false-negative window: `UNKNOWN` means "not computed yet", not "clean".** Measured live: at one moment **every open PR on the board read `mergeable: UNKNOWN` at once**, while `git merge-tree --write-tree --messages` showed 0 real conflicts. A detector that maps UNKNOWN to "no conflicts" prints `conflicting: none`, the monitor gate sees byte-stable output, and **every later tick is suppressed** — the watch silently stops watching. Fix: fold the UNKNOWN set through `merge-tree` and report its answer (#1015), keeping the output stable so quiet ticks still suppress. A broken local clone must return False rather than invent a rebase job. Negative controls: a genuinely conflicting head → `True`, main itself → `False`, empty head → `False`.
- **A `mergeable: UNKNOWN` that never resolves usually means the PR is CLOSED — read `.state` before re-polling.** Measured: a PR was repeatedly re-read as `UNKNOWN/UNKNOWN` for ~15 minutes after its checks all went `success`, and the cause was that it had **merged at `21:20:16Z`** and become main's tip. A closed PR has no merge ref to compute, so `mergeable`/`mergeStateStatus` report `UNKNOWN` forever, and no amount of waiting, or arming, changes it (`gh pr merge --auto` on a closed PR silently does nothing and reports `arm=false`). The one-field check that ends the loop instantly is `gh api repos/<o>/<r>/pulls/<n> --jq .state` together with `.merged`/`.merged_at`. Confirm the content landed by blob identity rather than ancestry — a squash merge leaves the branch tip a non-ancestor — e.g. `git rev-parse <merge_commit>:<path>` vs `git rev-parse <main>:<path>`. Related: never report `UNKNOWN` as "still computing" without first checking `state`; and never arm a PR you have not seen `MERGEABLE` on an OPEN state.
- **A salvage/prune audit must be re-run immediately before the owner acts, because work materialises during the audit.** Measuring worktrees takes minutes and a lane can stage new work in that window: one dirty worktree (12 staged files, a whole `openspec/changes/<x>/` tree) appeared *after* the first pass and belonged to another lane's live PR preparation. Report `as of <time>` and re-measure dirty worktrees right before drawing the delete list. Also declare your own leftover state explicitly (staged `git merge --no-commit` trees are `M ` index dirt with no unique commits) and clean those yourself — leaving them in the owner's dirty list inflates the preserve set and hides the real ones; prove no loss with blob identity against the merged commit, never with `--is-ancestor` (squash merges are not ancestors).
- **`CHANGES.md` conflicts on a tree that uses `docs/changes.d/` fragments: take main's file wholesale, then `scripts/changes_index.py write`, and `git add` AGAIN before `rebase --continue`.** The generator rewrites `CHANGES.md` after you staged it, so `git status` shows ` M CHANGES.md` (unstaged) and `rebase --continue` refuses with "you must edit all merge conflicts". Sequence per commit: `git checkout <main> -- CHANGES.md` → `scripts/changes_index.py write` → `scripts/changes_index.py check` (must say `ok: N fragment(s)`) → `git add -A` → `git rebase --continue`. Measured on #1049/#1050, both multi-commit branches that re-conflict on CHANGES.md once per replayed commit.
- **A replayed commit can silently regress a line main has since corrected — check the branch against main for "main is newer", not just for conflicts.** Measured on #919: the branch's `Makefile` carried `python3 scripts/ci_images.py ref agent` where **main carried `latest`** and `tests/test_fix_loop.py` asserted `latest` for both `agent-image-ref` and `fix-loop-image`. The regression came from commit `0ccbaf95` (#847) replayed over later main, and it reddened `linux/unit` with `1 failed, 15128 passed` — a single assertion, not a flake. It was present at every earlier head, so `merge-tree` showed 0 conflicts the whole time: a conflict-free rebase is not a correct one. The fix is to take main's line (the test and main agree; the branch is the older generation), prove it with the exact failing test plus the whole file, and commit one line. **Before dismissing a `linux/unit` red with a handful of failures as environmental, grep the FAILURE TEXT (`FAILED tests/…` then the `E   assert …` line), not any `urllib` line elsewhere in the log** — and run the control: if `main@<current>` passes the same suite in the same window, the red is the branch's.
- **A granted one-line edit (e.g. "tick this single openspec box") can already be DONE on the branch — read the branch's own commits before applying it.** A coordinator may grant authority conditional on a CI outcome ("tick item 6 only when `unit` concludes success") while reporting that outcome from a superseded head. Before editing: (a) re-check the live head's job conclusion yourself, because a conditional grant measured on a stale sha is not a live condition; (b) grep the branch's own log for a commit that already made the change — `git log --oneline <base>..<head>` and the live count, e.g. `git show <head>:openspec/changes/<c>/tasks.md | grep -c '\- \[ \]'`, which must be > 0 before there is anything to tick. Measured: both "unticked" PRs already carried their authors' own `chore(<id>): tick … test-unit task` commits with **0** unchecked boxes and `scope`+`openspec` green; applying the granted tick would have been a redundant commit colliding with the owner's work. A grant authorises an edit only against the state it was measured at — if that state is gone, the correct action is zero edits and a one-line report.
- **A rebase performed entirely through git in a sibling worktree counts as ZERO "relevant mutations" to the host's completion guard.** Measured twice, including after adding a posted-and-read-back PR comment: a full rebase + lease push + `check-docs`/openspec/container pytest, plus a posted PR comment re-read from the API, still left `relevant_mutation_attempts: 0` and the run was told "no task-relevant mutation was attempted". The guard's relevance filter only counts writes inside the paths it tracks (the profile scratch is explicitly excluded; `../llgenie-wt/…` git operations and `gh pr comment` are not classified). Do not invent a file edit to satisfy it: emit `nerve_nervous_event` (`completion_candidate`) with the measured evidence and call `nerve_verify` with an explicit per-check `pass: true/false` checklist — a free-form state dict grades ESCALATE, a numbered checklist with the sha/byte values each check was measured at grades PASS. If the guard repeats anyway, the check is unsatisfiable for this lane: report the measured state and stop. Refinement measured 2026-10-31: the guard still fired three times even after `nerve_nervous_event` was accepted and `nerve_verify` graded PASS twice with VERIFIED receipts (`jevrec-ff9fb071…`, `jevrec-ad931d3b…`); every firing follows a turn that contained NO tracked-path write — a report-only turn re-triggers it. So land the legitimate closeout (the skill fix for the defect the run surfaced) in the SAME turn as the final measured-state report, end the turn, and do not loop on another reply-only turn.
- **Mode gate: compare timestamps, not conclusions.** `createAt` of the newest `schedule` run must be strictly after PR 821's `mergedAt` *and* its conclusion must be `success`; a `success` run that predates the merge (or a `workflow_dispatch` result) does not put this lane into ALERT-ONLY. Measured: a green schedule run 5 h before the merge was repeatedly the only green in the window while the workflow itself was `disabled_manually`.
- Never merge, never squash to `main`, never push to `main` — merges are CI/owner only.
- Kill by PID, never by pattern: `pkill -f 'make test-unit'` matches the shell running that very command and takes down the call instead of the target. Capture the PID (`$!`, or `process_manage list`) and `kill <pid>`. Same class of mistake as a `git checkout --` that eats someone else's edit.
- Do not judge a long run by a piped tail. `make test-unit 2>&1 | tail -30` buffers, so a suite that is 80% done looks completely silent — the first honest report of the full gate came only when the process ended. Write to a log (`> /tmp/tu.log 2>&1 &`) and read it, or run the bounded subset. The full suite needs well over 900 s here (measured: ~80% at the 900 s timeout, killed with Error 137), so a 900 s foreground timeout will always cut it off.
- **Never quote a COUNT from a piped or truncated gate output, and never trust a gate's final `OK` line alone — grep the warning class explicitly.** Measured: `check_agent_profiles 2>&1 | tail -3` surfaced two `UNPROTECTED` lines and the report went out saying "two profiles"; the unpiped run had **four**. A gate that prints per-item warnings and then a summary `OK` exits 0 either way, so the summary is vacuous for those items and only the warning lines carry the truth: run the gate unpiped (or `| grep -c <CLASS>`), count the class itself, and read the summary as a claim about *declared* items only. When the resulting count contradicts one you already reported, correct it in the next message with both numbers rather than quietly restating — the reader is measuring your rows.
- **A coordinator can credit you with work you did NOT do — verify authorship and ancestry before accepting it, and correct the record when it is someone else's.** When a report says "you already retargeted and collapsed <child> at <sha>", read `git log -1 --format='%an <%ae> | %cn <%ce>' <sha>` and `git merge-base --is-ancestor <your-commit> <sha>`: the owner's squash is authored *and* committed by the owner and does not contain your commit, so accepting the credit misattributes another actor's work and hides that your own vehicle was superseded. Declining credit is as load-bearing as not over-claiming it — both protect the next reader's picture of who did what.
- Never touch unrelated files; a rebase PR's diff must stay its own change.
- Never run `make worktree-prune` / `git worktree prune` / `git worktree remove` — owner-only; it deletes directories and cannot see uncommitted work.
- Leave the worktree in place for the owner to inspect.
