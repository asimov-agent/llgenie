# A gated Hub file is not a dead link

## Why

The weekly `registry-sync` fails on a link it calls dead, before it reaches the store (issue #418):

```
FAIL: 1 newly-generated link(s) do not resolve (HTTP):
  https://huggingface.co/meta-models/Muse-Spark-Open-816B-A42B/resolve/main/chat_template.jinja
```

Measured 2026-10-20: the repo answers `200`, the file answers **`401`** — it exists and this token may not
read it. `scripts/gen_trending_quant_catalog.py::_probe_exists()` returned `True` only for `200`/`206`, so
`401`/`403` and `404` were the same answer. One gated model therefore blocks the whole weekly refresh.

The repo already settled the distinction elsewhere: `make web-coverage` treats `401/403` as reachable and
only `404` / `5xx` / a failed read as dead (OpenSpec `agent-web-reach`).

## What Changes

- **`scripts/gen_trending_quant_catalog.py`** — `_probe_status()` classifies a link as `ok` (200/206),
  `gated` (401/403) or `dead` (everything else); `_probe_exists()` keeps its meaning for callers ("really
  there"), and the sync fails only on `dead`, printing `gated=N` and naming the gated URLs.
- **`tests/test_quant_generator_edges.py`** — the existing seams move to `_probe_status`, plus two cases:
  the status classifier (200/206 ok, 401/403 gated, 404 dead) and a gated new link that no longer reds a
  sync but is written and reported.
- **README** — one line: a gated file is reported, not fatal.

## Impact

- Affected specs: `catalog-link-probe` (new capability).
- Affected code: `scripts/gen_trending_quant_catalog.py`, `tests/test_quant_generator_edges.py`,
  `README.md`, `agent-wiki/`.
- No data change: the catalog is regenerated by the weekly job, which no longer dies on a gated model.

## Not covered

- Whether the runner's `HF_TOKEN` is authorized for `meta-models/*` is a repo setting, not code; the probe
  must be right either way.
- The lossy store that also reds `registry-sync` is andyholst/trending-local-llms#463.
