# A starved queue is documented as supply, not as a broken PR

## Why

On 2026-10-28 the repository could not finish a CI run: 18 runs `queued`, 0 `in_progress`, with GitHub
reporting `Actions: operational`. Every open PR's checks stayed `pending`, every PR read `BLOCKED`, and the
automation that depends on CI green (`auto-merge`, `fix-bot`, `rebase-bot`) correctly did nothing. Three
agents spent about an hour on it and one recommended merging to drain the queue — which cannot work, because
`ci.yml` sets `cancel-in-progress` on `pull_request` and a push re-queues the whole matrix.

`docs/BOTS.md` described the `queued-alarm` workflow as "reports CI jobs queued far too long" and nothing
else: no way for a reader to tell a starved queue from a broken PR, so each reader re-derived it — two of
them wrongly.

## What changes

One hand-written section in `docs/BOTS.md`, **A queue is not a verdict**, placed after the generated
dispatch table (`<!-- dispatch-forms:begin/end -->` is regenerated by `make dispatch-forms-report`, so a
paragraph inside it would be overwritten):

1. the two commands that measure supply — `gh run list --json status` counts, and `gh run view <id> --json
   jobs` for the per-job wait;
2. the distinction from #801: one PR's empty rollup with `mergeStateStatus: DIRTY` is a branch needing a
   rebase, while repo-wide `queued`-with-nothing-running is supply;
3. "never merge or push to drain the queue", with the measured cost.

It points at the existing measurement (`make queued-alarm`, `scripts/queued_run_alarm.py`, `minutes` default
30) rather than adding a second one.

## Impact

- Documentation only: no target, no gate, no workflow change.
- Two proposed discriminators are recorded as **wrong** because they were measured first: `runner_name` is
  `null` for an `in_progress` job too, and `startedAt` is set at enqueue rather than at pickup. The doc states
  the measurement that does work (age of a `queued` job against a zero `completedAt`).
