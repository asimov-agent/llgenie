# Spec Delta — nonroot-user-dockerfiles (#2504)

## ADDED Requirements

### Requirement: Every shipped Dockerfile declares a non-root service user

All 36 shipped engine Dockerfiles (4 shared bases, 32 engine variants) SHALL specify a `USER` with a non-root uid as the trailing runtime identity, satisfying trivy `DS-0002`. The user SHALL be created idempotently so bases that already define uid/gid 1000 are not double-created. `containers/test/Dockerfile` is OUT of this scope: it is a hash input of the published `llgenie/test` CI image, and editing it in a fork-head PR moves a GHCR tag no PR token may publish (issue #155) — every `test-env`-consuming job then fails at pull (measured on PR #2517 head `09f814f79`: `ci-images` SKIP-publish `test:8fb483ae90f5`, then `linux/lint`, `linux/unit`, `linux/install`, `linux/cpu-health` red on `make test-env`). Its non-root fold needs the publish-order lane filed as its own issue.

#### Scenario: Generated engine image serves unprivileged

- **Given** an engine skill regenerated by `make generate-engine-params`
- **When** the rendered Dockerfile is inspected
- **Then** it contains the idempotent uid/gid 1000 create `RUN` and a trailing `USER 1000:1000` before the `HEALTHCHECK`

#### Scenario: Upstream base that already owns uid 1000

- **Given** a prebuilt variant whose upstream base (e.g. `nvcr.io/...`, `lmsysorg/sglang/...`) already defines uid/gid 1000
- **When** the image builds
- **Then** the create `RUN` succeeds via its `getent` guards without adding a duplicate identity

### Requirement: Build stages in derived images stay privileged

Every derived engine Dockerfile SHALL re-enable `USER root` immediately after each `FROM` (including multi-stage runtime bases), so build-time installs behave exactly as before the change.

#### Scenario: Compile stage after a USER-1000 base

- **Given** a shared base Dockerfile ending in `USER 1000:1000` and a derived stage `FROM llgenie/base-<backend>:<tag>`
- **When** the derived stage runs `apt-get`/`engine_runner.py install`
- **Then** it runs as root (the `USER root` line follows the `FROM`) and the build output is unchanged

#### Scenario: Misconfig scan clears

- **Given** the tree after this change
- **When** `trivy-misconfig` runs the shipped rule set over the repo's Dockerfiles
- **Then** zero `DS-0002` findings are reported (negative control: the pre-fix tree reports 37)
