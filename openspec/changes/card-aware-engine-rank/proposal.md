# Proposal: card-aware-engine-rank

Issues: llgenie #225 (this change). Related, NOT part of it: #227 (the explicit
per-range VRAM filter for the model list), #228 (the mock grid), #231
(analysis → issues). Upstream root: the trending-local-llms README rule "a
measurement on a bigger card does not qualify a smaller tier, because what it
needed there is unknown" (its card-fit section, issue #337) and its consumer
speed scope ("GPUs up to 48 GB, Apple Silicon, CPU; datacenter parts never
count").

## Why

`rank_engines` (`scripts/model_engine_pick.py`) picked a model's best engine on
this host by **raw t/s within a coarse backend class** (CUDA / ROCm / Metal /
CPU). A backend class has no notion of how powerful the measuring machine was,
so a figure from far beefier hardware of the same backend could become the top
recommendation on a small consumer card — and the top engine is what plain
`llgenie` offers and downloads (`engines[0]`, `--auto`, the interactive list's
first row).

Measured on the vendored registry (2026-10-13) for a 16 GB CUDA card, i.e. what
a user with that card was actually steered to:

| model | engine offered first | figure | measured on |
|---|---|---|---|
| `qwen3.8-27b` | vLLM | 300 t/s | 2x RTX 4090 (48 GB) |
| `qwen3.8-flash-next-125b` | Strata | 140 t/s | RTX 3090 24GB |
| `qwen3-14b` | Ollama | 65 t/s | RTX 3090 24GB |

Every one of those was labelled `same_hw=True` — "measured on hardware like
yours" — although the card was two to three times the user's. The registry holds
the evidence to do better: each measurement names its `hardware`, and upstream's
own README publishes the card-fit rule and the consumer/datacenter scope. t/s
scales with memory bandwidth and VRAM, so a figure from a bigger card predicts
nothing for a smaller one; only a figure from a card of this host's class or
smaller is a fit claim.

The same rule catches the datacenter case: a B300 figure (21 000 t/s for
`lfm2.5-24b-a2b`, single NVIDIA B300) ranked third for a 16 GB card, above every
consumer figure. Upstream never counts a datacenter part; llgenie did.

## What Changes

- `scripts/model_engine_pick.py`:
  - `measurement_card_gb(hardware)` — the card a measurement ran on, from the
    registry's own free-text `hardware` string: an explicit `NN GB` wins, else a
    known card model, else `None` (a host that is not a card, a cluster, a bare
    `"GPU"`). `2x RTX 3090` multiplies. The table and the parsing are upstream's
    (`_CARD_VRAM`, `hardware_vram_gb`), so llgenie and the README agree on what a
    hardware string means.
  - `datacenter_hardware(hardware)` — H100/A100/B300/MI300/GB200 ... : a
    datacenter part never counts as a fit, mirroring upstream's `_DATACENTER_HW`.
  - `rank_engines(model, arch, ids, gb)` — ranks become
    `0` proven on this card class (same backend AND a card no bigger than this
    host's), `1` same backend on a bigger card, `2` same backend with no card
    named, `3` another backend, `4` datacenter, `5` supported without a figure;
    within a rank, t/s then engagement. Rows gain `card_gb` and `card_class`.
    `same_hw` keeps its meaning — "this figure describes hardware like yours" —
    and is now exactly rank 0. The card class applies only where the host
    hardware IS a card (`cuda`/`rocm`/`vulkan`); an Apple-Silicon or CPU host is
    judged by unified memory / RAM, as upstream does.
  - `tps_label(e)` — the ONE place a row's t/s becomes text: `124 t/s`,
    `96 t/s (ROCm)`, `300 t/s (CUDA, 48 GB card)`, `67 t/s (CUDA, card unknown)`,
    `21000 t/s (CUDA, datacenter)`, `supported`.
  - `rank_models`, `recommend` and `matrix` pass their card size into
    `rank_engines`, so the trend list's server per row is card-aware.
- `scripts/llgenie_serve.py`: `_tps_label` delegates to `model_engine_pick.tps_label`
  (one rule, not two).
- `tests/test_card_aware_rank.py` (new): the hardware-string table, the ranking
  cases, the labels, the no-card-class path, and the real vendored registry's
  #225 acceptance case.
- Existing tests updated for the renumbered ranks and the shared label
  (`tests/test_trend_pick.py`, `tests/test_model_engine_pick.py`,
  `tests/test_trend_list_acceptance.py`).
- `tests/fixtures/trend-list-matrix.json` regenerated by
  `make render-trend-list-matrix`: the committed card-aware grid is the visible
  diff a reviewer reads.
- `README.md` + `agent-wiki/2026-10-17-card-aware-engine-rank.md`.

`data/models.json` is NOT touched: the vendored registry stays a verbatim copy
of upstream, and every field this change reads (`engines[].hardware`) is already
in it.

## Out of scope

- The model-list filter itself (#227): which models are "in the set llgenie
  works with for range R". Today the list still uses the coarse `vram_tier`
  (`fits()`); the card-fit evidence ladder upstream now derives (`ran-on` /
  `weights-only` / `declared`, `vram_min`) is that change, not this one.
- The mock `(arch, ram, vram)` grid and its per-engine regeneration (#228).
- Any change to `data/models.json` or to `make sync-registry` (#227).
- Upstream's `weight_gb` / `system_ram_min` / `storage_offload` fields, which
  arrive with the next weekly sync and are unused here.

## Impact

`scripts/model_engine_pick.py`, `scripts/llgenie_serve.py`,
`tests/test_card_aware_rank.py` (new), three existing test files,
`tests/fixtures/trend-list-matrix.json`, `README.md`, `agent-wiki/`, plus this
OpenSpec change. The default engine (and therefore the download) for a model can
change on every backend — that is the point — and the committed matrix fixture
shows exactly where.
