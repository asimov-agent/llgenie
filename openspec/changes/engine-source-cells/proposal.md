# Five engine cells claim a source build they do not have — build them, or record why not

## Why

`make check-engine-source` (issue #615, `scripts/engine_source_guard.py`) is in `ci-unit` and passes today
only because five cells carry an entry in `KNOWN_NOT_SOURCE`:

| cell | what its install actually does |
|---|---|
| `freetoken/cuda` | `uv pip install 'freetoken[accel]==0.2.1'` — a PyPI wheel |
| `litert/cpu` | `uv pip install litert-lm==0.18.1` — a PyPI wheel |
| `mlx/cpu`, `mlx/cuda` | `uv pip install 'mlx[cpu\|cuda13]' mlx-lm==0.32.2` — PyPI wheels |
| `tensorfold/cuda` | `curl … tensorfold-1.1.6-linux-x86_64.tar.gz`, sha256-verified — a release archive |

Each of those params files says `prebuilt: false`, i.e. it promises the image is compiled at the pin with
that backend's parameters. It is not: the image contains an upstream artefact. The dispatch sweep
(`make build-engines VERIFY=1`) then verifies a binary nobody in this repository built, so a broken build
recipe for those engines is invisible until a user hits it.

The other nine non-source cells are honest — they say `prebuilt: true` — and are out of scope here (each is
filed as its own linked issue by this change, per `AGENTS.md`).

## What changes

1. **`freetoken/cuda`** — clone `FlashML-org/FreeToken` at the pinned sha and run its own `setup.py`
   (`uv pip install --no-build-isolation -e .`), which names its CUDA fat arch list itself
   (`sm_75/80/90/100/120` + `sm_75` PTX); torch comes from PyPI's cu130 build, as the project's own
   pyproject documents.
2. **`mlx/cpu`, `mlx/cuda`** — build mlx's C++ core from `ml-explore/mlx` at the tag `mlx-lm` pins
   (`v0.32.2` = `1f8e74e3…`) with `MLX_BUILD_CUDA=ON` (or CPU only), then install `mlx-lm` from its own
   pinned tree. Both cells need the BLAS/LAPACK headers mlx's `CMakeLists.txt` looks for, so
   `container.<backend>.apt` names them.
3. **`tensorfold/cuda`** — the premise in `KNOWN_NOT_SOURCE` ("upstream ships no buildable tree") is false
   at the pin: the tree is a Zig project (`build.zig`, `.zig-version` = 0.17.0) that builds the CUDA server
   with its own `nvcc` fatbin step. Convert it to a source build, or — if the measured build cannot finish
   here — record the dated decision, with the wall-clock and disk it measured.
4. **`litert/cpu`** — the pip package is a Bazel-built wheel; the repo carries no `pyproject.toml`, and the
   CMake super-build produces a different CLI (`litert_lm_main`) than the skill's `litert-lm serve`. A
   time-boxed build attempt decides between a conversion and a dated decision.
5. Every converted cell loses its `KNOWN_NOT_SOURCE` entry in the same commit, so a regression to a
   wheel/archive install turns `make check-engine-source` red naming that engine/arch.

Scope decision (the refinement's open question): **(a) the five mislabelled cells.** The nine honestly
labelled `prebuilt: true` cells are nine multi-hour builds (ollama Go ×4, vllm from source ×3, sglang cuda,
tensorrt-llm cuda) whose cost must be measured before the sweep enables them; each is filed as its own
linked issue by this change rather than folded in.

## Impact

- `skills/engines/{freetoken,mlx,tensorfold,litert}/SKILL.md` — real `install.<backend>` steps and
  `container:` apt/base blocks.
- `containers/engines/params/*.json` + `containers/engines/dockerfiles/**` — regenerated by
  `make generate-engine-params`.
- `scripts/engine_source_guard.py` — `KNOWN_NOT_SOURCE` shrinks as cells convert.
- `tests/test_engine_source_guard.py` — the converted cells' committed params are asserted to be source
  builds after `generate-engine-params`.
- `README.md` (engine-image rule + recorded exception), `agent-wiki/2026-10-29-engine-source-cells.md`,
  `CHANGES.md`.
