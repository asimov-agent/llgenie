# requirements-pins — spec delta

Capability: `requirements-pins`
Issue: [#754](https://github.com/asimov-agent/llgenie/issues/754)

## ADDED Requirements

### Requirement: every direct runtime dependency is pinned exactly

`tools/requirements.in` SHALL name each direct runtime dependency with an exact `==` pin, so the
version the repository runs is stated by the repository rather than chosen by the resolver at
compile time.

WHEN the compile inputs are read,
THEN every direct requirement line in `tools/requirements.in` SHALL either carry a `==` pin, or
carry a `>=` floor naming the advisory (`GHSA-…` / `CVE-…`) that demands it, and no direct
requirement SHALL be bare or range-pinned without one.

#### Scenario: a bare direct dependency is a finding
Given `tools/requirements.in`,
When   the direct requirement lines are parsed,
Then   each is either an exact `==` pin (`numpy`, `gguf`, `huggingface_hub[cli]`) or an advisory
       floor, and a line with neither fails the check.
- **Test:** `tests/test_requirements_pins.py::test_every_direct_runtime_dependency_is_pinned_exactly`

### Requirement: a scanned advisory's fixed version is stated as a floor

For every package the security scan reports with a fix available, the compile inputs SHALL carry a
minimum version equal to the report's own `fixed` value, annotated with the advisory identifier, so
pip-compile can never resolve below it.

WHEN the scan reports `certifi`, `filelock` or `urllib3` with a fixed version above the compiled
pin,
THEN `tools/requirements.in` (and `tools/requirements-dev.in`) SHALL state that version as a `>=`
floor with the advisory named in a comment.

#### Scenario: the scanned floors are present and annotated
Given the compile inputs,
When   the floor lines are parsed,
Then   `certifi>=2026.10.18`, `filelock>=4.2.1` and `urllib3>=2.8.0` each appear with the
       advisory (`GHSA-…` / `CVE-…`) that demands them in the same line's comment.
- **Test:** `tests/test_requirements_pins.py::test_scanned_packages_carry_an_annotated_floor`

### Requirement: compiled pins never sit below a stated floor

Both compiled files SHALL be regenerated from their `.in` source and SHALL hold every floored
package at or above its floor, in the runtime file and in the dev file.

WHEN the compiled files are read,
THEN each floored package's compiled pin SHALL compare greater than or equal to the floor, and a
pin below it SHALL be a finding.

#### Scenario: a compiled pin below its floor fails
Given `tools/requirements.txt` and `tools/requirements-dev.txt`,
When   each floored package's compiled pin is compared with its floor,
Then   no compiled pin is below its floor, and the dev file (installed alongside the runtime file
       in the test image) carries the same floors.
- **Test:** `tests/test_requirements_pins.py::test_compiled_pins_are_at_or_above_every_floor`

### Requirement: the compiled files are generated, never hand-edited

A change to a compiled pin SHALL arrive through `make -C tools generate-requirements` /
`generate-requirements-dev`; the `.txt` files SHALL keep the generator's header.

WHEN a compiled file is inspected,
THEN it SHALL carry the `autogenerated by pip-compile` header, and a re-run of the generator on the
committed inputs SHALL leave the file unchanged.

#### Scenario: the generator is idempotent on the committed inputs
Given the committed `requirements.in` / `requirements-dev.in`,
When   `make -C tools generate-requirements` and `make -C tools generate-requirements-dev` are re-run,
Then   both `.txt` files are byte-identical to the committed ones.
- **Test:** CI job `ci-unit` -> `make check-security-bumps`; locally `make -C tools generate-requirements && git diff --exit-code tools/requirements.txt`
